# 全栈业务系统脚手架与建模范式

> 来源：从 LITECRM 的实际设计、返工与收口过程中提炼。
> 用途：启动新的中小型企业业务系统时，作为仓库骨架、建模原则、工程门禁和迭代顺序的默认蓝图。
> 边界：本文不是 CRM 规格，也不要求新项目继续使用相同 UI 库或业务对象；凡涉及客户、商机、报价等内容，都只作为例子。

---

## 一、范式定位

一句话概括：

> 以模块化单体承载业务，以 PostgreSQL 保存权威事实，以 OpenAPI 单向生成前端契约；桌面端和移动端共享业务语义但采用不同交互；所有重要规则同时落到文档、约束、事务和测试中。

这套范式优先解决以下项目：

- 5–50 人团队使用的内部业务系统或轻量 SaaS；
- 以表单、流程、状态变化、审批、时间线、列表和管理统计为主；
- 同时存在桌面管理端和移动执行端；
- 业务规则会持续演化，但尚不需要多团队独立部署微服务；
- 正确性、可追溯性和可维护性比极限吞吐更重要。

以下情况应调整或放弃本范式：

- 只有一次性原型：可先使用单应用，但仍建议保留迁移和 DTO 校验；
- 完全离线或强本地优先：需要额外设计同步、冲突合并和本地数据库；
- 多团队必须独立发布、独立扩缩容：再按稳定领域边界拆服务，而不是一开始就上微服务；
- 实时流处理或超高吞吐是主矛盾：应重新选择存储、消息和计算架构。

## 二、最核心的九条原则

### 1. 同一业务事实只维护一次

订单、付款、处理记录、审批结果等事实只能有一个权威写入位置。日历、看板、提醒、周报和统计都是读取投影，不得复制出第二套可编辑状态。

判断方法：如果两个页面都能修改“同一件事”，但修改后还需要额外同步，通常已经产生了第二事实源。

### 2. 历史事实、当前状态、未来行动分开建模

- 历史事实：只追加，回答“发生过什么”；
- 当前状态：可变聚合，回答“现在是什么情况”；
- 未来行动：独立对象，回答“下一步准备做什么”；
- 读取投影：可重算，回答“怎样高效展示和分析”。

不要让一张表同时承担四种职责，也不要用修改历史记录来表达新的业务变化。

### 3. 命令保护不变量，查询服务于决策

重要变化应暴露为有业务含义的命令，例如“批准”“作废”“结案”“移交”，而不是允许前端任意 PATCH 状态字段。命令负责权限、前置条件、事务、审计和并发；查询可以为页面组合所需字段。

### 4. 后端是权限与契约的最终裁决者

前端隐藏按钮只是体验优化，不是安全边界。后端统一回答：

- 当前用户能做什么；
- 当前用户能看哪些数据；
- 当前命令是否满足业务条件；
- 请求与响应的结构是什么。

### 5. 双端共享语义，不强求共享页面

桌面端面向批量管理、比较和分析；移动端面向现场执行、快速补录和待办处理。两端共享 DTO、API client、枚举、权限快照和业务格式化，但页面结构、导航和信息密度可以不同。

### 6. 强一致先用同一事务，弱提示优先实时派生

必须一起成功或失败的写入放在同一数据库事务中。提醒、风险和管理统计优先从权威事实派生，只有明确出现跨进程、可靠重试、削峰或独立扩展需求时才引入消息队列。

### 7. 可变数据必须识别并发覆盖

所有可变聚合带 `version` 和 `updatedAt`；更新使用 `WHERE id = ? AND version = ?`，成功后版本递增。旧页面提交返回 409，要求刷新，而不是让后提交静默覆盖先提交。

### 8. 派生字段必须能检查和重建

缓存字段、首次时间、最近活动、风险标签等只要进入列表筛选或管理统计，就必须明确：

- 权威来源是什么；
- 哪些写命令维护它；
- 如何检测漂移；
- 如何全量重算。

### 9. 规格、代码、迁移和测试必须同一变更收口

规则变化不能只改页面。一个完整变更通常同时检查 PRD、模型、DTO、OpenAPI、共享类型、数据库迁移、双端行为和测试。Git 记录“改了什么”，当前文档只保留“现在应该怎样”。

## 三、推荐仓库骨架

默认采用 pnpm workspace + Turborepo 的 monorepo：

```text
project/
  apps/
    web/                    # 桌面管理端
      src/
        pages/              # 路由页面，只做编排
        components/         # 页面级与通用展示组件
        features/           # 可选：领域组件
        router/
        theme/
    mobile/                 # 移动执行端；不需要移动端时可删除
      src/
        pages/
        components/
        features/
        router/
        theme/
    api/                    # 模块化单体 API
      src/
        access/             # 能力与数据范围
        auth/               # 身份、会话、令牌
        org/                # 用户与组织树
        audit/              # 审计
        catalog/            # 可配置字典
        <business-domain>/  # 每个领域一个纵向模块
        reporting/          # 只读管理聚合
        alerts/             # 派生提醒与已读回执
        common/             # DB、错误、日期等基础设施
      drizzle/              # 已提交迁移与快照
      scripts/              # seed、迁移兼容、投影检查
  packages/
    contracts/              # OpenAPI 及生成的 TypeScript 类型
    domain/                 # Web/Mobile 共享业务客户端层
      services/             # 薄 API client
      stores/               # 跨页状态
      composables/          # query、权限、格式化
      types/                # 非 API 类型
    design-tokens/          # 颜色、间距、字号、圆角、状态语义
    eslint-config/          # 共享代码规范
    tsconfig/               # 共享 TS 配置
  docs/
    01-当前有效/
    02-参考资料/
    03-实施证据/
    99-历史归档/
  docker/
  .github/workflows/ci.yml
  docker-compose.yml
  pnpm-workspace.yaml
  turbo.json
  package.json
```

### 依赖方向

```text
Web / Mobile 页面
       │
       ▼
packages/domain（服务、状态、共享语义）
       │
       ▼
packages/contracts（后端生成的 API 类型）

API Controller → Application Service → 领域规则 / DB
                         │
                         ├─ access / audit
                         └─ 同事务内的其他领域服务
```

硬约束：

- 页面不直接 `fetch`，不自行拼 URL；
- API 类型不在前端重复声明；
- 后端业务模块不得反向依赖 Web/Mobile/domain client；
- 共享层不引入 Element Plus、Vant 等端专属 UI；
- 跨模块写协作通过显式 service 接口和事务，不直接随意操作对方表；
- reporting 和 alerts 默认只读权威事实，不拥有第二套业务状态。

## 四、技术栈：默认值与可替换边界

| 层     | 默认实现                             | 保留的能力                       | 可替换项                      |
| ------ | ------------------------------------ | -------------------------------- | ----------------------------- |
| 仓库   | pnpm workspace + Turborepo           | 工作区、任务编排、缓存、统一命令 | Nx、Bazel 或单仓脚本          |
| Web    | Vue 3 + TypeScript + Element Plus    | 桌面管理交互                     | React/Angular、其他 UI 库     |
| Mobile | Vue 3 + TypeScript + Vant            | 移动 H5 快速执行                 | React、原生、小程序           |
| API    | NestJS 模块化单体                    | DTO、Guard、模块边界、DI         | Fastify、Spring Boot、ASP.NET |
| 数据   | PostgreSQL + Drizzle + SQL 迁移      | 事务、约束、关系、可审阅迁移     | Prisma、Hibernate、EF Core    |
| 契约   | Swagger/OpenAPI + openapi-typescript | 后端单源、生成类型、CI 无差异    | protobuf、GraphQL codegen     |
| 状态   | Pinia + 轻量 `useQuery`              | session、缓存、加载/错误/刷新    | TanStack Query、Redux Toolkit |
| 测试   | Vitest + supertest + 真实 PostgreSQL | 分层测试、真实约束               | Jest、JUnit、xUnit            |

技术可以换，以下能力不能丢：契约生成、迁移驱动、服务端权限、真实数据库测试、并发检测和统一质量门禁。

### 保持简单的升级触发器

| 当前默认        | 什么时候升级                                      |
| --------------- | ------------------------------------------------- |
| 模块化单体      | 不同模块需要独立团队、独立发布或差异化扩缩容      |
| 同步事务        | 跨服务后确实无法共享事务，且需要可靠重试/最终一致 |
| 轻量 query 封装 | 出现复杂缓存、失效、预取、离线或无限滚动需求      |
| 实时派生提醒    | 查询成本不可接受，或需要外部推送与可靠投递        |
| 单 PostgreSQL   | 数据规模、隔离、检索或分析负载已有明确瓶颈证据    |

不要因为“以后可能需要”提前支付复杂度。

## 五、数据建模基线

### 5.1 先判断表属于哪一类

| 类型         | 例子                       | 写入方式             | 基础字段                         | 是否允许重建           |
| ------------ | -------------------------- | -------------------- | -------------------------------- | ---------------------- |
| 可变聚合     | 用户、主业务对象、当前流程 | 条件更新             | `id/createdAt/updatedAt/version` | 否，属于权威当前状态   |
| 只追加事实   | 操作记录、报价、审批事件   | 仅 INSERT            | `id/createdAt/occurredAt`        | 否，属于商业历史       |
| 独立未来行动 | 待办、预约、下一步         | 明确状态机           | 可变聚合字段 + 计划日期          | 否，但可由领域命令终止 |
| 读取投影     | 最近活动、时间线、风险摘要 | 同事务维护或批量重算 | 按查询需要                       | 必须可以               |
| 只读聚合     | 看板、漏斗、团队统计       | 查询时计算/物化      | 不提供业务写命令                 | 必须可追溯到事实       |
| 回执/偏好    | 提醒已读、个人设置         | 幂等 upsert          | 用户 + 稳定 key                  | 可以                   |
| 配置字典     | 业务分类、可选项           | 管理命令             | 稳定 key + label + 状态          | 历史引用必须仍可解析   |

### 5.2 当前状态与历史事件并存

主表保存当前状态，事件表保存变化历史。例如：

```text
case.status = resolved              # 当前快照，便于查询
case_events(type=resolved, ...)     # 不可变事实，便于追溯
```

这不是完整 Event Sourcing。主表仍是权威当前状态，事件用于历史、时间线和归因。

### 5.3 业务日期与审计时刻分离

- `occurredDate/plannedDate/expenseDate`：业务归属日，使用数据库 `date` 和 API `YYYY-MM-DD`；
- `createdAt/updatedAt/approvedAt`：系统真实时刻，使用带时区时间戳；
- “今天是否逾期”比较业务日期，不用 UTC 时间戳猜本地日期；
- 同一天的多条事实可用 `createdAt` 稳定排序。

### 5.4 状态变化必须是领域命令

对每个状态机明确：

1. 允许的前态和后态；
2. 谁可以执行；
3. 必填原因或结果；
4. 同事务联动什么；
5. 剩余行动怎样处理；
6. 重复提交返回什么；
7. 是否需要审计。

禁止通过通用更新接口让前端直接写 `status`。

### 5.5 事务边界按业务不变量划分

一项用户动作在业务上“只能一起成立”的内容必须同事务完成。例如：

```text
批准申请
  = 更新申请终态
  + 更新主对象归属
  + 写入移交历史
  + 交接未完成行动
```

Controller 不组织多步写入；应用 Service 是事务与业务不变量的边界。

### 5.6 数据库负责最后一道防线

- FK：引用对象必须存在；
- UNIQUE：真正的权威唯一键和幂等键；
- CHECK：金额非负、状态组合合法等局部约束；
- 索引：围绕真实列表、范围过滤、排序和聚合；
- 事务：保证跨表原子性；
- 业务流程不塞进触发器和存储过程，保持应用层规则可见、可测。

### 5.7 并发与幂等

- 可变聚合：乐观锁，旧版本返回 409；
- 名额/余额/唯一库存：事务内锁定被竞争的稳定父行，再校验并占用；
- 创建命令：权威唯一索引或幂等键兜底；
- 终态命令：重复提交不能生成第二份事实；
- 前端 loading 只能减少误点，不能代替服务端幂等。

### 5.8 派生值与提醒

派生值应有统一计算函数，写入路径与重建脚本复用同一口径。提醒尽量采用：

```text
权威业务事实 → 实时筛选仍需关注的事项 → 拼稳定 alertKey
                                              │
                                              └─ alert_reads 仅保存已读回执
```

源事项完成后提醒自然消失，不再额外同步“提醒已完成”。

## 六、权限、组织与审计

将三个问题拆开：

```text
身份：我是谁？
组织：我处于哪棵汇报树？
授权：我能执行什么操作、能看到哪些数据？
```

推荐默认模型：

- RBAC/能力点控制操作，例如 `record.write`、`approval.review`；
- 组织树推导数据范围，例如 `self/team/full`；
- 业务区域、分类、标签是数据属性，除非有明确规则，否则不混入权限模型；
- Guard 统一检查能力，AccessService 统一生成可见 ID 范围；
- 列表、搜索、下拉候选和看板都必须应用相同数据范围；
- 前端消费后端返回的权限快照，用于菜单和交互，但不自行推导角色规则；
- 审计记录“谁在何时对什么做了什么”，与授权解耦。

优先定义能力点，再把能力组合成角色。不要在业务代码中到处写 `role === 'admin'`。

## 七、契约与 API 工作流

### 7.1 单向契约链

```text
后端 DTO + 校验注解
        ↓
Swagger / OpenAPI
        ↓
生成 packages/contracts 类型
        ↓
packages/domain 薄 client
        ↓
Web / Mobile 页面
```

API 变更的标准顺序：

1. 修改 DTO、响应描述和后端行为；
2. 重新生成 OpenAPI 与 TypeScript 类型；
3. 调整 domain service；
4. 调整双端调用；
5. 更新测试；
6. CI 执行生成物 `--verify`，确保没有漏提交。

### 7.2 Controller 与 Service 的职责

Controller 只负责：路由、参数、DTO、能力 Guard、当前用户和响应描述。

Service 负责：数据范围、业务前置条件、事务、不变量、乐观锁、审计和错误语义。

推荐 HTTP 语义：

- 400：输入或跨字段规则错误；
- 401：未登录或会话失效；
- 403：无能力或超出数据范围；
- 404：对象不存在或按安全策略不可见；
- 409：版本冲突、状态冲突、唯一性冲突；
- 5xx：非预期故障，不向用户暴露堆栈。

## 八、双端前端范式

### 8.1 功能按使用情境分配

| 桌面端更适合                 | 移动端更适合                  |
| ---------------------------- | ----------------------------- |
| 批量管理、复杂筛选、横向比较 | 现场记录、拍照/定位、快速补录 |
| 配置、用户、权限、导入导出   | 今日待办、提醒、单对象执行    |
| 大表格、管理看板、深度详情   | 卡片、时间线、少字段表单      |

不要把桌面页面等比缩小到手机，也不要为了“功能一致”把低频配置塞进移动端。

### 8.2 共享边界

应该共享：

- 契约类型和枚举；
- API services 与错误规范化；
- session、权限快照和必要的跨页状态；
- 日期、金额、状态展示函数；
- 重合业务表单的字段语义和校验规则；
- 读取投影的类型。

不应强行共享：

- 完整路由页面；
- 桌面表格和移动卡片的布局；
- UI 库组件；
- 端特有导航与交互流程。

### 8.3 页面统一具备四种状态

每个读取页面至少处理：加载、空、错误、成功。写入过程还要处理提交中和冲突。

写入成功后通过 `reload()`、缓存失效或明确合并返回值更新界面，不依赖整页刷新；失败后保留用户输入。

### 8.4 影响性操作

删除、停用、作废、结案、释放等操作应：

- 与普通主操作视觉分离；
- 就地说明影响范围；
- 必要时要求原因；
- 提交前二次确认；
- 服务端再次验证；
- 成功后保留可追溯历史。

### 8.5 Timeline 的使用条件

当对象的价值主要来自“发生过哪些变化”时，用服务端统一输出的类型化 Timeline；未来待办作为未发生节点单独显示。不要由 Web 和 Mobile 各自拼接、排序同一批事实。

## 九、后端纵向模块模板

每个业务域优先形成一个可独立理解的纵向切片：

```text
<domain>/
  <domain>.module.ts
  <domain>.controller.ts
  <domain>.service.ts
  dto/
    create-*.dto.ts
    update-*.dto.ts
    query-*.dto.ts
    command-*.dto.ts
  __tests__/
    <domain>.spec.ts
```

拆分信号：

- Service 超过约 400 行且包含多组独立职责；
- 读模型 SQL 与写命令互相干扰；
- 一个模块同时维护主对象、导入、归属、统计等多条链路；
- 事务边界已经无法一眼看清。

此时按业务职责拆为 application services 或 projection/query services，而不是增加无意义的通用 Repository 层。

## 十、测试与质量门禁

### 10.1 测试不是覆盖实现，而是执行规格承诺

推荐测试地图：

| 层           | 重点                            | 典型方式                            |
| ------------ | ------------------------------- | ----------------------------------- |
| 纯逻辑单测   | 状态推导、权限树、金额/日期计算 | Vitest，无数据库                    |
| domain 集成  | HTTP 封装、token 刷新、store    | mock fetch + jsdom                  |
| API 集成/e2e | 权限、事务、约束、并发、主链    | Nest test app + supertest + 真实 PG |
| 前端组件     | 状态语义、关键交互、投影展示    | Vue Test Utils + jsdom              |
| 浏览器验收   | 少量关键主链、响应式布局        | 真浏览器，不代替自动测试            |

涉及数据库规则的测试必须打真实 PostgreSQL，不能用 mock 证明事务、索引或约束正确。

### 10.2 CI 固定顺序

```text
checkout
→ 安装锁定依赖
→ 启动一次性 PostgreSQL
→ 从空库执行迁移
→ lint
→ typecheck
→ test
→ build
→ contracts no-diff
```

空库迁移是门禁的一部分。“我的开发库能升级”不能证明迁移完整。

### 10.3 提交门禁

- Prettier 统一格式；
- ESLint 统一规则；
- husky + lint-staged 只处理快速检查；
- commitlint 使用 Conventional Commits；
- 全量测试和构建交给 CI；
- 锁文件、`.env.example`、迁移、seed 和启动说明必须提交。

### 10.4 测试数据原则

- seed 幂等，可重复执行；
- 测试数据使用固定 ID 或明确前缀；
- 只清理测试自己创建的数据；
- 清理失败必须让测试失败，不能吞错；
- 并发、终态重复提交、越权和空数据是关键边界，不是附加项。

## 十一、文档治理范式

文档按“权威程度”而不是按文件类型分类：

| 目录          | 作用                             | 能否决定当前实现 |
| ------------- | -------------------------------- | ---------------- |
| `01-当前有效` | PRD、架构、交互、质量、测试      | 可以             |
| `02-参考资料` | 竞品、理论、工程背景、可复用范式 | 不直接覆盖规格   |
| `03-实施证据` | 某批完成项、迁移、测试结果       | 只能证明做过     |
| `99-历史归档` | 旧方案、冻结稿、演变过程         | 不可以           |

冲突优先级：

1. 用户行为与验收口径看 PRD；
2. 对象、权限、事务和数据语义看架构；
3. 页面入口和衔接看交互设计；
4. 工程与验证看质量清单和测试指南；
5. 实施证据和 Git 不反向篡改当前规格。

规则变化时在同一提交同步相关文档；实现进度只记在 Git 和实施证据，不往 PRD 填开发流水账。

## 十二、新项目推荐里程碑

### M0：工程地基

- monorepo、Node/pnpm 版本锁定；
- web/mobile/api 最小可运行；
- PostgreSQL Docker、本地 `.env.example`；
- SQL 迁移、空库 CI；
- contracts/domain/design-tokens；
- lint/typecheck/test/build/contract 门禁；
- README 换机器启动说明。

### M1：身份、组织与权限

- 登录、刷新、退出、token 失效；
- 能力点、角色组合、数据范围；
- 前端权限快照、菜单与路由守卫；
- 服务端越权测试；
- 审计骨架。

### M2：第一个完整纵向切片

选择最能代表项目价值的一条主链，而不是先铺所有 CRUD：

```text
列表 → 新建 → 详情 → 一次关键命令 → 历史可追溯 → 双端可见
```

同时验证 DTO、契约生成、数据库迁移、权限、事务和测试方式。

### M3：跨域闭环

- 跨模块事务；
- 下一行动或审批；
- 终态与剩余事项处理；
- 幂等与并发；
- 时间线与写后刷新。

### M4：执行端与读模型

- 移动端高频闭环；
- 服务端分页、搜索和类型化投影；
- 管理者需要的最小只读聚合；
- 不复制业务状态。

### M5：可靠性收口

- 所有可变聚合乐观锁；
- 派生投影检查和重建；
- 提醒与已读；
- 空库迁移、真实数据库主链、浏览器验收；
- 文档与代码最终对齐。

### M6+：有证据后扩展

外部集成、对象存储、Excel、通知推送、性能专项、消息队列、AI 和服务拆分都应由真实使用证据触发。

## 十三、从 LITECRM 抽取新项目时怎样处理

### 可以原样复制

- workspace/Turbo 结构和根命令；
- ESLint、Prettier、husky、lint-staged、commitlint；
- contracts 的生成与 verify 流程；
- domain 的 HTTP client、session、`useQuery` 形态；
- design-tokens 的组织方式；
- Docker PostgreSQL、空库迁移 CI；
- 文档四级目录与维护规则；
- API 的全局 ValidationPipe、异常与 Swagger 骨架；
- `id/createdAt/updatedAt/version` 基础列模式。

### 必须参数化

- 项目名、包 scope、端口、数据库名；
- Logo、颜色、导航和 UI 文案；
- 角色、能力点、数据范围；
- 时区、业务日期和金额单位；
- 种子账号和演示数据；
- 部署域名、CORS 和 token 时长。

### 必须重新设计，不能照搬

- 业务实体、状态机和事务边界；
- 哪些记录是事实、状态、行动或投影；
- 权威唯一键和查重规则；
- 桌面端与移动端的功能分工；
- 管理统计口径；
- 外部系统的主数据归属；
- 正式数据迁移策略。

建议将真正的 starter repo 只保留一个中性的示例域（例如 `work-items`），用于示范列表、新建、乐观锁、事件记录和权限；不要让新项目从删除大量 CRM 模块开始。

## 十四、常见反模式

- 两端各写一套 API client、枚举和状态中文映射；
- 页面直接 fetch，URL 和请求体散落；
- 看板或周报复制业务明细并允许修改；
- 用一个 `status` 表达所有业务进度，历史靠覆盖；
- 把报价、审批建议等中间事实误当最终结果；
- 前端隐藏按钮后，后端不校验权限；
- 所有角色判断都写成硬编码 if/else；
- 只靠 `updatedAt` 展示“最近活动”，混淆业务发生日与系统修改时刻；
- 为了以后扩展过早引入微服务、消息队列和规则引擎；
- 数据结构变化使用运行时同步，不提交迁移；
- 单元测试大量 mock，却没有真实数据库事务与约束测试；
- 文档同时保留多个“最新版”，靠文件名日期猜权威性；
- 移动端只是桌面端缩小版，没有围绕现场动作重排。

## 十五、最小完成定义（Definition of Done）

一个业务功能只有同时满足以下条件才算完成：

- [ ] 权威事实、当前状态、未来行动和读取投影的归属清楚；
- [ ] DTO、校验、权限和错误语义明确；
- [ ] 跨表不变量处于同一事务；
- [ ] 数据库约束、索引和迁移已提交；
- [ ] 可变聚合使用版本条件更新；
- [ ] OpenAPI 和共享契约已生成；
- [ ] Web/Mobile 使用同一业务语义，按各自场景完成交互；
- [ ] 加载、空、错误、成功和冲突状态均可见；
- [ ] 单测覆盖纯规则，真实数据库测试覆盖权限、事务和并发；
- [ ] 规格、交互和实施证据按变化类型同步；
- [ ] `lint/typecheck/test/build/contracts:check` 全部通过；
- [ ] 从空数据库可迁移，从 README 可在新机器启动。

这份完成定义比“页面能打开、接口能返回”更接近一个可长期迭代的业务系统。
