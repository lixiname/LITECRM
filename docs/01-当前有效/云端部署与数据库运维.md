# 云端部署与数据库运维

本文是 Lite CRM 的正式部署手册。核心边界是：**迁移负责结构，bootstrap 只补首次基础数据，应用启动只启动服务。** 三者不得绑在同一启动命令中。

## 1. 部署拓扑与端口

| 服务            | 对外/内部端口                     | 说明                                  |
| --------------- | --------------------------------- | ------------------------------------- |
| 旧 CRM Demo     | `8081` / `3001`                   | 原有服务保留，本项目不占用            |
| Lite CRM 桌面端 | `8082`                            | Nginx 静态站点，`/api/` 反代到 `3002` |
| Lite CRM 移动端 | `8083`                            | Nginx 静态站点，`/api/` 反代到 `3002` |
| Lite CRM API    | `127.0.0.1:3002`                  | NestJS，由 PM2 守护，不直接对公网暴露 |
| PostgreSQL 16   | `127.0.0.1:5432` 或云平台内网地址 | 不对公网暴露                          |

仓库已提供 `ecosystem.config.cjs` 和 `deploy/nginx/litecrm.conf`。Nginx 的 `proxy_pass` 必须是 `http://127.0.0.1:3002`（末尾无 `/`），因为 API 自身带有 `/api` 全局前缀。

## 2. 数据库动作边界

| 动作       | 命令                                 | 写入内容                                                           | 执行时机                  |
| ---------- | ------------------------------------ | ------------------------------------------------------------------ | ------------------------- |
| 结构迁移   | `pnpm db:migrate:runtime`            | 已提交的增量 SQL，由 Drizzle 记录执行历史                          | 首次部署及每次发布        |
| 正式初始化 | `pnpm db:bootstrap`                  | 缺失的正式账号、汇报树、默认字典、S/A/B/C 名额、行政区划与销售大区 | 首次部署；排障时可重跑    |
| 初始化校验 | `pnpm db:bootstrap:verify`           | 只读校验账号、树、字典、名额和泵浦大区                             | bootstrap 之后            |
| 开发造数   | `pnpm db:seed` / `pnpm db:seed:demo` | 测试账号和演示业务数据                                             | 仅本地/测试，正式环境禁止 |

API 的 PM2 启动、重启和服务器重启均不会自动执行迁移、bootstrap 或 seed，因此不会在常规发布时重置业务数据。

## 3. 首次建库

迁移只能连接已经存在的数据库，不负责创建数据库本身。先通过云数据库控制台或 PostgreSQL 管理账号完成：

1. 创建 PostgreSQL 16 数据库 `litecrm`。
2. 创建 Lite CRM 专用账号，授予该库的建表、改表和读写权限。首期可使用数据库 owner；以后再按需拆分 migration/runtime 账号。
3. 在 `litecrm` 库启用 `pg_trgm`。首份迁移会执行 `CREATE EXTENSION IF NOT EXISTS pg_trgm`；云厂商禁止普通账号建扩展时，由平台管理员预先启用。
4. 确认数据库只允许服务器内网或本机访问。

密码不写入 Git、文档或命令历史。若数据库密码被组装进 URL，`@ : / ? # %` 等字符必须 URL 编码；优先使用云厂商给出的完整连接串。

## 4. 生产环境变量

PM2 配置的 `cwd` 是仓库根目录，NestJS `ConfigModule` 因此默认读取**仓库根目录的 `.env`**。服务器上从 `.env.example` 复制一份 `.env`，严禁提交：

```dotenv
NODE_ENV=production
PORT=3002
DATABASE_URL=postgresql://<user>:<encoded-password>@<host>:5432/litecrm
JWT_SECRET=<独立生成的高强度随机值>
JWT_ACCESS_TTL=2h
JWT_REFRESH_TTL=14d

# 仅首次 bootstrap 创建缺失账号时使用
BOOTSTRAP_ADMIN_PASSWORD="<管理员初始密码，至少 12 位>"
BOOTSTRAP_STAFF_PASSWORD_SUFFIX="<员工密码后缀>"

# 当前由 Nginx 同源反代，保持为空
CORS_ORIGINS=
ENABLE_SWAGGER=false
```

密码含分号或其他特殊字符时，在 `.env` 中使用引号包裹，不要临时拼接进 shell 命令。设置 `chmod 600 .env`。`JWT_SECRET`、数据库密码和初始账号密码不得复用。

## 6. 首次发布顺序

```bash
pnpm install --frozen-lockfile
pnpm build
pnpm db:migrate:runtime
pnpm db:bootstrap
pnpm db:bootstrap:verify

sudo install -d -m 755 /var/www/litecrm/web /var/www/litecrm/mobile
sudo rsync -a --delete apps/web/dist/ /var/www/litecrm/web/
sudo rsync -a --delete apps/mobile/dist/ /var/www/litecrm/mobile/

pm2 start ecosystem.config.cjs --env production
pm2 save
pm2 startup

sudo cp deploy/nginx/litecrm.conf /etc/nginx/sites-available/litecrm
sudo ln -s /etc/nginx/sites-available/litecrm /etc/nginx/sites-enabled/litecrm
sudo nginx -t
sudo systemctl reload nginx
```

`pm2 startup` 会输出一条需要以 sudo 执行的系统命令，按它的输出执行一次，然后再 `pm2 save`。如果 Nginx 启用链接已存在，不要重复创建；确认指向正确配置后直接测试。

## 7. 发布验证

先在服务器本机验证 API 与数据库：

```bash
curl --fail http://127.0.0.1:3002/api/health
```

正常返回应包含 `"status":"ok"` 和 `"database":"ok"`。然后验证：

1. `http://<server>:8082` 桌面端能登录，`http://<server>:8083` 移动端能登录。
2. 旧 Demo 的 `8081` 仍可访问。
3. admin、纯管理、executive、sales 和 assistant 的菜单与数据范围符合权限矩阵。
4. 字典、客户分级名额和“泵浦”大区已存在。
5. 手工设置人员所属大区后，用少量 Excel 客户先做预览/查重，再导入全量数据。

首次登录后应尽快修改初始密码，然后从服务器 `.env` 移除两个 `BOOTSTRAP_*` 变量。已存在账号不会因为后续重跑 bootstrap 而改密。

## 8. 后续发布

1. 备份数据库并确认备份可恢复。
2. `git pull --ff-only`，然后 `pnpm install --frozen-lockfile`。
3. `pnpm build`。
4. `pnpm db:migrate:runtime`。
5. 同步 Web/Mobile `dist` 到 Nginx 目录。
6. `pm2 reload ecosystem.config.cjs --env production`。
7. 执行 health check 和登录、客户查询、商机跟进、周视图等关键冒烟。

`db:bootstrap` 不是日常发布步骤。Drizzle 会记录已执行迁移；没有新迁移时，`db:migrate:runtime` 是空操作。功能更新若不改变库结构，不需要重新初始化业务数据。

## 9. 迁移安全与回滚

- 所有结构变化必须形成新的、提交进 Git 的增量迁移；正式库禁止 schema push。
- 不修改已在正式环境执行过的迁移文件；修正时新增下一份迁移。
- 删字段、改类型、大量回填和新增唯一约束属于高风险迁移，必须先在正式备份副本上演练。
- 应用与迁移存在兼容窗口时，采用“先扩展、后切换、再清理”，不在一次发布中直接删除旧字段。
- 代码可回滚到上一版，数据库不默认依赖反向 SQL。故障时先停止发布与风险写入，判断旧代码能否兼容新结构；不兼容且数据已受影响时，按已演练的备份恢复方案执行。

备份、空库迁移演练和发布后验证是正式发布的一部分，不是附加动作。
