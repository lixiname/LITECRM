# 云端部署与数据库运维

本文规定 Lite CRM 首次上云、后续发布和数据库维护的执行边界。核心原则是：**迁移负责结构，bootstrap 负责首次基础数据，应用启动只负责启动服务。三者不得混在一起。**

## 1. 三类数据库动作

| 动作       | 命令                                 | 允许写入的内容                                       | 何时执行                       |
| ---------- | ------------------------------------ | ---------------------------------------------------- | ------------------------------ |
| 结构迁移   | `pnpm db:migrate:runtime`            | 仓库中已提交的增量 SQL；迁移记录由 Drizzle 保存      | 首次部署及每次发布             |
| 正式初始化 | `pnpm db:bootstrap`                  | 缺失的初始管理员、默认字典、行政区划、销售大区及映射 | 首次部署一次；排障时可安全重跑 |
| 开发造数   | `pnpm db:seed` / `pnpm db:seed:demo` | 固定测试账号、默认配置和演示业务数据                 | 仅本地与测试环境               |

API 的 `start:prod`、容器启动和进程重启均不得自动调用上述命令。当前 API 启动入口没有自动迁移或 seed；生产环境下开发 seed 还会主动拒绝执行。

## 2. 首次建立云端数据库

### 2.1 先在数据库平台建立空库

迁移脚本必须先连接到一个已经存在的数据库，因此不能由 `db:migrate` 创建数据库本身。优先通过云数据库控制台完成：

1. 创建 PostgreSQL 16 或更高版本实例。
2. 创建名为 `litecrm` 的数据库。
3. 创建专用应用账号并授予该库的建表、改表和读写权限。小规模首次部署可以让该账号成为数据库 owner；以后如需强化安全，再拆分 migration 与 runtime 账号。
4. 确认可启用 `pg_trgm` 扩展。首份迁移会执行 `CREATE EXTENSION IF NOT EXISTS pg_trgm`；若云厂商限制普通账号创建扩展，应先由平台管理员在 `litecrm` 库中启用。

数据库真实密码只放在云平台 Secret／环境变量中，不写进 `.env.example`、部署脚本、GitHub Actions 明文或文档。若密码包含 `@`、`:`、`/`、`?`、`#`、`%` 等字符，拼入连接 URL 前必须进行 URL 编码；优先直接使用云厂商提供的完整连接串。

### 2.2 配置生产环境变量

部署平台至少需要以下 Secret：

```dotenv
NODE_ENV=production
DATABASE_URL=postgresql://<user>:<encoded-password>@<host>:5432/litecrm?sslmode=require
JWT_SECRET=<独立生成的高强度随机值>
BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_PASSWORD=<首次管理员随机密码，至少12位>
BOOTSTRAP_ADMIN_DISPLAY_NAME=系统管理员
BOOTSTRAP_ADMIN_JOB_TITLE=系统管理员
```

不要复用数据库密码作为 `JWT_SECRET` 或管理员密码。首次登录并完成正式账号配置后，可以从部署平台移除 `BOOTSTRAP_ADMIN_PASSWORD`；重复运行 bootstrap 时，已存在的管理员不会被改密。

## 3. 首次发布顺序

在与正式应用使用同一份 `DATABASE_URL` 的发布环境中按顺序执行：

```bash
pnpm install --frozen-lockfile
pnpm build
pnpm db:migrate:runtime
pnpm db:bootstrap
pnpm --filter @crm/api start:prod
```

完成后按以下业务顺序准备系统：

1. 使用首次管理员登录。
2. 在用户管理中建立真实人员账号，配置职位、系统角色、汇报关系和所属销售大区；不要把开发账号 `manager`、`sales1` 等带入正式库。
3. 检查并按公司口径调整字典和销售大区配置。
4. 下载客户导入模板，先用少量数据预览和查重，确认归属、客户关系和字段映射后再执行全量导入。
5. 导入后抽查客户数量、归属、分级、联系人、历史成交标记及重复候选。

正式环境绝不运行 `db:seed` 或 `db:seed:demo`。

## 4. 后续代码发布

每次发布执行以下顺序：

1. 备份数据库并确认备份可恢复。
2. 部署新代码与已提交迁移文件。
3. 执行 `pnpm db:migrate:runtime`。
4. 迁移成功后启动或滚动重启 API、桌面端和移动端。
5. 做登录、客户查询、商机跟进和周视图等关键冒烟验证。

Drizzle 会记录已经执行的迁移。没有新增迁移时，`db:migrate:runtime` 是空操作；已有迁移不会因为重启再次执行。功能更新若不改变数据库结构，不需要额外处理业务数据。

`db:bootstrap` 不属于日常发布步骤。它虽然可重复执行，但只会补缺，不会：

- 重置已有管理员密码、角色、职位或启用状态；
- 覆盖用户已修改的字典名称、排序和启停状态；
- 覆盖既有行政区划、销售大区和映射；
- 创建、删除或更新客户、联系人、商机、报价、计划、费用等业务数据。

## 5. 迁移安全约束

- 所有结构变化必须形成新的、提交进 Git 的增量迁移；禁止在正式库使用 schema push 或手工同步代替迁移历史。
- 禁止修改已经在正式环境执行过的迁移文件。需要修正时新增下一份迁移。
- 删除字段、改类型、大批量回填和新增唯一约束属于高风险迁移，必须先在正式库备份的副本上验证。
- 应用代码与迁移存在兼容窗口时，采用“先扩展、后切换、再清理”的方式，不在一次发布中直接删除旧字段。
- 数据库账号、连接串和备份不得提交 Git；仓库只保留变量名和无效示例值。

## 6. 回滚边界

代码可以回滚到上一版本，但数据库不能默认依靠反向 SQL 回滚。发生故障时优先：

1. 停止继续发布和写入风险操作；
2. 判断旧代码能否兼容新结构；
3. 能兼容则回滚代码，数据库保留向前兼容结构；
4. 不能兼容且数据已受影响时，按经过验证的恢复方案使用备份恢复。

因此，备份和迁移演练不是附加动作，而是正式发布的一部分。
