# Lite CRM 产品需求明细（PRD）

> **文档定位**：产品需求明细——回答"做什么、用起来顺不顺"。与[架构决策与实施蓝图](./重构架构决策与实施蓝图.md)（技术规格：怎么做、语义对不对）互补。
> **职责边界**：蓝图管语义与架构约束（数据/权限/流程规则）；**PRD 管页面清单、交互、反馈、验收标准**。
> **用途**：打磨的逐条依据——拿着 PRD 逐模块打勾，缺哪补哪；也是 M0–M5 模型收口和后续真机验收的检查单。
> **历史启动边界**：[M0-M5 冻结版 PRD](../99-历史归档/CRM立项PRD-M0-M5冻结版-V0.1.md) 仅用于追溯最初范围；当前业务规则和页面行为以本文为准。

**设计基线**：围绕客户、业务事实、未来行动、商机报价与明确成交建立可执行、可追溯、可验收的销售管理闭环。

## 0. 文档约定

### 0.1 功能点字段模板

每个功能点按以下字段描述（无内容项默认省略）：

| 字段 | 说明                      |
| ---- | ------------------------- |
| 入口 | 从哪里进入                |
| 操作 | 用户操作步骤              |
| 校验 | 输入/状态约束             |
| 权限 | 能力点要求（无则"登录"）  |
| 边界 | 异常/临界情况处理         |
| 反馈 | UI 反馈（成功/失败/确认） |
| 验收 | 可验证的标准              |

### 0.2 通用交互规范（全局强制，所有页面遵守）

| 规范             | 要求                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| **三态统一**     | 加载中（loading/骨架屏）、空态（el-empty/van-empty + 文案）、错误态（提示 + 重试按钮）走共享组件，禁止各页手写 |
| **操作反馈**     | 写操作成功 → 全局消息（ElMessage/Toast）；失败 → 错误信息展示                                                  |
| **危险操作确认** | 删除/停用/作废/释放 → 确认弹窗，必须说明后果                                                                   |
| **提交链路**     | 提交按钮 loading + 防重复提交；成功后 `reload()`/`setData()` 刷新，**不整页刷新**（红线 11）                   |
| **权限 UI**      | 无能力点的入口/按钮不渲染（`hasAbility`），与路由守卫同源                                                      |
| **表单校验**     | 内联提示 + 提交拦截；必填项标 `*`                                                                              |
| **登录态**       | access 过期 401 → 统一跳登录，记录来源页，登录后回跳                                                           |

## 2. 身份与登录

### 2.1 登录页（web / mobile）

- **入口**：未登录访问任意页 → 重定向 `/login`
- **操作**：账号 + 密码 → 登录按钮
- **校验**：两项必填（非空）
- **边界**：防爆破（后端连续 5 次锁 15 分钟）；密码错误提示不区分"账号不存在/密码错"（防枚举）
- **反馈**：错误 → "账号或密码错误"；锁定 → "尝试次数过多，已锁定 15 分钟"；成功 → 跳落地页（web 客户列表 / mobile 客户 Tab）
- **验收**：正确登录进落地页；错误 5 次出现锁定提示；刷新后会话保持（refresh 静默续期，后置）

### 2.2 修改密码（本人）

- **入口**：我的 / 用户菜单 → 修改密码
- **操作**：旧密码 + 新密码（≥8 位）+ 确认
- **反馈**：成功 → 提示"密码已修改，请重新登录"，清 token 跳登录
- **验收**：改密后旧会话全部失效

## 3. 用户管理（admin · `user.manage`）

> 设计要求：用户管理必须覆盖列表检索、新增、编辑、停用/启用和重置密码，不能只提供账号创建能力。

### 3.1 用户列表

- **入口**：侧边栏 → 用户管理
- **内容**：列 = 用户名 / 显示名 / 角色 / 上级 / 区域 / 状态 / 最近登录
- **操作**：搜索（用户名/显示名）、筛选（角色/状态）、分页
- **反馈**：加载中、空态（"暂无用户"）、错误态+重试
- **验收**：admin 可见该菜单；非 admin（如 executive）不可见

### 3.2 新建用户

- **入口**：列表 → "新建用户"按钮
- **字段**：用户名（唯一）、显示名、角色、上级（按组织树可选）、手机、区域、初始密码（≥8 位）
- **校验**：用户名查重（冲突提示"用户名已存在"）
- **反馈**：成功 → toast + 返回列表并刷新；失败 → 提示原因
- **验收**：创建后列表可见；重复用户名被拦截

### 3.3 编辑用户

- **入口**：列表行 → "编辑"按钮（或详情操作）
- **可改**：显示名 / 角色 / 上级 / 手机 / 区域 / 状态
- **反馈**：成功 → toast + 列表刷新；改角色后该用户重新登录权限生效
- **验收**：改角色后该用户登录可见菜单/能力随之变化

### 3.4 停用 / 启用

- **操作**：行 → 停用 → 确认弹窗（说明"该用户将无法登录，当前会话立即失效"）→ 确认；停用后同一入口变为"启用"
- **反馈**：成功 → toast + 状态列更新
- **验收**：停用后该用户旧 token 失效（登录被拒）；启用后恢复

### 3.5 重置密码

- **入口**：行 → 重置密码 → 确认
- **反馈**：弹窗展示临时密码（仅此一次），提示"请线下告知，建议首次登录后修改"
- **边界**：重置后该用户全端失效（token_version+1）
- **验收**：临时密码可登录；旧密码/旧 token 均失效

## 4. 客户管理

### 4.1 客户列表（web 完整 / mobile 精简）

- **入口**：web 侧边栏·客户 / mobile Tabbar·客户
- **web 列**：客户（名称+销售大区/城市+状态）/ 业务画像（客户行业+具体领域）/ 客户等级 / 有效商机（阶段+数量+预计金额）/ 最近活动 / 下一步行动 / 负责人（销售本人视角可隐藏）
- **操作**：搜索（名称/城市，防抖 300ms，五级排序）、筛选（等级/状态）、分页；移动端每页 20 条无限滚动并支持下拉刷新、失败重试
- **权限**：登录可见列表；`customer.write` 才显示"新建客户"
- **边界**：查重/搜索可命中权限外客户，但只显示最小标识（名称+城市），点击详情走权限（§7.3）
- **反馈**：三态统一；行点击进详情
- **最近活动口径**：取拜访、商机创建/跟进/报价/结案、客诉登记/跟进、明确成交等已发生事实的最大业务时间；未来行动的计划时间不计入最近活动
- **验收**：五级检索排序正确；权限外客户只显最小标识；新增任一客户活动后列表“最近活动”同步更新；有效商机与下一步行动从业务事实和计划源投影，不在客户表复制维护；移动端请求失败不能被误判为“没有更多”，刷新与并发搜索不产生重复行

### 4.2 新建客户（走查重管道）

- **入口**：列表 → "新建客户"
- **字段**：名称（必填，可地址式）、联系人电话（**至少一个，可无名**）、省/地级市（标准行政区划联动）、地址（软建议）、客户行业/具体领域/类型/来源/产品线（字典）、客户等级 S/A/B/C、负责人（销售/经理录入时默认本人，代录时从在职销售或经理中选择）
- **业务画像语义**：客户行业与具体领域是两个正交维度，不是一级/二级父子分类。例如“客户行业=电镀、具体领域=五金”表达“五金电镀客户”；两者独立配置、独立校验
- **区域语义**：行政区划保存稳定编码和名称快照；销售大区由行政区映射自动解析，不允许录入人员重复手填。城市级映射优先于省级映射，未命中映射时允许销售大区为空
- **查重流程**（§8.2 五步管道）：
  1. 硬拦截：ERP 客户编码/统一社会信用代码重复 → 409"已存在"，禁止继续
  2. 疑似提示：归一化名称、电话、地址等高置信命中 → 醒目提示 + "查看/申请接管"；中低置信降级提示
  3. 名称相同不直接判定为同一法定主体；用户明确确认后可继续新建，确认动作与理由留审计
- **边界**：口语名+无地址无电话 → 软提示"信息不完整，可能无法识别重复"（不拦截）
- **反馈**：成功 → 跳详情页
- **验收**：权威标识硬拦截不可绕过；仅名称归一化相同仍可在确认后建档；查重命中权限外客户可申请接管

### 4.3 客户详情

- **页面目标**：进入客户后先回答“现在要推进什么、每个开放商机走到哪里、最近发生了什么”，再提供档案查阅和治理操作；不得把详情页做成若干无优先级的资料卡堆叠
- **桌面布局**：头部放客户名称、状态/等级和高频业务操作；主栏依次为“商机进展 → 客户活动时间线”，侧栏依次为“经营概览 → 联系人 → 客户档案”。主栏宽于侧栏，档案信息不得挤占业务进展的首屏位置
- **商机进展**：每个商机使用可点击的进展卡，而非只列名称/金额的普通表格；卡片展示后端按真实事实投影的最近 3—5 个节点（需求发现、实际发生的每次推进与报价、终态），下一步计划作为未来事项独立呈现，不使用固定四格假流程
- **活动时间线**：拜访、商机建立/跟进、报价、客诉、成交按业务时间倒序聚合；历史事实只读，点击可回到来源商机或客诉，不另造“客户动态”事实表
- **移动布局**：保持同一信息优先级，按“快速登记 → 商机进展 → 活动时间线 → 经营结果 → 客户档案”纵向排列，不因屏幕变窄退化为资料字段优先
- **操作区**（按状态和能力点显隐）：在案客户可记拜访/建商机/登客诉/编辑/移交/放入公海；区域负责人和管理员可标记无效、恢复无效客户；公海客户可认领
- **权限**：`customer.write` 才能操作；只读角色（assistant）仅查看
- **验收**：首屏能看出开放商机各自所处节点和下一步；无权限操作不渲染；无商机/活动时有明确空态；时间线可追溯来源；桌面和移动的信息优先级一致

### 4.4 编辑客户

- **入口**：详情 → 编辑
- **可改**：名称 / ERP 客户编码 / 统一社会信用代码 / 省市地址 / 网址 / 字典字段（客户行业/具体领域/类型/来源/产品线）/ 客户等级 / 备注
- **等级规则**：等级变化必须填写原因，写入等级变更历史，并在同一事务校验新等级名额
- **校验**：名称改动较大时建议复走查重（后置可选）
- **反馈**：成功 → toast + 详情刷新
- **验收**：编辑后详情与列表同步更新

### 4.5 联系人管理

- **操作**：详情 → 联系人 → 添加/编辑/删除
- **字段**：姓名（可空=裸电话）、职务（客户原始称谓，自由文本）、岗位类别（字典 `contact_function`，可空）、电话（脱敏展示 138\*\*\*\*1234）、是否首要联系人（每客户至多 1 个）
- **岗位语义**：职务保留“动力设备科副科长”等真实称谓；岗位类别用于按企业负责人、采购／商务、技术／工艺、设备／工程、生产／使用、环保／安环、财务和其他进行统一检索与统计。首要联系人只表示日常主要联络对象，不等于商机决策人
- **校验**：每客户至少一个联系人电话（记录级约束，应用层校验）；岗位类别必须引用启用中的字典项；删除联系人或清空电话不得破坏电话约束；将某人设为首要联系人时自动取消原首要联系人
- **验收**：自由文本职务与标准岗位类别可同时保存和展示；脱敏规则正确；首要联系人唯一；最后一个有效电话不可删除

### 4.6 归属治理（所有权）

| 操作         | 入口            | 规则                                                                                                            | 反馈                        |
| ------------ | --------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------- |
| **移交**     | 详情 → 移交     | owner 本人/管理链/admin；目标必须是在职销售或经理，并校验对应客户等级名额；同事务交接                           | 确认弹窗 → 成功 toast       |
| **接管申请** | 详情 → 申请接管 | 非 owner 可发起；已有 pending 不可重复                                                                          | 成功 toast → 接管审批列表   |
| **放入公海** | 详情 → 客户状态 | owner 本人/管理链/admin；开放商机或未解决客诉时入口禁用并就地说明原因，后端继续拦截兜底；普通待拜访计划自动取消 | 确认弹窗（说明后果）→ toast |
| **标记无效** | 详情 → 客户状态 | 区域负责人/admin；开放商机或未解决客诉时入口禁用并就地说明原因，后端继续拦截兜底；原因必填                      | 转入无效档案                |
| **认领**     | 公海列表 → 认领 | 状态 public；销售区域与客户区域匹配；对应客户等级名额校验；不强制同时创建首次行动计划                           | 成功 toast → 进自己名下     |
| **恢复**     | 无效档案 → 恢复 | 区域负责人/admin；重新指定本区域在职负责人、填写恢复原因并校验客户等级名额                                      | 状态恢复为在案              |

- **状态语义**：active=在案且必须有负责人；public=有效但暂无负责人；invalid=停止经营的只读档案。public/invalid 的 owner 必须为空，状态不能在普通编辑表单中直接修改
- **池与档案可见性**：销售可检索本销售区域公海；区域负责人可查看本区域公海与无效档案；管理员可查看全公司；跨范围查重仍返回“已有档案及其状态”，但不开放完整客户历史
- **经营约束**：只有 active 客户可以新增拜访、商机、客诉和业务计划；public 必须先认领，invalid 必须先恢复
- **释放联动**：历史事实不改写；普通 pending 拜访计划自动变为 cancelled，取消原因由系统写为“客户已放入公海/客户已标记无效”，不要求用户重复填写；开放商机和未解决客诉必须先结案或移交
- **验收**：开放商机/未解决客诉均能阻止释放；接管走审批流；公海和无效档案按角色及销售区域可见；状态与 owner 组合不会产生矛盾

### 4.7 客户分级与分级名额

- **客户等级**：S/A/B/C 只表示客户价值与经营优先级；客户表保存当前等级，调整等级必须填写原因并形成变更历史
- **名额口径**：按“负责人 × 客户等级”统计 active 客户；支持公司默认名额和个人覆盖，不设置同名的“销售 S/A/B/C 等级”
- **触发校验**：建档指定负责人、移交、认领、接管批准和客户改级时，在同一事务内检查对应等级剩余名额
- **产品边界**：产品分级不复用客户等级或产品线字典；后续新增产品主数据和 Open 5000 产品编码映射
- **验收**：不同客户等级分别占用名额；并发操作不能突破上限；改级历史可追溯

### 4.8 客户经营阶段与冷启动导入

- **经营阶段**：系统派生“潜在客户 / 本年新客 / 存量客户”，销售不得直接维护“新老客户”标签。CRM 启用前已成交为存量客户；没有任何成交为潜在客户；CRM 内首次成交发生在当前自然年为本年新客，进入后续年份后自动成为存量客户
- **冷启动事实**：导入时允许标记“CRM 启用前已成交”，并可选填 CRM 前累计成交金额；未知金额保存为 `null`，不得以 0 冒充未知。该轻量事实只用于客户经营阶段和历史经营概览，不伪造订单、商机、报价或成交明细
- **Excel 工作台**：桌面端采用“下载模板 → 上传解析 → 字段映射与批次默认值 → 查重预览 → 确认导入 → 下载错误行”的闭环。下载模板第 1 行为填写说明、第 2 行为字段名称、第 3 行起填写客户数据；上传端自动定位前 10 行内的字段名称行，并兼容第 1 行直接为表头的旧文件。支持批次默认导入为存量成交客户、潜在客户或逐行指定，支持指定负责人或进入公海
- **最低资料**：导入允许只有满足建档要求的基础客户字段且暂缺联系人；日常手工建档仍执行联系人电话约束。ERP 客户编码、统一社会信用代码存在时继续硬查重，缺失时走名称、电话、地址疑似识别
- **审计**：导入批次保存文件摘要、映射、默认值、操作者、成功/疑似/失败数量；每行保存处理结果。导入成功的客户继续进入正常归属、分级和状态治理
- **验收**：导入存量客户不依赖虚构成交过程即可被识别为存量；历史金额与 CRM 内成交金额分开展示；重复和错误数据在确认前可见，提交后可追溯

## 5. 拜访登记（P0 主场景）

### 5.1 拜访表单（mobile 主场景 / web 同构）

- **入口**：客户详情"记一笔拜访" / 移动"记一笔"Tab / 销售日志快捷入口
- **字段**：客户（必填，选择器+内联建档）、拜访日期（默认今天，可改，精确到天）、方式（线下拜访/远程/其他）、类型（新客户/存量维护/行业关系）、生意情况 / 设备使用 / 人员变动、下次拜访日期与内容（必填）
- **校验**：`customerId/occurredAt/method/nextActionAt/nextActionContent` 必填；拜访结束不能只勾“完成”而没有下一次安排
- **联动**：是否执行计划由入口决定。从计划进入时带入只读计划上下文和 `sourcePlanId`，保存时同事务写入拜访事实、完成来源计划并创建下一条客户拜访计划；从“记录实际”直接进入时不携带 `sourcePlanId`，因此不会把已有计划算作已执行
- **直接登记续接**：若已有 pending 拜访计划，表单将其日期和内容预填为下次安排；用户未改动则沿用原计划，改动则保持同一计划 ID 和 pending 状态，原地更新下一安排并追加前后日期、内容、原因和操作人历史。表单不让用户选择“执行/保留”，也不生成一条 cancelled“旧计划”
- **边界**：内联建档（选不到 → 表单内快速建客户，走查重管道，一个流程不跳出）
- **反馈**：成功 → toast + 返回并刷新时间线/列表
- **验收**：拜访记录只保存已经发生的事实；一名客户最多一条 pending 拜访计划；来源计划只能被一个实际拜访完成；下次拜访只在计划表维护一次并进入周视图

## 6. 商机闭环

### 6.1 商机列表（web）

- **列**：客户 / 商机名称 / 阶段 / 当前参考金额（明确标注预估、口头报价或正式报价来源）/ 最近报价 / 最近跟进 / 当前行动（逾期标红）/ 负责人
- **操作**：搜索（客户/名称）、筛选（阶段/金额区间/是否报过价/是否无下一步）、分页
- **负责人口径**：显示客户当前负责人；商机 `ownerId` 只保留创建时责任快照，客户移交后列表和详情按客户当前归属自动变化
- **查询上下文**：列表接口一次返回最近报价、最近跟进、当前 pending 行动、当前负责人及风险标记；页面不逐行补请求
- **停滞**：只对开放商机实时派生，不保存第二份状态。当前行动逾期、无 pending 行动、最后一次业务活动（创建/跟进/报价取最大值）超过 30 天、预计成交日已过，分别形成独立标记
- **展示语义**：阶段、报价类型和报价状态属于固定状态机，前端统一转换为中文；来源和产品线从字典解析展示名称
- **验收**：超过当前周的历史逾期行动仍可见；能筛出“报过价但长期无动作”的商机

### 6.2 新建商机

- **入口**：客户详情"新建商机" / 商机列表"新建" / 周视图日 card 与移动快速记录的"新建商机"；快速入口先选择客户，再复用同一商机表单
- **字段**：客户（必填）、名称、来源（字典）、产品线（0..N，多选关系）、初始金额依据（预估金额/口头报价/正式报价单）及金额、需求发现日、预计成交日、第一步行动（内容+日期，必填）；报价依据时补充报价日期，正式报价可选单号与文件引用
- **一致性**：所有入口复用同一创建命令与同一校验；从客户或快速入口进入时锁定客户，从商机列表进入时可检索本人数据范围内的客户；从某日 card 进入时该日期只预填为需求发现日，第一步行动时间仍须独立明确安排
- **反馈**：成功 → 跳详情
- **事务与验收**：商机、产品线关系、可选的首条报价事实和第一步行动在同一事务完成。预估依据只写预测金额；口头/正式报价依据同时追加首条 `opportunity_quotes`，商机直接进入跟进中，但不会成交

### 6.3 商机跟进

- **内容**：基本信息、当前行动和完整商机活动 Timeline；Timeline 从需求发现、推进、报价、成交/丢失/需求消失事实统一投影，报价历史仍可独立查看明细
- **统一入口**：销售日常主操作统一称为“记录商机推进”，不再让“记录跟进”和“记录报价”成为互斥的平级入口；报价是本次推进可能产生的业务结果
- **字段**：本次推进日期、沟通方式（电话/现场/线上等）、推进结论、是否产生报价、下次跟进日期与内容；产生报价时展开报价类型、金额、正式报价单号、文件引用和说明
- **操作**：入口决定执行语义：从计划进入则完成来源计划，直接登记则只追加事实、不完成现有计划；两种入口都必须明确下一计划。直接登记时现有 pending 计划作为下次安排预填，未改动则沿用，改动则保持同一计划 ID 原地调整并留痕。只有转订单/丢单/需求消失等终态命令可以不安排下一次
- **事务**：一次提交始终新增一条推进事实；若本次产生报价，则在同一事务追加报价事实、自动替代上一有效报价，并通过 `followUpId` 关联本次推进；来源计划只完成一次，下一计划只创建或沿用一次
- **状态机**：首次跟进后 `intent → following`；跟进本身不等于报价或成交
- **验收**：每次推进追加历史，不覆盖上一结论；一次推进可无报价或产生一条新报价；同一来源计划只对应一次推进事实；开放商机始终最多一条且必须有一条 pending 跟进计划

### 6.4 口头报价与正式报价单

- **关系**：一个商机下允许口头报价 0..N 次、正式报价单 0..N 次
- **主路径**：销售在“记录商机推进”中勾选本次发生报价并填写报价字段；报价历史区域可保留弱化的“补录报价”入口，用于确有报价事实但没有同步客户沟通的异常补录，不进入移动端快速填报主菜单
- **字段**：类型（口头/正式）、报价日期、金额、登记人；正式报价可选报价单号和文件引用；由推进产生的报价关联 `followUpId`
- **重新报价**：商业上的改价必须新增报价记录；新报价自动替代该商机当前有效报价，旧记录转为 `superseded`，同一商机任一时刻最多一条有效报价
- **版本语义**：口头报价后出正式报价单、正式报价单再次改价，均追加新报价；系统通过 `supersedesQuoteId` 自动指向上一有效版本，用户不选择替代对象，也不维护并行有效方案
- **边界**：CRM 本阶段不负责制作报价单，也不强制上传文件；登记报价不会自动生成 Deal
- **验收**：可以看到完整报价次数、最近报价日期和金额；口头/正式报价均不改变成交状态；报价完成后必有明确的客户反馈行动

### 6.5 明确下单与结案

- **双端能力**：Web 与 Mobile 都必须能独立完成确认成交、丢单和需求消失；不允许因销售当时无电脑而延迟业务事实的发生时间
- **赢单操作**：客户明确下单后执行“确认成交”，填写成交日期与成交金额；系统自动关联当时的当前有效报价，无有效报价时允许成交但不建立报价关联
- **赢单结果**：商机进入 `won`，生成唯一 Deal，取消剩余未完成行动；并发重复确认返回冲突，不得生成两个 Deal
- **失败结案**：丢失/需求消失，原因必填，取消剩余未完成行动
- **后续边界**：Deal 是 CRM 的成交事实，不是 Open 5000 订单；订单、出货、应收和回款后续独立接入
- **验收**：报价金额不能触发成交；只有明确下单命令生成 Deal；结案原因必填

## 7. 客诉闭环

### 7.1 登记客诉

- **入口**：客户详情"登记客诉" / 客诉列表"新建"
- **字段**：客户（必填）、类型（字典 6 类）、问题描述（必填）、发生日期、第一步处理行动（必填）
- **联动**：登记 → 触发客户风险告警（异步）
- **验收**：登记成功；风险看板出现该客诉

### 7.2 客诉跟进与解决

- **桌面工作台**：客诉选择列表与所选客诉 Timeline 同屏，不以“列表页 → 详情页”形成额外导航层；旧详情 URL 重定向并定位对应客诉
- **分页**：列表由服务端分页，默认 20 条、最大 100 条，返回 `items/total/page/pageSize`；数据库全局排序为未解决逾期 → 未解决 → 已解决，不能前端只对当前页重排
- **列表边界**：只返回客户、描述、状态和当前行动摘要；仅所选客诉请求 Timeline，禁止列表携带所有历史节点
- **内容**：顶部仅保留客户、类型、状态和持续时间摘要；主体为倒序生命周期时间线，依次展示当前待办或解决结果、历次处理倒序、最初登记
- **时间线读模型**：后端从 `complaints + complaint_follow_ups + follow_up_actions` 组合类型化节点；Web 与 Mobile 使用同一节点序列，不在两端分别拼接排序
- **操作**：跟进（内容必填；FOLLOWED_UP → 下一步行动必填；RESOLVED → 解决结果必填并取消剩余行动）
- **边界**：resolved 为终态，**禁止任何跟进**（后端拦截 + 前端置灰）；未解决且关联行动逾期 → 风险视图
- **验收**：历史处理为实心事实节点，待办为空心/虚线节点，逾期标红，解决终点标绿；解决后跟进入口置灰/拦截；逾期客诉进风险看板

## 9. 销售计划周视图 / 管理看板 / 接管审批 / 字典配置

### 9.1 销售计划与周视图（web / mobile 同一闭环）

- **入口**：web 侧边栏·销售计划周视图 / mobile 本周计划
- **内容**：周定位以明确的周一日期为事实源并写入 URL。桌面端使用相邻周箭头、周选择器和离开当前周后才出现的“回到本周”；移动端使用“‹ 相对周名 + 日期范围 ›”，点击范围打开月历，月历内可回今天，不在主界面常驻复位按钮。移动端主体采用“七日摘要条 + 选中日详情 + 周概览”，默认只展开一天，切相邻周时保持所选星期。单日详情分为待执行、业务记录和客诉，已执行计划置灰保留；双端统一汇总所有早于今天且仍为 pending 的计划，本周已经过去的待办也不得漏出逾期区
- **计划类型**：只允许客户拜访 `customer_visit`、商机跟进 `opportunity_follow_up`、客诉跟进 `complaint_follow_up`。`planKind` 表示将执行什么业务，`originType/sourceId` 只表示它由哪次历史事实产生，两者不得混用
- **手工安排**：用户可在某日直接安排客户拜访或开放商机跟进，必须选择客户及对应业务对象；不提供“整理资料”等与销售闭环无关的普通任务
- **计划待办**：pending 计划整张卡片可点击，直接进入对应领域执行表单；改期属于次级操作。表单顶部只读展示“本次执行计划”，不再询问是否关联原计划
- **计划外记录**：用户可从今天或历史日 card 的统一入口新建商机，或直接记录该日拜访、商机推进和新客诉；未来日期不提供实际记录入口。直接记录永不携带 `sourcePlanId`，不会把现有计划算作已执行；若下一安排未变化则沿用现有 pending 计划，变化则保持同一计划 ID 原地调整日期和内容并留痕，不能制造第二条 pending 计划或虚假的取消记录
- **移动端计划优先**：直接点击底部“记录”时，发生日期默认今天并优先展示全部逾期及今日待办；从周视图“记录当日实际”进入时明确带入所选的今天或历史日期并显示补录上下文。发生日期可修改但不得晚于今天，不显示昨天／今天／明天三态切换。点击具体计划始终直接进入执行表单，计划日期只作上下文，实际日期默认今天；选择客户或商机后若发现匹配计划，突出“按此计划填报”并保留弱化的“记录计划外实际”，不得自动完成计划
- **执行**：提交实际拜访、商机推进或客诉处理后，才由同一事务把具体来源计划置为 completed 并创建下一计划。计划执行关系只来自用户点击具体计划；周视图不存在脱离业务事实的“直接完成”
- **事实只读**：已发生 item 点击后进入类型化只读事实详情，只展示本次实际内容和来源计划；不得打开填报表单，也不得把“查看事实”跳转成可继续处理的客户/商机/客诉详情。所属业务对象仅作为独立链接查看
- **留存**：计划按 `plannedAt` 留在原日期；双端 completed/cancelled 默认折叠进“已结束计划”，拜访/跟进/报价/客诉按 `occurredAt`、商机发现按 `discoveredDate` 进入“已发生”，并标明“来自计划 / 直接记录”。计划与执行事实通过 `sourcePlanId` 精确关联，计划完成后不丢失历史
- **调整**：主动改期只改变日期，必须填写原因，目标日期只能是今天或未来；计划外事实带来的下一安排修订可同时调整日期和内容。两者都保持计划 ID 与 pending 状态，并追加前后值、原因、操作人与操作时间的不可变历史；实际执行内容仍通过业务事实与原计划对照，不提供“替换计划”和裸取消
- **终止**：只有客户释放/无效、商机成交/丢失/需求消失、客诉解决等领域命令可以取消剩余计划；延期必须给出新的明确日期
- **唯一性**：每个客户最多一条 pending 客户拜访计划；每个开放商机、未解决客诉各最多一条 pending 跟进计划
- **周摘要**：每人每业务周可维护一份目标/复盘文字；行动明细不复制进 weekly plan
- **指导意见**：管理者 → 被指导者（红点已读闭环）；author 须为被指导者上级
- **验收**：计划 → 实际事实 → 下一计划可完整追溯；完成计划在原日期置灰且实际记录在发生日期可见；所有已发生 item 只读；移动端高频入口优先暴露匹配待办；不能重复安排同一业务；不能无事实直接完成或裸取消；每次改期均可查看改期前后日期、原因与操作人；当前周仍能看到更早逾期；各入口显示同一条计划

### 9.2 接管审批（`approve.claim`）

- **入口**：web 侧边栏·接管审批
- **内容**：pending 申请列表（客户/申请人/原因/时间）；审批操作（通过/拒绝，拒绝必填意见）
- **规则**：单点审批（候选池任一批准即生效）；禁止自我审批；同客户仅一条 pending
- **反馈**：审批后通知申请人；结果在列表状态更新
- **验收**：通过后客户归属变更；拒绝留意见；并发重复审批被拦

### 9.3 字典配置（`user.manage`）

- **入口**：web 侧边栏·字典配置（admin）
- **维度清单（9 类，§7.2 customer_dimension_options）**：industry 客户行业 / sub_industry 具体领域（与客户行业正交）/ customer_type 客户类型 / product_line 产品线 / source 客户来源 / complaint_type 客诉类型 / trade_type 交易性质 / opportunity_source 商机渠道 / visit_type 拜访类型
- **列表**：维度下拉切换（切换即按维度过滤）+ 选项表格（显示名称/稳定字典值/排序/状态）+ 三态（加载/空/错误）
- **新增**：当前维度下同时填写显示名称和稳定字典值；稳定值采用可长期引用的英文标识，并在维度内唯一
- **编辑**：允许修改显示名称、排序号；已有项的稳定字典值在界面中只读，避免破坏历史引用
- **启停**：停用后不再出现在新增/编辑表单下拉中；历史记录仍以稳定值关联并显示该项名称
- **校验**：维度内稳定字典值唯一（冲突提示）；业务写入只接受存在且启用的稳定值
- **验收**：配置页同时可读地展示中文名称与稳定值；切换维度正确过滤；名称修改后各业务页面同步显示；停用项不可新选但历史可读

> 设计要求：每个业务维度独立查询和维护自己的选项，切换维度不得混入其他维度数据；业务数据保存稳定值，界面统一通过字典的 `label` 展示，不在页面内另写一套分类映射。

### 9.4 管理看板（web · `dashboard.view`）

- **定位**：同时承担经营结果与过程管理；先回答“当前销售储备是否可信、期间转化了多少、团队正在做什么、哪些重点客户需要介入、费用发生在哪里”，不复制业务状态，也不替代 ERP/财务结果。
- **导航**：管理者登录桌面端默认进入管理概览；内部使用“管理概览 / 商机经营 / 团队动态 / 重点客户 / 团队费用”五个页签。概览只呈现关键数字和最高优先风险，所有内容必须能下钻到人员期间内容（选择“本周”时即周内容）、客户或商机。
- **统一筛选**：日期、组织树内人员、销售大区、产品线。日期只作用于期间推进、成交、团队活动和费用；当前商机池是截至今日的开放存量，不得随日期筛选伪装成“本周商机池”。人员作用于全部视图；销售大区和产品线只作用于客户/商机类指标，不应错误裁剪人员费用与实际活动。
- **业务日期**：拜访、推进、报价、下单、客诉、费用和计划等业务日统一使用 `YYYY-MM-DD`，数据库使用 `date`；当天不算逾期。`createdAt/updatedAt/approvedAt` 等系统审计时间继续使用带时区时间戳，不能把两类时间互相替代。

#### 商机经营与当前金额构成

- **当前存量**：开放商机按“仅预估 / 口头报价 / 正式报价”互斥分桶；每个商机仅计一次，优先采用最新 `active` 报价，没有有效报价才回退预估金额。被替代和撤回报价不计入当前池，历次报价不得累加制造虚高。
- **展示关系**：使用“当前开放商机池总额 + 细横向分段构成条 + 纵向三项图例”表达包含关系；图例逐行对齐名称、数量、金额和占比，不把总额与三个组成项做成四张平级卡片。顶部不显示没有业务分母的“总完成率”；本结构称为“当前参考金额构成”，不能把“仅预估”误称为报价类型。
- **风险子集**：停滞金额、行动逾期和无下一步属于当前商机池的交叉风险，不作为第四个金额构成分段；在构成条下独立展示并可下钻处置。
- **期间流量**：分别统计新增商机、首次报价、首次正式报价、确认成交、失败结案数量与金额；这些是期间发生事件，不得与期末存量混为同一漏斗分母。
- **结案赢单率**：`期间赢单数 ÷（期间赢单数 + 期间丢失/需求消失数）`；没有结案样本时显示“暂无可计算结案”，不得显示 0% 冒充结果。
- **人员拆分**：展示开放商机数、商机池总额、当前金额依据微型分段条、停滞金额和本期成交；构成条悬停可读三类金额，避免把总额、口头报价和正式报价误认为可相加的平级指标；点击人员下钻商机列表。
- **边界**：Deal 是 CRM 的明确成交事实，不等同 ERP 订单、出货、应收或回款；当前没有阶段概率和销售目标，不展示加权收入预测或目标完成率。

#### 个人商机摘要

- 普通销售不开放完整管理看板，但在桌面端“我的工作”和移动端“我的”看到轻量“我的开放商机”摘要：当前总额、开放数量、仅预估/口头/正式构成，以及停滞、行动逾期、无下一步数量。
- 个人摘要与管理看板复用同一聚合口径，但服务端强制按当前登录人裁剪，不能接受 `ownerId` 越权查询；销售管理员的个人摘要只看本人，管理看板继续看本人及递归下属。
- 桌面摘要可下钻到按本人筛选的现有商机列表；移动端首版保持只读，不为了一个摘要新增独立页面或底部 Tab。

#### 团队动态

- **第一层**：组织树内每人一张期间摘要 Card，展示实际拜访、商机跟进、报价、客诉记录、待执行、完成计划和逾期积压；实际业务记录优先于计划完成率。
- **第二层**：点击人员查看其按日展开的完整“待执行/已结束计划 + 已发生事实”；默认个人周视图只看本人，管理者必须明确选择组织树内人员，禁止把整个团队记录混在一张个人周视图中。
- **归属**：商机存量按客户当前负责人；拜访按 `visit_records.owner_id`、商机跟进/报价按实际 actor、客诉登记/处理按记录人员、费用按费用 owner。历史执行归属与当前客户责任不得混用。

#### S/A 重点客户

- 默认显示“需要关注”，并可切换“全部 S/A”。关注原因实时派生：未解决客诉、行动逾期、开放商机无下一步、商机 30 天无动作、预计成交日已过、客户 30 天无活动。
- 行内展示等级、当前负责人、销售大区、开放商机数/金额、最近活动和明确风险原因，点击进入客户详情。
- 首版不保存全局“重点关注”布尔字段；后续如需管理者主动收藏，应建立“管理者 × 客户”的个人关注关系。

#### 团队费用

- 按日期和人员汇总 `submitted` 费用，并按烟酒、礼品、餐叙、招待、住宿拆分；`draft` 只显示未提交条数，不进入金额，`voided` 剔除。
- 本视图不引入预算、报销审批或财务凭证，保持轻量统计边界。

- **验收**：改价只计最新有效报价；当前池三段金额相加等于总额；停滞只作为交叉风险，不混入构成；日期筛选不改变截至今日的当前池；客户移交后存量归新负责人但历史执行仍归原执行人；销售不可访问管理看板但可读本人摘要；管理者不可越组织树选人；概览数字与各详情页签一致；空数据、无结案样本和无风险均有明确状态。

## 10. 产品与模型验收基线

> 用法：先验证模型约束，再逐条验收页面。基础事实不可信时，不叠加管理看板或导入正式数据。

### 10.1 通用规范落地检查

- ☐ 所有列表页有**空态**（el-empty/van-empty + 文案）
- ☐ 所有请求有**错误态**（提示 + 重试），不白屏/静默失败
- ☐ 所有写操作有**成功/失败反馈**（全局消息）
- ☐ 所有**危险操作**（删除/停用/作废/释放/结案）有确认弹窗 + 后果说明
- ☐ 所有提交按钮有 loading + 防重复提交
- ☐ 所有无权限入口/按钮按 `hasAbility` 隐藏
- ☐ token 过期 401 → 统一跳登录

### 10.2 模型层阻断项（先于页面打磨）

- `normalized_key` 只用于相似候选和检索；客户编码、统一社会信用代码作为可空硬唯一键；名称疑似重复必须确认但不能误伤合法客户
- S/A/B/C 只表达客户等级；分级名额按“负责人 × 客户等级”约束，校验与占用必须处于同一事务
- `follow_up_actions` 是未来销售计划唯一事实源；`plan_kind` 决定执行入口，`source_type/source_id` 只追溯生成来源；周视图只做查询投影，不复制计划明细
- 拜访、商机推进、报价和客诉跟进分别保存实际事实；一次商机推进可通过 `follow_up_id` 关联本次可选报价。只有领域执行事实以唯一 `source_plan_id` 承接原计划，统一计划存储不等于统一实际业务模型
- 同一客户/开放商机/未解决客诉分别最多一条相应 pending 计划；完成必须由领域命令在写入实际事实的同一事务内发生
- 商机推进与报价均为追加事实；日常入口一次提交一条推进事实和至多一条关联报价，口头报价 0..N、正式报价 0..N，报价不能隐式改变成交状态
- 明确下单使用独立命令；一个商机最多生成一个 Deal，成交金额与估算、报价金额分离
- 可变聚合使用版本条件更新；拜访和各类跟进事实只追加，不允许覆盖历史
- `firstVisitedAt/firstDealAt/lastActivityAt` 等派生字段必须有明确投影与重算机制，否则不得用于管理口径

### 10.3 界面验收要求

- ☐ 用户管理具备编辑、停用/启用和重置密码，并对影响性操作二次确认
- ☐ 所有列表具备空态、错误态和重试入口
- ☐ 商机结案、客诉解决、客户释放等影响性操作说明后果并二次确认
- ☐ 移动端提交成功后返回来源页，来源列表或详情同步刷新
- ☐ 移动端“我的”提供七日摘要、选中日详情、周概览和费用管理；逾期待办独立可达
- ☐ 客户详情首屏先呈现商机进展和活动时间线，商机卡只展示真实发生节点与独立下一计划，不显示固定假流程；档案信息降到侧栏或后序
- ☐ 关键领域组件至少覆盖空态、核心展示和来源回链，不允许仅保留 M0 smoke 测试

### 10.4 产品验收完成定义

- 每个页面过一遍 0.2 通用规范 → 模块功能点 → 无红叉
- 双端主链路（登录 → 建客户 → 拜访 → 下一步行动 → 商机跟进 → 多次口头/正式报价 → 客户明确下单）走通且反馈完整
- 能演示“报价后一至两个月没有动作”的商机如何被识别、补行动或结案
- PRD 各章节"验收"项可演示验证
