# 交互设计打磨（UX · 功能如何呈现、UI 如何衔接）

> **定位**：与 PRD 互补——PRD 定"做什么、功能点"，本文定"**如何呈现、页面间如何衔接**"。
> **核心**：销售计划周视图是移动端主界面的设计主干；历史拜访/跟进是事实时间线，未来计划是唯一待办来源，两者不复制也不混成一个业务模型。
> 配套：[PRD](./PRD.md)（功能点/验收）、[技术打磨清单](./技术打磨清单.md)（实现健壮性）。
> **设计基线**：历史事实与未来计划分开展示；用户从计划进入对应业务执行，写入实际事实后系统完成原计划并生成下一计划。

## 1. 交互设计基线（跨模块通用）

### 1.1 页面分区（详情页按决策优先级）

```
PageHeader：对象名称 + 状态/等级 + 高频业务操作
  ├─ 当前工作区：开放商机进展 / 当前计划 / 首要待处理事项
  ├─ 历史活动区：拜访、跟进、报价、客诉、成交时间线
  └─ 支撑信息区：经营概览、联系人、基本档案与治理操作
```

**原则**：先回答“现在推进什么”，再回答“之前发生什么”，最后才是“这个对象有哪些资料”。主操作一眼可见；危险操作（释放/结案/作废）与主操作视觉分离。

### 1.2 操作组织

- **主操作**（主色）：新建、提交、认领
- **次要操作**（灰/描边）：编辑、移交、申请接管
- **危险操作**（红色/描边）：释放、结案、作废、停用 → 必须弹确认 + 说明后果
- 入口按能力点显隐（`hasAbility`），无权限不渲染

### 1.3 衔接原则

| 场景                         | 衔接方式                                                               |
| ---------------------------- | ---------------------------------------------------------------------- |
| 列表 → 详情                  | 行点击跳详情（web）；卡片点击（mobile）                                |
| 详情 → 填报表单              | **弹窗/抽屉（web）或 push 页面（mobile）**，完成后返回详情并刷新时间线 |
| 表单提交成功                 | toast + 返回来源页 + 目标页刷新（红线 11，不整页刷新）                 |
| 弹窗类操作（移交/接管/释放） | 弹窗内完成 → 关闭 → 详情局部刷新（`reload`），不跳走                   |
| 返回                         | mobile `router.back()`；web 详情页"返回列表"（保持查询上下文，后置）   |

### 1.4 双端一致性

- 重合功能（客户详情/表单）**结构对齐**：mobile 的"快速登记"组 ↔ web 的"业务操作区"必须同构（§5.4 schema 共享）；
- 差异只在形态（web 弹窗 vs mobile 整页 push），**功能入口一个不少**。

### 1.5 系统级视觉打磨

**当前优先级**：M0–M5 业务主链路和主要交互完成收口后，下一阶段先统一 UI 视觉基础，再逐页打磨。不能继续让各页面直接堆叠 Element Plus/Vant 默认组件，否则业务功能虽已可用，仍会呈现为层级弱、密度失衡、状态语义不统一的“毛坯后台”。视觉改造不改变已经确认的业务对象和命令边界。

**目标风格**：专业、克制、紧凑，体现工业设备销售的可靠、清晰和执行感，但不做成纯 CRUD 后台、大屏展示或泛化的 AI SaaS 渐变界面。视觉必须服务于“当前状态如何、哪里需要处理、下一步做什么”，不以颜色、图表、圆角或阴影数量衡量完成度。

#### 风格来源与取舍

| 参考来源             | 主要借鉴                                             | 不直接照搬                                     |
| -------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| Atlassian            | 应用外壳、导航分组、页头、状态反馈、空态与操作层级   | 产品品牌色和面向研发协作工具的术语             |
| IBM Carbon           | 高密度数据表、32/40/48px 密度档、边界与排版的系统性  | 过强的企业平台感和完整设计系统体量             |
| Salesforce           | 记录页“重点摘要—活动—详情—关联”的信息架构            | 颜色噪声、过多标签和大型产品累积出的视觉复杂度 |
| Linear               | 低噪声界面、上下文筛选、轻量侧栏和聚焦当前工作的方式 | 面向研发任务的极简字段量                       |
| Day One 等时间记录类 | 时间线的阅读节奏、事实内容与时间标记的主次           | 过于柔和、适合个人日记但不适合批量管理的密度   |
| USWDS                | 复杂表单的渐进披露、帮助文字、错误与无障碍反馈       | 政务网站的视觉外观                             |

上述来源是拆解后的设计证据，不选某一套产品整皮复制。CRM 记录页、经营列表、周计划和移动填报需要的密度不同，应共用视觉语义和组件规则，而不是共用完全相同的卡片排版。

#### 候选方向（用同内容静态 HTML 决策）

1. **工业运营蓝灰（推荐基线）**：深石墨导航、冷灰工作区、钢蓝主色、克制的琥珀风险色；低圆角、细边界、弱阴影、较高信息密度。最符合工业设备销售和过程管理，但要防止过于沉重。
2. **现代企业效率**：浅色应用外壳、偏蓝紫主色、较舒展间距和轻量卡片。学习成本低、最接近成熟 SaaS，但容易变成缺乏行业识别度的通用管理后台。
3. **温和关系经营**：暖灰底、低饱和青绿主色、强调客户活动时间线和阅读感。适合客户经营与拜访回顾，但在密集表格、经营分析和异常处置中可能显得松散。

正式改代码前，在 `02-参考资料/视觉风格方案/` 使用**完全相同的 CRM 内容与布局**制作三份无复杂交互的静态 HTML，只改变色彩、字体层级、边界、密度和组件外观。比较时先看客户列表、客户详情/活动时间线、周计划和移动端记录四类代表场景；选定方向后才沉淀设计令牌，避免一边改业务页一边反复换皮。

2026-08-30 已完成第一轮可视化样稿：`01-industrial-operations.html`、`02-modern-enterprise.html`、`03-warm-relationship.html`。三份样稿共用经营看板、重要客户时间线和移动端今日工作等真实业务内容，仅切换应用外壳、色彩语义、边界、圆角、阴影与信息密度；样稿用于方向决策，不代表最终页面布局或可直接合入生产代码。

第一轮体验反馈倾向第二套“现代企业效率”和第三套“温和关系经营”。据此新增 `04-modern-relationship-operations.html` 融合稿：以第二套的浅色应用外壳、间距与操作清晰度为骨架，采用第三套的低饱和青绿、温和记录感和琥珀重点色；管理分析区保持理性紧凑，客户时间线与移动记录区适度增加阅读温度。该融合方向暂命名为“现代关系运营”，用于下一轮方向确认。

2026-08-30 已确认采用“现代关系运营”作为正式视觉方向，并完成第一阶段代码落地：共享设计令牌统一为低饱和青绿主色、暖中性背景、琥珀关注色和克制的阴影/圆角体系；桌面端完成应用外壳、分组导航、页头、按钮、筛选、表格、标签、卡片、弹窗等 Element Plus 基础映射，并优先迁移经营看板、客户列表、客户详情/活动时间线和销售周视图；移动端完成 Vant 基础映射，并优先迁移今日工作、客户列表和快速记录。该阶段只调整信息层级、密度和视觉表达，不改变业务模型、权限或命令边界。其余页面先继承统一基础，再按实际试用反馈逐页消除局部旧样式。

#### 实施顺序

1. 确认风格方向与业务状态色，不先逐页修局部 CSS。
2. 建立颜色、字体、间距、圆角、阴影、密度和状态语义令牌，同时约束 Element Plus/Vant 主题变量。
3. 先改应用外壳、导航、页头、按钮、筛选条、表格、标签、弹窗、空态和错误态等公共组件。
4. 再按“客户经营 → 商机推进 → 我的工作/周计划 → 客诉与费用 → 管理看板”迁移业务页面；移动端独立按业务优先级重排，不机械缩小桌面端。
5. 每迁移一类页面同时检查状态语义、信息密度、响应式、键盘/触屏操作和写后反馈，旧样式不得长期与新样式并存。

集中打磨时必须统一处理：

1. **业务视觉语义**：建立客户等级、商机阶段、正常/待关注/需介入、待执行/已完成/已取消/已逾期的固定色彩与标记体系，同一语义不允许跨页变色。
2. **信息层级**：按“对象状态 → 当前重点/下一步 → 业务过程 → 基础资料”组织详情页；列表首先支持判断和处置，不平铺低价值字段。
3. **组件体系**：统一页头、筛选条、指标卡、业务卡、表格、时间线、状态标签、空态、错误态和确认弹窗，减少默认 Element Plus 组件拼装感。
4. **密度与响应式**：桌面端提高有效信息密度并保持主次；移动端按业务优先级重排，不机械压缩桌面表格。
5. **管理看板**：以经营问题和可下钻处置为中心，优先展示商机池健康度、需管理介入事项、团队异常和重点客户；不追求“大屏感”，不把可重复发生的报价类型伪装成线性漏斗阶段。

**验收标准**：任一核心页面都应让用户在首屏判断当前状态和首要操作；关键状态跨模块表达一致；常用桌面列表在 1440px 宽度下不出现无意义大片空白；移动端单手可触达主要动作；管理看板每个组件都能对应一个管理问题及后续下钻动作。

### 1.6 桌面端主导航

桌面端导航按工作意图分组，不把客户、商机、审批和系统配置平铺成同一层级：

| 分组       | 入口                                   | 认知目标                       |
| ---------- | -------------------------------------- | ------------------------------ |
| 工作台     | 我的工作                               | 计划、待办与每日记录的执行入口 |
| 客户与销售 | 客户经营、商机推进、客诉处理、费用记录 | 围绕业务对象持续经营和填报     |
| 管理协同   | 经营分析、客户接管                     | 查看团队经营并处理管理事项     |
| 系统设置   | 用户与组织、业务字典、分级名额         | 与日常销售明确隔离             |

- 导航名称使用“对象 + 工作意图”，并附一行稳定说明，避免用户只能看到抽象对象名；图形标识仅用于加快扫描，不能代替文字。
- 入口仍按服务端下发能力点显隐；无可见入口的分组整体不出现。`customer.write` 控制“我的工作”和“费用记录”，管理与系统入口分别由现有管理、审批和配置能力控制。
- 管理角色登录后进入经营分析；销售进入我的工作；无填报能力的只读角色进入客户经营。详情、导入等二级页面不进入主导航。
- 侧栏只承担跨业务场景导航，不在其中塞入新建客户、记录跟进等高频命令；这些动作继续放在对应工作台和对象上下文中。

## 2. 销售计划：周视图（核心界面）

> 心智：**业务日历**——日卡里放的是未来计划，不是“什么都能填”的通用任务。客户拜访、商机跟进、客诉跟进执行后分别形成自己的历史事实。
> 呼应蓝图：§8.7 销售计划唯一事实源、§8.4/8.5/8.6 各领域事实与下一计划联动。

### 2.1 定位

- **移动端主界面**：销售打开看“今天/本周要拜访谁、推进哪个商机、处理哪项客诉”；
- **桌面端“我的工作”页**：以销售计划周视图承载个人周历；管理聚合另行设计。

### 2.2 移动端周览（选中日 + 周概览）

- 周标题使用“‹ 本周 · 8/24—8/30 ›”结构；左右箭头切相邻周，中间日期范围可点击打开月历并按所选日期定位其所在周。离开本周后不常驻“回到本周”按钮；月历内提供“今天”，再次点击已选中的底部“计划”可作为辅助复位动作
- 切换相邻周时保留当前选中的星期位置，例如当前查看周三，进入下一周后仍选中周三；月历直接选择某天时进入该天所在周并选中该天
- 顶部使用一行七日摘要条，每天展示日期和待执行/已记录数量；默认选中今天，左右切换或点日期时只替换下方单日内容，不让用户滚过七张长卡才能找到某天
- 单日详情固定分为“待执行 / 业务记录 / 客诉”。pending 保持业务色；执行后不消失，在原计划日期置灰保留；实际拜访、商机推进和报价按业务日期进入记录区，客诉保持独立分区以便快速识别服务风险
- “周概览”按七天显示计划、已执行、临时记录和客诉数量，用于跨日比较、排期和回顾；它只汇总同一周视图读模型，不维护第二份日历数据
- 计划可执行、改期（按天）；不提供脱离实际业务记录的“勾选完成”和裸取消。所有早于今天且仍未执行的计划统一进入独立逾期入口，包括本周已经过去的日期；原日期同时保留风险色，便于对照原计划
- 今天和过去的选中日提供“记录今日实际 / 补录该日实际”，自动带入该日期；未来日期不允许生成实际记录。移动端以执行已有计划为第一视觉入口，但仍允许记录临时发生的拜访、商机推进和客诉

### 2.3 桌面端周览（横向周网格）

- 布局：相邻周箭头 + 可直接选择任意日期所在周的周选择器 + 离开当前周后才出现的“回到本周” + **7 列横向周网格**。每列保持至少约 268px 的可读宽度，窗口不足时横向滚动，不以压缩卡片换取机械的一屏七列
- 每列只保留两个主要语义区：**待执行**放 pending 计划，**已发生**按时间倒序统一放拜访、商机跟进、报价、客诉登记和客诉跟进；不再为客诉制造第三个孤立区域
- pending 卡片整体就是待办入口，点击卡片或“去执行”进入对应领域表单；改期收进次级菜单，不提供“替换计划”。执行后生成的事实显示“来自计划”，计划外补录显示“直接记录”
- 大屏通过 `sourcePlanId` 精确追溯实际拜访、跟进或报价，不靠文本做模糊配对
- completed/cancelled 计划仍在原日期留痕，但默认折叠为“已结束计划”数量，避免与真正待办争夺视觉层级；实际记录同时进入周视图和所属领域时间线
- 同一天没有任何内容时只显示一个整体空态；不分别重复“暂无计划 / 暂无记录 / 暂无客诉”
- 日列顶部保留单一“新增”入口，分组提供安排待办、直接记录拜访/商机推进、登记新客诉；报价作为商机推进中的可选结果，不再成为互斥平级的高频入口
- 更早逾期计划放在周网格上方的可折叠处理区，展开后同样以“去执行”为主操作
- 点击计划或“新增记录”后在周视图内打开领域弹窗/抽屉；保存后关闭弹层并刷新当前周、当前日期，不跳到客户详情页。复用的是拜访、商机和客诉表单组件及命令，不是整个详情路由页面

### 2.4 计划与记录分流（关键原则）

| 动作                   | 思维                     | 交互                                                       |
| ---------------------- | ------------------------ | ---------------------------------------------------------- |
| **安排计划**（未来）   | “哪天推进哪个业务对象”   | 日历式：选客户拜访、商机跟进或客诉跟进，并绑定具体业务对象 |
| **记录事实**（已发生） | “实际做了什么、结果如何” | 类型驱动：走拜访/商机跟进或报价/客诉跟进表单               |

> 安排计划按日期组织，记录事实按领域组织。只有从计划卡片进入的事实才完成该来源计划；直接登记只记录新事实。“计划的业务类型”和“产生它的来源”是两个维度，不能拿来源类型充当执行类型。

是否执行计划由入口在用户操作时已经确定，表单不得再次询问：

- **从计划点击“去执行”**：路由携带该计划 ID，表单只读展示“本次执行计划”；保存事实时填写 `sourcePlanId`，完成该计划并创建下一计划；
- **从“新增或记录”直接进入**：不携带 `sourcePlanId`，只能追加直接发生的事实，绝不把已有计划标记为 completed。

拜访、开放商机推进和客诉跟进无论从哪个入口进入，都必须填写下一次日期和内容；报价作为商机推进的可选结果，不单独完成第二次计划。直接登记时若已有 pending 计划，系统预填其日期和内容：未改动则继续沿用；改动则保持同一计划 ID 和 pending 状态，原地修订下一安排并记录前后日期、内容、原因和操作人。这样既不误判计划执行，也不会产生取消假象或两条 pending 计划。

### 2.5 移动端计划优先与事实只读

- 直接点击底部“记录”默认发生日期为今天并优先展示逾期与今日待办；从周视图某日点击“记录当日实际”则明确带入该日，过去日期显示“正在补录”的上下文。顶部只保留一个可修改且不得晚于今天的“发生日期”，不再使用同时混合计划筛选与事实日期的昨天／今天／明天按钮
- 点击具体计划直接进入对应执行表单，只携带 `planId`；计划日期只读展示，实际发生日期默认今天。系统不得因为计划原定在过去或未来，就把原计划日期静默写成实际发生日期
- 选中客户或商机后再次检查匹配计划：今日/逾期计划以“按此计划填报”为主按钮，未来计划以“提前执行此计划”提示；“记录计划外实际”为弱化入口
- 系统不得根据客户、商机或文本相似自动完成计划；只有点击具体计划进入的表单携带 `sourcePlanId`
- 已发生 item 无论来自计划还是直接记录，点击后均进入类型化只读详情；详情可提供“查看所属对象”链接，但不提供继续填写、修改下一计划或再次完成入口
- completed 计划留在原计划日期置灰；点击时只读展示计划及其执行事实。cancelled 只表达客户释放、商机结案、客诉解决等真实业务终止，不用于表达计划调整

### 2.6 商机推进统一填报

- 销售高频入口统一为“记录商机推进”，字段包含时间、沟通方式、推进结论、是否产生报价和下一次计划
- 本次产生报价时展开口头/正式、金额、单号、文件引用和说明；一次提交原子新增推进事实和可选报价事实
- 报价通过 `followUpId` 关联本次推进，新报价自动替代上一有效报价；计划只完成一次，下一计划只创建或沿用一次
- 单独“补录报价”仅作为报价历史区域的弱化异常入口，不放入移动端快速记录主菜单

### 2.7 联动落位

| 动作             | 落位                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| 客户拜访计划执行 | 展示原计划 → 记录实际拜访 → 完成原计划 → 必填下次拜访计划                                           |
| 商机跟进计划执行 | 展示原计划 → 记录商机推进（可选产生报价）→ 完成原计划 → 必填下一计划                                |
| 客诉跟进计划执行 | 展示原计划 → 记录处理；未解决则必填下一计划，解决则取消剩余计划                                     |
| 手工安排         | 仍须选择上述三种计划类型及业务对象，不提供普通任务                                                  |
| 未实际执行       | 时间变化用改期并填写原因；原计划内容不改写，执行时分别记录实际结果；业务终止由结案/解决命令取消计划 |

### 2.8 计划调整不造成断链

- **改期**：仍是同一件事，只改变当前 `plannedAt`；新日期只能是今天或未来，必须填写原因，并追加原日期、新日期、原因、操作人与操作时间的不可变历史；
- **计划外事实后的下一安排修订**：不代表旧计划被执行，也不创建“替换计划”；保持原计划 ID，将下一日期和内容更新为销售刚刚确认的安排，并保存前后值；
- **计划与实际差异**：原计划内容不允许通过“替换”抹去。用户执行计划时填写实际做了什么，计划内容与实际事实并列保留，供复盘计划与执行差异；
- **终止**：只有客户释放/无效、商机成交/丢失/需求消失、客诉解决等领域终态可以取消剩余计划；
- 不提供“以后再说”或无日期挂起。需要推迟时必须给出明确日期，从而仍可被周视图和逾期规则重新拾起。

## 5. 支撑模块 · 客户管理链路

### 5.1 客户列表

- Web 呈现：以销售判断为目标，关键列为客户（名称+销售大区/城市+状态）、业务画像（客户行业+具体领域）、等级、有效商机、最近活动、下一步行动、负责人；城市和状态不单独占用高价值主列
- Mobile 呈现：每张客户卡依次显示名称、业务画像、销售大区/城市、等级/状态和下一步行动；逾期行动使用风险色，不把桌面表格机械压缩到小屏
- Mobile 加载：每页 20 条无限滚动；请求失败显示重试且保持当前内容，不把失败误判为“没有更多”；下拉刷新保留搜索条件，请求返回按代际丢弃过期响应并按客户 ID 去重
- 衔接：点行 → 详情；"新建客户"主按钮（`customer.write`）

### 5.2 新建客户（查重弹窗交互）

- 字段语义：客户行业与具体领域是两个独立选择，不使用一级/二级或级联概念；省份与地级市使用行政区划联动选择，销售大区由系统自动解析
- 流程：填名称+电话 → 提交时**静默查重**：
  - 硬拦截 → 直接报"已存在"，禁止继续
  - 疑似 → 弹窗列出疑似客户（名称+城市+置信度徽标），三个动作：**查看疑似 / 继续新建 / 申请接管**
- 衔接：继续新建 → 原表单保留不丢失；成功后跳详情
- 内联建档：客户选择器搜不到 → 当前表单内展开快速建档（名称+电话），不跳页

### 5.3 客户详情设计约束

| 必须满足的设计     | 应避免的反模式                                                       |
| ------------------ | -------------------------------------------------------------------- |
| 业务记录入口       | 详情只提供移交、释放等治理操作，却不能记拜访、建商机或登记客诉       |
| 面向人的移交选择器 | 要求用户输入内部用户 ID，而不是按姓名、组织和角色选择负责人          |
| 聚合活动时间线     | 只展示基本资料和联系人，用户必须分别进入多个模块才能判断客户最新进展 |
| 商机连续进展卡     | 只列商机名称、金额和阶段，无法看出跟进、报价与下一步的连续关系       |
| 明确的编辑入口     | 客户资料只能查看，或把编辑能力隐藏在与业务无关的位置                 |

**目标设计**：

```
头部：客户名（+ 状态/等级标签）     操作区：记拜访(主) | 商机 | 客诉 | 编辑 | 移交/接管/释放(危险)
主栏上：商机进展卡（最近3—5个真实活动节点） + 独立下一计划/终态
主栏下：客户活动时间线（拜访/商机/报价/客诉/成交按时间倒序）
侧栏上：经营概览（开放商机、成交次数、成交总额）
侧栏中：联系人（首要联系人优先，可维护；同时显示原始职务和字典化岗位类别，二者不得互相替代）
侧栏下：客户档案（省市/销售大区/客户行业/具体领域/等级/负责人/地址/备注）
```

移动端使用同一优先级纵向排列：快速登记 → 商机进展 → 活动时间线 → 经营结果 → 客户档案。商机卡不是完整商机详情的替代品，点击后进入商机详情继续推进。

商机卡和商机详情不得预设固定步骤格。后端从需求发现、每次推进、每次口头/正式报价、成交、丢单和需求消失投影活动节点；客户卡取最近节点，商机详情展示完整 Timeline。未来的 pending 下一计划单独显示，不能伪装成已经发生的节点。

### 5.4 归属操作衔接

| 操作         | 交互设计                                                                          |
| ------------ | --------------------------------------------------------------------------------- |
| **移交**     | 弹窗：**用户选择器**（搜索显示名）+ 原因；确认后 toast + 详情刷新（负责人列变化） |
| **接管申请** | 弹窗：原因；提交后 toast + 提示"已提交审批"                                       |
| **释放**     | 确认弹窗：去向（公海/无效）+ 原因 + **后果说明**（未解决客诉拦截提示）            |
| **认领**     | 主按钮直接执行 + toast                                                            |

- 所有归属操作**弹窗内完成**，不跳走详情（衔接原则 1.3）

### 5.5 双端一致性验收清单

- ☐ web 详情补齐"业务操作区"（与 mobile"快速登记"同构）
- ☐ 移交选择器双端统一（web 弹窗 / mobile 弹层 picker）
- ☐ 时间线双端呈现（web 表格时间线 / mobile cell 列表）
- ☐ 归属操作双端入口一致（web 完整 / mobile 查看为主 + 关键操作）
- ☐ 客户列表双端读取同一销售判断投影（业务画像、有效商机、最近活动、下一步），只调整信息密度
- ☐ 客户详情双端统一显示省市、销售大区、客户行业和具体领域，字典停用项仍能解析历史值
- ☑ 移动端客户建档复用行政区划 API 和共享客户 DTO；省市联动选择，客户行业与具体领域独立选择，不重新引入自由输入省市或“一级/二级产业”文案

### 5.6 移动端集中改版基线

移动端客户管理按以下页面链路整体走查，不能只改单页样式：

1. **客户列表**：确认业务画像、销售大区/城市、等级/状态、下一步行动和逾期提示的信息顺序；补充有效商机摘要时直接使用客户列表投影，不逐客户额外请求详情。
2. **新建商机与后续报价**：产品线使用多选；初始金额必须选择预估/口头报价/正式报价单依据。后续在“记录商机推进”中勾选本次产生报价，不暴露“改价自”选择器；口头转正式、正式改价均追加版本并自动替代当前有效报价，不覆盖历史记录。表单只提示保存后将替代的当前版本。
3. **客户详情**：保持“快速登记 → 商机进展 → 活动时间线 → 经营结果 → 客户档案”的优先级；档案区统一展示省市、销售大区、客户行业和具体领域。
4. **快速记录中的客户选择器**：客户候选项至少显示名称、城市和业务画像，避免同名客户只靠城市文本辨认；选择“新建商机”后直接进入商机创建，选择“商机推进”后再选择已有开放商机。
5. **移动端建档**：客户列表提供固定“新建”入口；使用省/地级市联动选择，客户行业与具体领域独立选择，销售大区由服务端自动计算；请求体复用共享契约并执行相同查重规则。
6. **跨端回归**：同一客户在 Web 与 Mobile 的地区、业务画像、有效商机、最近活动和下一步必须一致；差异仅限布局和操作形态。

### 5.7 客户经营阶段与 Excel 冷启动

- 客户列表与详情展示系统派生的“潜在客户 / 本年新客 / 存量客户”，不提供人工切换新老客户的下拉框；经营概览将 CRM 前累计成交金额与 CRM 内成交金额分栏，未知历史金额显示“未提供”，不显示为 0
- 桌面客户列表提供“导入客户”工作台，按照“上传文件 → 字段映射与批次默认值 → 查重预览 → 确认导入 → 结果/错误行下载”分步完成；每一步保留前一步选择，禁止上传后直接静默落库
- 批次默认值明确询问导入数据是 CRM 前存量成交、潜在客户还是由每行字段决定，并允许设置默认负责人或导入公海；预览行突出硬重复、疑似重复、字段错误和最终去向
- 模板只要求最小建档字段，允许历史客户缺少联系人；始终必填及条件必填列前置，依次为客户名称、是否存量客户、负责人账号，并在首行说明各字段的适用条件；界面需说明这是冷启动例外，避免用户误以为日常手工建档也可长期省略联系方式

## 6. 商机闭环（推进、可选报价与明确下单）

### 6.1 定位

- 商机的核心是持续回答“最近发生了什么、现在有效报价是什么、下一步由谁何时做”；阶段看板是视图，不是唯一操作入口

### 6.2 桌面端：阶段看板

- 列：intent → following → won / lost / demand_disappeared（§8.5 状态机）
- 卡片：客户 + 名称 + 当前参考金额及来源 + 最近报价 + 当前行动；行动逾期或无下一步时红标
- 点卡片 → 详情页面；日常主操作为“记录商机推进”，表单内按本次实际展开口头/正式报价；“确认下单”和“结案”保持独立终态命令
- 拖拽为可选增强（小团队以按钮推进为主，不强制拖拽）

### 6.3 移动端：列表 + 详情推进

- 列表：按阶段筛选 / 逾期优先
- 详情：基本信息 + 完整商机活动 Timeline + 独立当前计划；活动 Timeline 由后端统一投影真实推进、报价与终态节点，“记录商机推进”仍是商机域专用表单，不是跨拜访、客诉的万能活动模型
- 开放商机的底部操作固定分为“记录推进 / 未成交结案 / 确认成交”；推进表单内可选本次报价，确认成交、丢失和需求消失均可在移动端独立完成
- 终态命令使用独立表单和二次确认；确认成交必须记录客户下单时间与成交金额，失败结案必须选择丢失/需求消失并填写说明

### 6.4 逾期治理

- 逾期商机：当前计划逾期 → 红标/置顶；开放商机无 pending 计划 → “无下一步”；最近报价或跟进超过阈值 → “停滞”
- 风险原因可在读取模型中保留多个，但列表只展示一个按优先级选出的首要待处理原因，其余以数量提示，避免标签堆叠
- **点进去即处置**：记录跟进/重新报价、改期或明确结案；单纯查看不会自动改变状态，也不能只点“完成”

## 7. 客诉闭环（工单式 · 借鉴 Zendesk）

### 7.1 定位

- **待解决驱动**：客诉的价值在"解决"，界面围绕"还有哪些没解决 + 逾期"

### 7.2 列表

- 逾期 / 未解决优先排序，逾期红点
- 状态标签（registered / resolved）+ 解决后置灰
- Web 使用分页主从工作台：左侧/上方为每页 20 条的选择列表，右侧/下方为所选客诉 Timeline；切换客诉不离开页面
- 分页和排序由服务端完成，最多允许每页 100 条；列表不预载所有客诉的时间线

### 7.3 详情

- 顶部状态摘要：客户、类型、处理中/已解决、持续时间；避免重复铺陈详情字段
- 主体使用一条**倒序完整生命周期时间线**：当前待办/解决终点 → 0..N 个处理节点倒序 → 最初登记；打开即看到当前要做什么
- 已发生事实使用实心节点；待办使用空心/虚线节点；逾期标红；解决终点标绿。主表与跟进子表的存储边界不暴露给用户
- 时间线由 API 输出类型化读取模型，Web 与 Mobile 共享节点顺序与状态语义
- 操作：跟进（内容必填；FOLLOWED_UP → 下一步行动；RESOLVED → 解决结果并取消剩余行动）
- 解决为终态，跟进入口置灰/拦截（§8.6）

### 7.4 联动

- 未解决 + 关联行动逾期 → 风险视图（§8.9 客户风险）

## 8. 费用（随手记 · 借鉴记账类应用）

### 8.1 定位

- 轻量统计，非报销（蓝图 §8.8）；"顺手记"不折腾

### 8.2 移动端：快速记一笔

- 默认今天 + 五类金额（烟酒/礼品/餐叙/招待/住宿）快速输入 + 备注 + 提交
- 同天再记 = 更新原记录（upsert，§8.8）
- 入口放在“我的 → 费用管理”，不增加底部主 Tab；移动端默认加载当前月有限记录，并提供新增/更新当天费用

### 8.3 桌面端：月度列表 + 汇总

- 月度列表（按人/月/分项）；汇总卡（个人按日、团队按月）
- 三态可见：draft（草稿灰）/ submitted（计入）/ voided（剔除标灰留痕）

### 8.4 作废

- 确认弹窗："将不再计入统计，留痕可查" → 提交

## 9. 销售计划周视图（日历式）

### 9.1 定位

- 销售计划 + 周目标/复盘 + 指导意见闭环；周视图不拥有第二份计划数据，也不承担普通个人任务管理

### 9.2 行动管理

- 新增有业务对象的客户拜访/商机跟进/客诉跟进计划；pending 可执行或改期，不提供替换计划和裸取消；执行必须进入对应领域表单

### 9.3 计划与完成情况（桌面）

- 周网格展示 pending、completed 和由业务终态取消的计划；通过实际事实上的 `sourcePlanId` 精确追溯计划与完成结果。completed 在原日期置灰，cancelled 弱化显示

### 9.4 指导意见

- 管理者 → 被指导者，**红点已读闭环**；author 须为被指导者上级（§8.7）

### 9.5 移动端“我的”工作摘要

- 默认日程采用七日摘要条 + 选中日详情，另提供周概览；逾期、今日待执行、本周已执行和已发生事实均来自周视图同一读模型
- 逾期和选中日待执行项可直接进入对应领域表单；摘要不复制计划，不允许在此单独勾选完成；费用管理作为同一页面的业务工具入口
- 待关注提醒集中展示逾期行动、接管审批结果、指导意见及管理者待审批事项；未读使用轻量红点，点击后标记已读并进入对应业务对象，不另造通知详情页

## 10. 登录 / 用户管理（标准 SaaS）

### 10.1 登录

- 标准登录页；会话保持（refresh 静默续期）；403 引导（无权限提示）
- 防爆破：错误 5 次锁定提示（后端语义，前端展示）

### 10.2 用户管理

- 表格 + 行操作（编辑 / 停用启用 / 重置密码），交互见 PRD §3
- 操作按 `user.manage` 显隐；停用/重置有确认 + 后果说明

### 10.3 字典配置

- 列表将“显示名称”和“字典值”并列展示：管理者看到中文业务含义，也能识别系统保存的稳定值
- 新增时两项均必填；字典值建议使用稳定英文标识，并明确提示其会被业务数据长期引用
- 编辑时字典值只读，只允许调整显示名称、排序和启停状态；确需替换稳定值时应新增新项并停用旧项
- 各业务表单只展示启用项及其显示名称；历史详情仍能解析已停用项，不直接向用户暴露英文值

## 11. 管理看板（经营结果 + 过程管理）

### 11.1 定位

- `executive/admin` 的桌面登录落地页；回答“销售池子有多大、期间推进与结果如何、团队在做什么、哪些重点客户需要介入”。销售个人不进入完整管理看板，但在日常工作区获得本人商机摘要。

### 11.2 组成

- **管理概览**：首屏先用一张“当前开放商机池”组合卡表达总额、数量、金额构成和风险子集，旁侧放期间成交与结案赢单率；下方保留 S/A 最高优先风险清单和团队/费用摘要，不再用四张平级卡混放存量总额、组成项、风险子集与期间结果。
- **商机经营**：上方使用总额主指标 + 细横向 100% 分段条显示当前“仅预估 / 口头报价 / 正式报价”互斥构成；分段条下使用纵向图例，逐行右对齐数量、金额和金额占比。没有销售目标等可靠分母时不显示总完成率。停滞金额、行动逾期和无下一步放在构成条下作为交叉风险。中部显示期间新增、首次报价、首次正式报价、成交和失败结案；下方人员表用微型分段条表达每人构成。
- **团队动态**：第一层使用自适应人员 Card，卡内突出实际业务记录、待办和逾期；点击后用宽抽屉按日流式展示该人员期间内容，日 Card 不强制七列一行。
- **重点客户**：默认“需要关注”，可切换“全部 S/A”；风险原因使用少量可读标签，整行可进入客户详情。
- **团队费用**：先展示已提交总额和分类结构，再显示人员明细；草稿作为待提交提示，不混进金额。
- **筛选区**：固定在页签上方，提供本周/本月快捷切换、任意日期范围、下辖人员、销售大区和产品线；切换页签保留条件。当前商机池显式标注“截至今日”且不受日期影响，期间结果显式标注所选起止日期。
- **加载策略**：默认只加载当前页签；概览由服务端统一口径聚合。图表为空时保留口径说明，不用 0% 或空坐标轴制造误导。
- **下钻**：商机经营按“人员所属大区→人员→商机列表”逐级下钻；团队动态默认是按大区分组的今日团队紧凑表，可切换本周个人对比，点击人员只展开当日或七天内容；重点客户→客户详情。看板本身只读，不在聚合卡片中偷偷修改业务状态。
- **个人摘要**：桌面端放在“我的工作”页头下方，保持低高度并提供“查看我的商机”；移动端放在“我的”工作摘要之后，首版只读。两端复用相同颜色和顺序：灰=仅预估、蓝=口头报价、绿=正式报价。
