# Lite CRM 测试速查（实战向）

> [!TIP]
> **实战优先**：主线 = 照着做就能写测试。标 ⬇️ 折叠或 `进阶` 的是原理内容，**第一遍跳过不影响**。
> 范本：单测 `apps/api/src/access/access.service.spec.ts` · 集成 `packages/domain/src/services/__tests__/http.spec.ts` · e2e `apps/api/src/auth/__tests__/permission-matrix.spec.ts`

---

## 一、核心模型（3 句记住）

1. **测试 = 把规格承诺翻译成可自动执行的断言。** `it('sales 越权访问用户管理被拒 403')` 就是一句承诺。
2. **金字塔**：单元（多·快）→ 集成 → e2e（少·真）。能用单测别上 e2e。
3. **测哪些 = 有承诺的环节**。没承诺的环节用 smoke 占位即可。

---

## 二、测试架构全景

### 一次 `pnpm test` 的完整流转（7 个节点）

```
你敲 pnpm test
 ① turbo 读根 turbo.json 的 task "test"，从 workspace 发现包清单（8 个）
 ② 逐个包查 scripts.test → 4 个包有，标记为待执行
 ③ 对每个包执行 test script（即 vitest run，cwd = 该包目录）
 ④ vitest 读该包 vitest.config.ts（environment + include）
 ⑤ vitest 按 include 收集 .spec.ts 文件
 ⑥ 执行每个测试文件：beforeAll(建数据/建app) → it() → afterAll(关资源)
 ⑦ 汇总报告；turbo 记录 hash 缓存（下次文件没变直接读缓存）
```

### 架构分层（两层分工）

```
┌────────────────────────────────────────────────────┐
│  触发层：pnpm test（CI 在 push/PR 时跑同一套）        │
└──────────────────────┬─────────────────────────────┘
                       ▼
              turbo test（调度器）
   ┌───────────────┼───────────────┬─────────────────┐
   ▼               ▼               ▼
@crm/api:test   @crm/domain:test  @crm/web+mobile:test
 vitest run       vitest run        vitest run
 env: node       env: jsdom        env: jsdom
   │               │                 │
单测 + e2e      mock fetch 集成    smoke 占位
真实 Postgres   (Pinia/localStorage)
```

- **turbo（调度层）**：管"跑哪些包、按依赖顺序、缓存"——不看测试内容
- **vitest（执行层）**：管"哪些文件、什么环境、怎么断言"——不知道其他包存在

> [!NOTE] 想亲手看一遍"发现机制"：`pnpm exec turbo run test --dry` 只打印计划、不执行。

## 四、工具链速查（谁干什么）

| 工具                | 管什么                                                           |
| ------------------- | ---------------------------------------------------------------- |
| **Vitest**          | 全部测试的引擎（运行/断言/mock/环境），读各包 `vitest.config.ts` |
| **supertest**       | 后端 e2e 发真实 HTTP 请求（打内存 server，不占端口）             |

| **jsdom**           | 给前端/domain 测试模拟浏览器（localStorage/window）              |

| **husky + CI**      | husky 只拦代码风格；**测试由 CI 全量跑**                         |

## 五、写测试五步法（反复训练用）

1. **列承诺**：读规格/需求，一条承诺 = 一个 `it()`
2. **选层**：纯逻辑 → 单测；跨组件 → 集成；服务端裁决/真实数据 → e2e
3. **幂等 setup**：跑两遍结果一致（seed 用 `onConflictDoUpdate`，见 `scripts/seed.ts`）
4. **写断言**：描述**行为**不描述实现；补三类边界——没权限？空数据？不该包含的？
5. **验证**：跑两遍 + **故意改错一条断言确认会红**（防止测试是摆设）

> [!NOTE] `it()` 文案即承诺：`❌ it('calls the service')` → `✅ it('sales 越权被拒 403')`

### 测试数据清理约束

- e2e 数据使用明确前缀或固定 ID，只清理该测试拥有的数据；禁止模糊删除真实业务数据
- 涉及多张外键表时，清理必须在单个事务内按依赖顺序执行
- 不得用 `.catch(() => {})` 吞掉清理错误；清理失败必须让测试变红，否则会形成“测试通过、数据库持续污染”的假象
- 子表没有 `customer_id` 时必须通过真实外键路径清理，例如报价使用 `opportunity_id IN (SELECT id FROM opportunities WHERE customer_id ...)`
- API e2e 共享本地 PostgreSQL 测试库，因此测试文件串行执行（`fileParallelism: false`）；单个文件内部仍可并行纯函数测试，禁止让跨文件造数互相占用客户名额
- 列表型工作台同时断言“查询条件、分页元数据、上下文投影、派生风险”四层结果；风险筛选与行内风险标记必须由同一服务端规则产生
- 固定状态机值（例如 `intent/active/superseded`）应以纯展示函数逐项测试中文名称；可配置分类则测试字典值与 `label` 的解析，不把两类概念混在一起

## 六、后端 e2e 模板（照抄改）

```ts
beforeAll(async () => {
  await seedAccounts() // 幂等造数（脚本共享）
  const app = await Test.createTestingModule({ imports: [AppModule] }).compile()
  app.setGlobalPrefix('api') // ← 必须手动补生产配置
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }))
  await app.init()
})
afterAll(async () => {
  await app.close()
})

async function login(username: string, password: string) {
  // helper 抽离
  const res = await request(app.getHttpServer())
    .post('/api/auth/login')
    .send({ username, password })
  expect(res.status).toBe(200)
  return res.body
}

it('sales 越权访问 /users 被拒 403', async () => {
  const sales = await login('sales1', 'Crm@123456')
  const res = await request(app.getHttpServer())
    .get('/api/users')
    .set('Authorization', `Bearer ${sales.accessToken}`)
  expect(res.status).toBe(403)
})
```

## 七、常用命令

| 命令                             | 作用                                                         |
| -------------------------------- | ------------------------------------------------------------ |
| `pnpm test`                      | 全包测试（turbo 编排）                                       |
| `pnpm --filter @crm/api test`    | 只跑某包                                                     |
| `pnpm exec turbo run test --dry` | 只看测试计划（不执行）                                       |
| `pnpm db:seed`                   | 幂等建 5 个测试账号（admin/manager/sales1/sales2/assistant） |
| `pnpm db:seed:demo`              | 幂等建立 3 个关联业务演示客户；与正式 seed 分离              |

`db:seed:demo` 使用固定 ID 和 upsert，可重复执行而不会追加重复客户，覆盖开放商机、成交、报价后停滞、未来行动与未解决客诉。正式环境只运行 `db:seed`，不运行演示数据脚本。

<summary>⬇️ 进阶：理解「为什么」（第一遍跳过，有兴致再读）</summary>

### A. 约定优于配置：工具怎么发现彼此

**turbo.json 只放"规则"（dependsOn/cache），不放"清单"**——清单全是运行时发现的：

| 层               | 约定来源                                                     | 决定什么                                                       |
| ---------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| 有哪些包         | `pnpm-workspace.yaml` 的 `packages: ['apps/*','packages/*']` | turbo 扫描 glob → 8 个包                                       |
| 每包有没有某任务 | 各包 `package.json.scripts`                                  | 有 → 执行（Command = script 值）；无 → 标 `<NONEXISTENT>` 跳过 |
| 哪些文件是测试   | 各包 `vitest.config.ts` 的 `include: ['src/**/*.spec.ts']`   | vitest 按 `.spec.ts` 约定扫描                                  |
| 任务规则         | 根 `turbo.json`                                              | 只定义"怎么跑"，不定义"谁跑"                                   |

**推论**：给某包补上 `"test"` 脚本，turbo 下次自动纳入，零编排配置。

### B. 手写 vs 自动生成

**写什么内容手写，怎么组织/怎么跑/生成物自动。**

| 环节          | 手写                              | 自动生成/自动计算                             |
| ------------- | --------------------------------- | --------------------------------------------- |
| 应用代码      | DTO、service、组件、store…        | —                                             |
| 契约类型      | DTO 上的 `@ApiProperty` 装饰器    | `openapi.json` + `generated/api.ts`（库生成） |
| 数据库迁移    | `schema/*.ts` 表定义              | `drizzle/*.sql`（drizzle-kit 生成）           |
| 测试文件      | `*.spec.ts` 的断言与 setup        | —                                             |
| 测试配置      | 各包 `vitest.config.ts`（写一次） | —                                             |
| 包清单        | `pnpm-workspace.yaml`（写一次）   | turbo 扫描 glob → 8 个包（自动）              |
| 任务计划      | `turbo.json` 规则（写一次）       | "哪些包有 test/跑什么命令"（自动发现）        |
| 缓存          | —                                 | 输入文件 hash（自动计算）                     |
| 测试报告/日志 | —                                 | vitest + turbo 自动输出                       |

### C. e2e 什么时候非它不可

**涉及"服务端唯一裁决"的承诺必须 e2e**：登录/越权/权限这类"绕过前端也要被拦"的语义，mock 证明不了。慢 + 依赖真实 DB，所以只在关键路径用。

### D. 缓存机制（turbo hash）

turbo 对任务输入文件算 hash；输入没变 → cache hit（秒回），变了 → 重跑。所以**改了源码再跑 test 是增量执行**，没改的包直接命中缓存。

### E. 为什么前后端统一 Vitest（规格决策 2）

弃 Jest 避免 `jest-resolve → unrs-resolver` 原生构建脚本（Windows/pnpm 供应链安全）；顺带 pnpm approve-builds 警告消失。

## 附：环境要求

- **后端 e2e 依赖真实 DB**：本地 `docker compose up -d db`（或 CI postgres service），并在测试前执行 `pnpm db:migrate`；`beforeAll` 只负责幂等 seed，不负责建表
- **CI 必须从空库验证**：GitHub Actions 的 PostgreSQL service 每次均为空库，顺序必须是 install → migrate → lint → typecheck → test → build → contracts:check。若测试报告 `relation ... does not exist`，优先检查迁移步骤，而不是在测试里临时建表
- **扩展属于建库依赖**：模糊检索索引依赖 `pg_trgm`。首份迁移负责声明扩展；本机数据库用户无扩展权限时，由管理员预先执行 `CREATE EXTENSION IF NOT EXISTS pg_trgm`
- **迁移需做双重验证**：既验证已有开发库的增量升级，也验证空数据库能从首份迁移完整执行到最新版本；只验证前者会遗漏扩展、默认值和迁移顺序等隐含前置条件
- **Windows 迁移兜底**：若 drizzle-kit 在 Windows 报 `uv_os_get_passwd ... ENOMEM`，使用 `pnpm --filter @crm/api db:migrate:runtime` 执行同一批已提交迁移
- **迁移日志必须单调递增**：生成迁移后检查 `drizzle/meta/_journal.json` 的 `when` 大于上一条；若历史迁移使用过人工未来时间戳，新生成项可能反而更小，运行时迁移器会无报错地跳过该文件。修正日志顺序后，必须通过实际表结构或种子写入确认迁移确已执行
- **前端/domain 测试**：无外部依赖（jsdom + mock fetch）
- **提交门禁**：husky pre-commit 只跑 lint+format；测试在 CI 全量执行
