# 交互设计打磨（UX · 功能如何呈现、UI 如何衔接）

> **定位**：与 PRD 互补——PRD 定"做什么、功能点"，本文定"**如何呈现、页面间如何衔接**"。
> **核心**：销售计划周视图是移动端主界面的设计主干；历史拜访/跟进是事实时间线，未来计划是唯一待办来源，两者不复制也不混成一个业务模型。
> 配套：`docs/PRD.md`（功能点/验收）、`docs/技术打磨清单.md`（实现健壮性）。
> **设计基线**：历史事实与未来计划分开展示；用户从计划进入对应业务执行，写入实际事实后系统完成原计划并生成下一计划。

## 1. 交互设计基线（跨模块通用）

### 1.1 页面分区（详情页按决策优先级）

```
PageHeader：对象名称 + 状态/等级 + 高频业务操作
  ├─ 当前工作区：开放商机进展 / 当前计划 / 首要待处理事项
  ├─ 历史活动区：拜访、跟进、报价、客诉、成交时间线
  └─ 支撑信息区：经营概览、联系人、基本档案与治理操作
```

**原则**：先回答“现在推进什么”，再回答“之前发生什么”，最后才是“这个对象有哪些资料”。主操作一眼可见；危险操作（释放/结案/作废）与主操作视觉分离。

### 1.2 操作组织

- **主操作**（主色）：新建、提交、认领
- **次要操作**（灰/描边）：编辑、移交、申请接管
- **危险操作**（红色/描边）：释放、结案、作废、停用 → 必须弹确认 + 说明后果
- 入口按能力点显隐（`hasAbility`），无权限不渲染

### 1.3 衔接原则

| 场景                         | 衔接方式                                                               |
| ---------------------------- | ---------------------------------------------------------------------- |
| 列表 → 详情                  | 行点击跳详情（web）；卡片点击（mobile）                                |
| 详情 → 填报表单              | **弹窗/抽屉（web）或 push 页面（mobile）**，完成后返回详情并刷新时间线 |
| 表单提交成功                 | toast + 返回来源页 + 目标页刷新（红线 11，不整页刷新）                 |
| 弹窗类操作（移交/接管/释放） | 弹窗内完成 → 关闭 → 详情局部刷新（`reload`），不跳走                   |
| 返回                         | mobile `router.back()`；web 详情页"返回列表"（保持查询上下文，后置）   |

### 1.4 双端一致性

- 重合功能（客户详情/表单）**结构对齐**：mobile 的"快速登记"组 ↔ web 的"业务操作区"必须同构（§5.4 schema 共享）；
- 差异只在形态（web 弹窗 vs mobile 整页 push），**功能入口一个不少**。

### 1.5 系统级视觉打磨（后置工作）

**当前优先级**：先完成业务模型、核心闭环和主要交互的可用性；不在业务仍频繁变动时开展逐页美化。当 M0–M5 主链路稳定、关键页面信息顺序不再大幅调整后，再以一次系统级改版统一收口。

**目标风格**：专业、克制、紧凑，但不做成纯 CRUD 后台或大屏展示。视觉必须服务于“当前状态如何、哪里需要处理、下一步做什么”，不以颜色、图表或阴影数量衡量完成度。

集中打磨时必须统一处理：

1. **业务视觉语义**：建立客户等级、商机阶段、正常/待关注/需介入、待执行/已完成/已取消/已逾期的固定色彩与标记体系，同一语义不允许跨页变色。
2. **信息层级**：按“对象状态 → 当前重点/下一步 → 业务过程 → 基础资料”组织详情页；列表首先支持判断和处置，不平铺低价值字段。
3. **组件体系**：统一页头、筛选条、指标卡、业务卡、表格、时间线、状态标签、空态、错误态和确认弹窗，减少默认 Element Plus 组件拼装感。
4. **密度与响应式**：桌面端提高有效信息密度并保持主次；移动端按业务优先级重排，不机械压缩桌面表格。
5. **管理看板**：以经营问题和可下钻处置为中心，优先展示商机池健康度、需管理介入事项、团队异常和重点客户；不追求“大屏感”，不把可重复发生的报价类型伪装成线性漏斗阶段。

**验收标准**：任一核心页面都应让用户在首屏判断当前状态和首要操作；关键状态跨模块表达一致；管理看板每个组件都能对应一个管理问题及后续下钻动作。

## 2. 销售计划：周视图（核心界面）

> 心智：**业务日历**——日卡里放的是未来计划，不是“什么都能填”的通用任务。客户拜访、商机跟进、客诉跟进执行后分别形成自己的历史事实。
> 呼应蓝图：§8.7 销售计划唯一事实源、§8.4/8.5/8.6 各领域事实与下一计划联动。

### 2.1 定位

- **移动端主界面**：销售打开看“今天/本周要拜访谁、推进哪个商机、处理哪项客诉”；
- **桌面端“销售计划”页**：个人周历；管理聚合另行设计。

### 2.2 移动端周览（单列日 card 流）

- 布局：周选择器 + **7 张日 card 纵向滚动**；默认定位今天，今天高亮
- 每张日 card 固定分为“计划 / 业务记录 / 客诉”三个语义区；没有内容时显示轻量空态，不用等高空白撑版面
- pending 计划保持业务色；执行后不消失，而是在原计划日期置灰并显示“已执行”；实际拜访/跟进/报价按 `occurredAt` 落到真实发生日期
- 计划可执行、改期（移动端默认按“天”粒度）；不提供脱离实际业务记录的“勾选完成”和裸取消；**早于当前范围仍未执行的计划固定在顶部逾期区**
- 日 card 提供“+ 记录实际”入口；代办来自前置流程，优先支持执行/改期，不在移动端追加计划创建主路径
- 单列适合单手滑动，一屏 1~2 天

### 2.3 桌面端周览（横向周网格）

- 布局：周选择器 + **7 列横向周网格**。每列保持至少约 268px 的可读宽度，窗口不足时横向滚动，不以压缩卡片换取机械的一屏七列
- 每列只保留两个主要语义区：**待执行**放 pending 计划，**已发生**按时间倒序统一放拜访、商机跟进、报价、客诉登记和客诉跟进；不再为客诉制造第三个孤立区域
- pending 卡片直接展示主操作“去执行”，改期收进次级菜单；“替换”作为高级入口保留（默认不在常规待办菜单突出），执行后生成的事实显示“来自计划”，临时补录显示“直接记录”
- 大屏通过 `sourcePlanId` 精确追溯实际拜访、跟进或报价，不靠文本做模糊配对
- completed/cancelled 计划仍在原日期留痕，但默认折叠为“已结束计划”数量，避免与真正待办争夺视觉层级；实际记录同时进入周视图和所属领域时间线
- 同一天没有任何内容时只显示一个整体空态；不分别重复“暂无计划 / 暂无记录 / 暂无客诉”
- 日列顶部保留单一“新增”入口，分组提供安排待办、直接记录拜访/跟进/报价、登记新客诉；客诉登记复用客户业务表单并预填所选日期，避免内容过多时要翻到底部寻找
- 更早逾期计划放在周网格上方的可折叠处理区，展开后同样以“去执行”为主操作

### 2.4 计划与记录分流（关键原则）

| 动作                   | 思维                     | 交互                                                       |
| ---------------------- | ------------------------ | ---------------------------------------------------------- |
| **安排计划**（未来）   | “哪天推进哪个业务对象”   | 日历式：选客户拜访、商机跟进或客诉跟进，并绑定具体业务对象 |
| **记录事实**（已发生） | “实际做了什么、结果如何” | 类型驱动：走拜访/商机跟进或报价/客诉跟进表单               |

> 安排计划按日期组织，记录事实按领域组织。提交事实时完成来源计划并创建下一计划；“计划的业务类型”和“产生它的来源”是两个维度，不能拿来源类型充当执行类型。

从“记录实际”直接进入时，如果该客户或商机已有 pending 计划，表单必须先让用户选择：

- **关联并完成原计划**：本次事实填写 `sourcePlanId`，完成原计划，并安排下一计划；
- **临时记录，保留原计划**：本次事实不填写 `sourcePlanId`，原计划继续有效，也不重复创建另一条计划。

这不是技术冲突提示，而是业务语义选择。系统不得自行把所有直接记录都算作计划执行，也不得在保留原计划时再生成重复计划。

### 2.5 联动落位

| 动作             | 落位                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| 客户拜访计划执行 | 展示原计划 → 记录实际拜访 → 完成原计划 → 必填下次拜访计划             |
| 商机跟进计划执行 | 展示原计划 → 选择记录跟进或重新报价 → 完成原计划 → 必填下一跟进计划   |
| 客诉跟进计划执行 | 展示原计划 → 记录处理；未解决则必填下一计划，解决则取消剩余计划       |
| 手工安排         | 仍须选择上述三种计划类型及业务对象，不提供普通任务                    |
| 未实际执行       | 时间变化用改期；内容或目标变化用替换；业务终止由结案/解决命令取消计划 |

### 2.6 计划调整不造成断链

- **改期**：仍是同一件事，只改变 `plannedAt`；
- **替换**：事情已经变化，默认通过高级入口触达。必须同时写明新时间、新内容和替换原因。系统在一个事务中将旧计划留痕并创建新计划；
- **终止**：只有客户释放/无效、商机成交/丢失/需求消失、客诉解决等领域终态可以取消剩余计划；
- 不提供“以后再说”或无日期挂起。需要推迟时必须给出明确日期，从而仍可被周视图和逾期规则重新拾起。

## 3. 填报便利性（移动端，P0）

### 3.1 默认今天

- 周览默认定位今天；"记一笔"默认今天；表单日期字段默认今天
- 改日期是**例外动作**，不打断"打开即填"

### 3.2 补录快捷（外勤刚需）

- 日期字段提供 **"昨天 / 今天 / 明天"快捷按钮**，点一下切换，不翻日历
- 覆盖"现场没空记、晚上补录"的高频场景

### 3.3 多入口预填

| 入口            | 预填          |
| --------------- | ------------- |
| Tabbar·记一笔   | 默认今天      |
| 周览·某天分区   | 该日期        |
| 客户详情·记拜访 | 该客户 + 今天 |

### 3.4 轻量表单

- mobile 只留必填（客户 + 时间 + 方式 + 一句话），复杂字段收起
- 呼应 P0"顺手快不打断"

## 4. 填报入口（类型面板 · 学 Tabbar）

### 4.1 移动端"记一笔"Tab

- 快捷面板：**拜访 / 商机 / 客诉**三大按钮 + 顶部默认日期（可切昨今天），点哪个进哪个表单（超兔式：意图直接）

### 4.2 桌面端填报入口

- 周视图日列“新增” → 分流为**安排待办 / 记录已发生 / 登记新客诉**，先预填日期和业务对象，再进入对应领域表单
- 侧边栏各模块列表的"新建"按钮（类型入口）
- 客户详情"记拜访"（预填客户）

## 5. 支撑模块 · 客户管理链路

### 5.1 客户列表

- Web 呈现：以销售判断为目标，关键列为客户（名称+销售大区/城市+状态）、业务画像（客户行业+具体领域）、等级、有效商机、最近活动、下一步行动、负责人；城市和状态不单独占用高价值主列
- Mobile 呈现：每张客户卡依次显示名称、业务画像、销售大区/城市、等级/状态和下一步行动；逾期行动使用风险色，不把桌面表格机械压缩到小屏
- 衔接：点行 → 详情；"新建客户"主按钮（`customer.write`）

### 5.2 新建客户（查重弹窗交互）

- 字段语义：客户行业与具体领域是两个独立选择，不使用一级/二级或级联概念；省份与地级市使用行政区划联动选择，销售大区由系统自动解析
- 流程：填名称+电话 → 提交时**静默查重**：
  - 硬拦截 → 直接报"已存在"，禁止继续
  - 疑似 → 弹窗列出疑似客户（名称+城市+置信度徽标），三个动作：**查看疑似 / 继续新建 / 申请接管**
- 衔接：继续新建 → 原表单保留不丢失；成功后跳详情
- 内联建档：客户选择器搜不到 → 当前表单内展开快速建档（名称+电话），不跳页

### 5.3 客户详情设计约束

| 必须满足的设计     | 应避免的反模式                                                       |
| ------------------ | -------------------------------------------------------------------- |
| 业务记录入口       | 详情只提供移交、释放等治理操作，却不能记拜访、建商机或登记客诉       |
| 面向人的移交选择器 | 要求用户输入内部用户 ID，而不是按姓名、组织和角色选择负责人          |
| 聚合活动时间线     | 只展示基本资料和联系人，用户必须分别进入多个模块才能判断客户最新进展 |
| 商机连续进展卡     | 只列商机名称、金额和阶段，无法看出跟进、报价与下一步的连续关系       |
| 明确的编辑入口     | 客户资料只能查看，或把编辑能力隐藏在与业务无关的位置                 |

**目标设计**：

```
头部：客户名（+ 状态/等级标签）     操作区：记拜访(主) | 商机 | 客诉 | 编辑 | 移交/接管/释放(危险)
主栏上：商机进展卡（需求发现 → 最近跟进 → 最近报价 → 下一计划/结果）
主栏下：客户活动时间线（拜访/商机/报价/客诉/成交按时间倒序）
侧栏上：经营概览（开放商机、成交次数、成交总额）
侧栏中：联系人（首要联系人优先，可维护）
侧栏下：客户档案（省市/销售大区/客户行业/具体领域/等级/负责人/地址/备注）
```

移动端使用同一优先级纵向排列：快速登记 → 商机进展 → 活动时间线 → 经营结果 → 客户档案。商机卡不是完整商机详情的替代品，点击后进入商机详情继续推进。

### 5.4 归属操作衔接

| 操作         | 交互设计                                                                          |
| ------------ | --------------------------------------------------------------------------------- |
| **移交**     | 弹窗：**用户选择器**（搜索显示名）+ 原因；确认后 toast + 详情刷新（负责人列变化） |
| **接管申请** | 弹窗：原因；提交后 toast + 提示"已提交审批"                                       |
| **释放**     | 确认弹窗：去向（公海/无效）+ 原因 + **后果说明**（未解决客诉拦截提示）            |
| **认领**     | 主按钮直接执行 + toast                                                            |

- 所有归属操作**弹窗内完成**，不跳走详情（衔接原则 1.3）

### 5.5 双端一致性验收清单

- ☐ web 详情补齐"业务操作区"（与 mobile"快速登记"同构）
- ☐ 移交选择器双端统一（web 弹窗 / mobile 弹层 picker）
- ☐ 时间线双端呈现（web 表格时间线 / mobile cell 列表）
- ☐ 归属操作双端入口一致（web 完整 / mobile 查看为主 + 关键操作）
- ☐ 客户列表双端读取同一销售判断投影（业务画像、有效商机、最近活动、下一步），只调整信息密度
- ☐ 客户详情双端统一显示省市、销售大区、客户行业和具体领域，字典停用项仍能解析历史值
- ☐ 若移动端新增客户建档/编辑入口，必须复用行政区划 API 和共享客户 DTO，不得重新引入自由输入省市或“一级/二级产业”文案

### 5.6 移动端集中改版基线

后续集中调整移动端客户管理时，必须按以下页面链路整体走查，不能只改单页样式：

1. **客户列表**：确认业务画像、销售大区/城市、等级/状态、下一步行动和逾期提示的信息顺序；补充有效商机摘要时直接使用客户列表投影，不逐客户额外请求详情。
2. **新建商机与后续报价**：产品线使用多选；初始金额必须选择预估/口头报价/正式报价单依据。后续记录报价允许选择“改价自”，口头转正式、正式改价均追加版本，不覆盖历史记录。
3. **客户详情**：保持“快速登记 → 商机进展 → 活动时间线 → 经营结果 → 客户档案”的优先级；档案区统一展示省市、销售大区、客户行业和具体领域。
4. **快速记录中的客户选择器**：客户候选项至少显示名称、城市和业务画像，避免同名客户只靠城市文本辨认。
5. **未来新增的移动建档/编辑**：使用省/地级市联动选择；客户行业与具体领域独立选择；销售大区只读自动计算；请求体复用共享契约。
6. **跨端回归**：同一客户在 Web 与 Mobile 的地区、业务画像、有效商机、最近活动和下一步必须一致；差异仅限布局和操作形态。

## 6. 商机闭环（跟进、报价与明确下单）

### 6.1 定位

- 商机的核心是持续回答“最近发生了什么、现在有效报价是什么、下一步由谁何时做”；阶段看板是视图，不是唯一操作入口

### 6.2 桌面端：阶段看板

- 列：intent → following → won / lost / demand_disappeared（§8.5 状态机）
- 卡片：客户 + 名称 + 当前参考金额及来源 + 最近报价 + 当前行动；行动逾期或无下一步时红标
- 点卡片 → 详情抽屉/页面，分开呈现“记跟进”“记口头报价”“登记正式报价”“确认下单”“结案”
- 拖拽为可选增强（小团队以按钮推进为主，不强制拖拽）

### 6.3 移动端：列表 + 详情推进

- 列表：按阶段筛选 / 逾期优先
- 详情：基本信息 + 跟进时间线 + 报价时间线 + 当前行动；操作按钮按业务事实分开，不用一个万能“推进”弹窗

### 6.4 逾期治理

- 逾期商机：当前计划逾期 → 红标/置顶；开放商机无 pending 计划 → “无下一步”；最近报价或跟进超过阈值 → “停滞”
- 风险原因可在读取模型中保留多个，但列表只展示一个按优先级选出的首要待处理原因，其余以数量提示，避免标签堆叠
- **点进去即处置**：记录跟进/重新报价、改期或明确结案；单纯查看不会自动改变状态，也不能只点“完成”

## 7. 客诉闭环（工单式 · 借鉴 Zendesk）

### 7.1 定位

- **待解决驱动**：客诉的价值在"解决"，界面围绕"还有哪些没解决 + 逾期"

### 7.2 列表

- 逾期 / 未解决优先排序，逾期红点
- 状态标签（registered / resolved）+ 解决后置灰
- Web 使用分页主从工作台：左侧/上方为每页 20 条的选择列表，右侧/下方为所选客诉 Timeline；切换客诉不离开页面
- 分页和排序由服务端完成，最多允许每页 100 条；列表不预载所有客诉的时间线

### 7.3 详情

- 顶部状态摘要：客户、类型、处理中/已解决、持续时间；避免重复铺陈详情字段
- 主体使用一条**倒序完整生命周期时间线**：当前待办/解决终点 → 0..N 个处理节点倒序 → 最初登记；打开即看到当前要做什么
- 已发生事实使用实心节点；待办使用空心/虚线节点；逾期标红；解决终点标绿。主表与跟进子表的存储边界不暴露给用户
- 时间线由 API 输出类型化读取模型，Web 与 Mobile 共享节点顺序与状态语义
- 操作：跟进（内容必填；FOLLOWED_UP → 下一步行动；RESOLVED → 解决结果并取消剩余行动）
- 解决为终态，跟进入口置灰/拦截（§8.6）

### 7.4 联动

- 未解决 + 关联行动逾期 → 风险视图（§8.9 客户风险）

## 8. 费用（随手记 · 借鉴记账类应用）

### 8.1 定位

- 轻量统计，非报销（蓝图 §8.8）；"顺手记"不折腾

### 8.2 移动端：快速记一笔

- 默认今天 + 五类金额（烟酒/礼品/餐叙/招待/住宿）快速输入 + 备注 + 提交
- 同天再记 = 更新原记录（upsert，§8.8）

### 8.3 桌面端：月度列表 + 汇总

- 月度列表（按人/月/分项）；汇总卡（个人按日、团队按月）
- 三态可见：draft（草稿灰）/ submitted（计入）/ voided（剔除标灰留痕）

### 8.4 作废

- 确认弹窗："将不再计入统计，留痕可查" → 提交

## 9. 销售计划周视图（日历式）

### 9.1 定位

- 销售计划 + 周目标/复盘 + 指导意见闭环；周视图不拥有第二份计划数据，也不承担普通个人任务管理

### 9.2 行动管理

- 新增有业务对象的客户拜访/商机跟进/客诉跟进计划；pending 可执行、改期、取消；执行必须进入对应领域表单

### 9.3 计划与完成情况（桌面）

- 周网格展示 pending、completed 和由业务终态取消的计划；通过实际事实上的 `sourcePlanId` 精确追溯计划与完成结果。completed 在原日期置灰，cancelled 弱化显示

### 9.4 指导意见

- 管理者 → 被指导者，**红点已读闭环**；author 须为被指导者上级（§8.7）

## 10. 登录 / 用户管理（标准 SaaS）

### 10.1 登录

- 标准登录页；会话保持（refresh 静默续期）；403 引导（无权限提示）
- 防爆破：错误 5 次锁定提示（后端语义，前端展示）

### 10.2 用户管理

- 表格 + 行操作（编辑 / 停用启用 / 重置密码），交互见 PRD §3
- 操作按 `user.manage` 显隐；停用/重置有确认 + 后果说明

### 10.3 字典配置

- 列表将“显示名称”和“字典值”并列展示：管理者看到中文业务含义，也能识别系统保存的稳定值
- 新增时两项均必填；字典值建议使用稳定英文标识，并明确提示其会被业务数据长期引用
- 编辑时字典值只读，只允许调整显示名称、排序和启停状态；确需替换稳定值时应新增新项并停用旧项
- 各业务表单只展示启用项及其显示名称；历史详情仍能解析已停用项，不直接向用户暴露英文值

## 11. 管理看板（经营结果 + 过程管理）

### 11.1 定位

- `executive/admin` 的桌面登录落地页；回答“销售池子有多大、期间转化了多少、团队在做什么、哪些重点客户需要介入”。销售个人仍从客户和移动端待办进入日常工作，不把管理视图强塞给销售。

### 11.2 组成

- **管理概览**：四到六个关键指标卡 + S/A 最高优先风险清单；只负责摘要和下钻，不在首屏堆满所有图表。
- **销售漏斗**：上方显示当前“仅预估 / 口头报价 / 正式报价”互斥存量卡；中部显示期间新增→首次报价→首次正式报价→成交/失败结案；下方是人员拆分表。金额旁始终说明口径，不能把历次报价相加。
- **团队动态**：第一层使用自适应人员 Card，卡内突出实际业务记录、待办和逾期；点击后用宽抽屉按日流式展示该人员期间内容，日 Card 不强制七列一行。
- **重点客户**：默认“需要关注”，可切换“全部 S/A”；风险原因使用少量可读标签，整行可进入客户详情。
- **团队费用**：先展示已提交总额和分类结构，再显示人员明细；草稿作为待提交提示，不混进金额。
- **筛选区**：固定在页签上方，提供本周/本月快捷切换、任意日期范围、下辖人员、销售大区和产品线；切换页签保留条件。
- **加载策略**：默认只加载当前页签；概览由服务端统一口径聚合。图表为空时保留口径说明，不用 0% 或空坐标轴制造误导。
- **下钻**：人员漏斗行→人员商机列表；团队人员 Card→单人期间内容；重点客户→客户详情。看板本身只读，不在聚合卡片中偷偷修改业务状态。
