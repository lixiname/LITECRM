# M0 工程骨架说明

> 一句话：**这套配置不是堆出来的，是从空 template 一步步长出来的——每长一个文件，都在解决一个不加就会踩的坑。**
> 配套阅读：`docs/重构架构决策与实施蓝图.md`（技术规格，决策依据）。

---

## 一、为什么复杂：先看它解决了哪些坑

| 若没有它                               | 会踩的坑                               |
| -------------------------------------- | -------------------------------------- |
| workspace 声明 + 单 lockfile           | 6 个包各自 install，版本满天飞         |
| 共享 tsconfig                          | 三端严格度不一致，A 能过 B 挂          |
| 共享 eslint-config                     | 三端风格漂移，换端如换项目             |
| design-tokens                          | 桌面/移动两套色值，改主题改两处        |
| 契约链路                               | 后端改字段，前端类型不知道，运行期才炸 |
| domain 层约束                          | 页面直接 fetch，URL 散落全仓库         |
| turbo 编排                             | build 顺序靠手动，慢且易漏             |
| 门禁（husky/lint-staged/commitlint）   | 坏代码和乱提交进 git，历史无法回溯     |
| docker-compose + .env.example + README | 换机器环境装不起来                     |
| CI                                     | 本地能过、远端挂，无人兜底             |

**结论：文件数量约等于坑的数量。** 关键不是文件多，而是每个文件都有明确的因果——下面按生长顺序看它们怎么一个个出现。

## 二、成长路径：从空 template 长到现在

### 2.1 演进树（纵览）

```
空 template（各自独立的 vite / nest 脚手架）
 │
 ├─ ① 版本控制   git init + .gitignore + .nvmrc
 ├─ ② 工程中枢   pnpm-workspace.yaml + 根 package.json + turbo.json
 ├─ ③ 规则单源   packages/tsconfig（base/node/vue）
 ├─ ④ 规范单源   packages/eslint-config + 根 eslint/prettier 配置
 ├─ ⑤ 主题单源   packages/design-tokens（tokens 对象 + CSS 变量）
 ├─ ⑥ 三应用骨架 apps/web + apps/mobile + apps/api
 ├─ ⑦ 契约单源   api 的 Swagger → openapi.json → packages/contracts 生成
 ├─ ⑧ 数据配置   api 的 drizzle.config.ts（业务 schema 待 M1）
 ├─ ⑨ 环境兜底   .env.example + docker-compose + README
 └─ ⑩ 门禁+CI    husky + lint-staged + commitlint + GitHub Actions

现在 ──► M1 起填充：contracts 业务 DTO、domain 业务层、drizzle 业务表、各业务模块
```

### 2.2 十步生长日志（每步 = 一个为什么现在做）

| 步  | 动作                                       | 为什么在这一步                                       | 若省略              | 怎么验证                  |
| --- | ------------------------------------------ | ---------------------------------------------------- | ------------------- | ------------------------- |
| ①   | `git init` + `.gitignore` + `.nvmrc`       | 一切改动可回溯、可回滚，是其他一切的地基             | 改错无法恢复        | `git log`                 |
| ②   | 声明 workspace + 根 scripts + `turbo.json` | 先让 pnpm 认识仓库、turbo 认识任务，后续一键起才成立 | 6 个包各自为政      | `pnpm dev:api` 能起       |
| ③   | `@crm/tsconfig`（base/node/vue）           | 三端严格度统一，写业务前先立类型规范                 | 类型检查行为漂移    | `pnpm typecheck` 全绿     |
| ④   | `@crm/eslint-config` + prettier            | 代码风格统一，规则先于业务代码存在                   | 风格漂移、diff 混乱 | `pnpm lint` 无错          |
| ⑤   | `@crm/design-tokens`                       | 双端主题只此一份，从第一行样式就引用它               | 两端色值各写各的    | 改一处两端生效            |
| ⑥   | web/mobile/api 三应用骨架                  | 让三个应用能起、能测、能 lint——业务有处跑            | 写了业务没处跑      | `pnpm dev:*` + smoke test |
| ⑦   | 契约链路（Swagger → contracts）            | 类型唯一来源的管道先通，业务 DTO 是内容              | 前端手写类型、漂移  | `pnpm contracts:generate` |
| ⑧   | `drizzle.config.ts`                        | 迁移驱动的开关先接好                                 | 后续建表无出口      | `pnpm db:generate` 可跑   |
| ⑨   | `.env.example` + docker-compose + README   | 换机器可跑先于写业务                                 | 新环境半天起不来    | 按 README 走一遍          |
| ⑩   | husky/lint-staged/commitlint + CI          | 把规范变强制，异地办公兜底                           | 靠自觉，迟早失守    | 提交一次试试              |

> 规律：**先搭管道，再灌内容。** 契约、DB、门禁都是先有管道后有数据；业务代码（DTO、表、domain）属于内容，M1 起才灌。

## 三、从 0 照做：完整搭建手册

> 本手册不含具体版本号——直接 `pnpm add` 装最新即可（生态已全部同步）。理解"为什么这样"，看上文的成长路径。

### 3.1 前置环境

| 工具    | 要求                | 备注                         |
| ------- | ------------------- | ---------------------------- |
| Node.js | ≥20.19（建议 22.x） | `.nvmrc` 已锁                |
| pnpm    | 11.x                | `corepack enable` 或独立安装 |
| Docker  | 任意近期版本        | 仅本地 PostgreSQL 用         |

### 3.2 骨架文件顺序

按成长路径的十步，**先建文件、后装依赖**：

| 步  | 建什么                                                                                                |
| --- | ----------------------------------------------------------------------------------------------------- |
| ①   | `git init` + `.gitignore` + `.nvmrc`                                                                  |
| ②   | `pnpm-workspace.yaml`（packages 声明）+ 根 `package.json`（scripts/engines/prepare）+ `turbo.json`    |
| ③   | `packages/tsconfig`（base/node/vue）                                                                  |
| ④   | `packages/eslint-config`（index.mjs）+ 根 `eslint.config.mjs` / `.prettierrc`                         |
| ⑤   | `packages/design-tokens`（tokens.ts + tokens.css）                                                    |
| ⑥   | web/mobile/api 三应用骨架（main.ts/router/占位页/vite/vitest；api 的 main.ts/Swagger/drizzle.config） |
| ⑦   | api 的 `scripts/generate-openapi.ts` + `packages/contracts`（scripts: generate/check）                |
| ⑨   | `.env.example` + `docker-compose.yml` + `README.md` + `.github/workflows/ci.yml`                      |
| ⑩   | `.husky/pre-commit` + `.husky/commit-msg` + `commitlint.config.mjs` + `lint-staged.config.mjs`        |

### 3.3 依赖安装（完整命令，根目录执行）

```bash
# ① 根工具链（必须先装！--ignore-scripts 跳过 prepare，否则 husky 未装会失败）
pnpm add -wD --ignore-scripts eslint prettier husky lint-staged @commitlint/cli @commitlint/config-conventional

# ② 共享 eslint-config 的依赖
pnpm --filter @crm/eslint-config add --ignore-scripts typescript-eslint eslint-plugin-vue vue-eslint-parser eslint-config-prettier @eslint/js globals

# ③ 前端运行时
pnpm --filter @crm/web add element-plus pinia vue-router
pnpm --filter @crm/mobile add vant@4 pinia vue-router

# ④ 前端测试
pnpm --filter @crm/web add -D vitest @vue/test-utils jsdom
pnpm --filter @crm/mobile add -D vitest @vue/test-utils jsdom

# ⑤ api 运行时
pnpm --filter @crm/api add drizzle-orm pg @nestjs/config class-validator class-transformer @nestjs/swagger @nestjs/jwt bcryptjs @nestjs/event-emitter

# ⑥ api 开发依赖
pnpm --filter @crm/api add -D drizzle-kit vitest supertest @types/pg @types/supertest openapi-typescript

# ⑦ contracts 契约生成
pnpm --filter @crm/contracts add -D openapi-typescript

# ⑧ 清理 Nest 骨架自带的旧测试 + 冗余 lint（换 Vitest + 共享配置后都不需要）
pnpm --filter @crm/api remove jest ts-jest @types/jest eslint prettier @eslint/js @eslint/eslintrc eslint-config-prettier eslint-plugin-prettier globals typescript-eslint

# ⑨ 构建脚本审批（交互式：原生/二进制类放行，遥测类拒绝）
pnpm approve-builds
pnpm install    # 补跑已批准包的构建脚本
pnpm prepare    # 激活 husky 钩子
```

> 💡 不想交互可手动写 `pnpm-workspace.yaml`：
>
> ```yaml
> allowBuilds:
>   esbuild: true # 平台二进制自检，放行
>   '@scarf/scarf': false # 遥测，拒绝
> ```

### 3.4 版本注意点（踩过的坑）

| 坑                     | 正确做法                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| prepare 鸡生蛋         | husky 未装时任何 pnpm 命令都会因 `prepare: husky` 失败 → 第①步必须 `--ignore-scripts`                         |
| eslint 版本            | 直接用最新（10+）：typescript-eslint / eslint-plugin-vue / vue-eslint-parser 均已声明支持 eslint 10，无需锁 9 |
| @types/bcryptjs        | bcryptjs 3.x 自带 TS 类型，**不要**装 @types/bcryptjs（已弃用）                                               |
| Nest 自带 Jest         | 骨架自带 jest/ts-jest，换 Vitest 后必须移除（否则引入 unrs-resolver 原生构建脚本）                            |
| api 自带 eslint 全家桶 | 共享配置包接管后，api 里的 eslint/prettier/globals/typescript-eslint 全是冗余，移除                           |
| 传递依赖 deprecated    | glob/inflight/esbuild 多版本等警告来自上游，无权升级，忽略                                                    |

### 3.5 首次启动验证

```bash
docker compose up -d db       # 起本地 PG16（含 pg_trgm）
cp .env.example .env
pnpm dev:api | dev:web | dev:mobile      # 三个终端分别起
pnpm lint && pnpm typecheck && pnpm test && pnpm build   # 全仓门禁
pnpm contracts:generate && pnpm contracts:check           # 契约首次生成 + 无 diff 校验
```

## 五、关键机制：4 条链

| 链     | 参与者                                                               | 一句话                                                     |
| ------ | -------------------------------------------------------------------- | ---------------------------------------------------------- |
| 依赖链 | pnpm-workspace.yaml + lockfile + 符号链接                            | 一个 lockfile 锁全部版本，本地包互相链接，改共享包立即生效 |
| 任务链 | turbo.json                                                           | 按 ^build 依赖顺序执行，结果缓存，只重建变更部分           |
| 契约链 | DTO → Swagger → openapi.json → openapi-typescript → contracts → 前端 | 后端是唯一事实源，前端类型永远跟随后端，CI 强制无 diff     |
| 质量链 | husky → lint-staged → commitlint → CI                                | 提交时强制格式化+lint+规范消息；push 时远端跑全套检查      |

## 六、日常开发只用 4 条命令

```bash
pnpm install        # 换机器/新依赖后
pnpm dev:web | dev:mobile | dev:api   # 起开发服务
pnpm db:migrate     # 应用数据库迁移
git commit          # 门禁自动跑
```

其余（contracts:generate/check、db:generate/studio、build/test/lint/typecheck）按需调用，不是日常负担。

## 七、FAQ

**为什么前端拆成 web + mobile 两个应用？**
桌面用 Element Plus、移动用 Vant，UI 体系/路由/页面都不同；但业务逻辑共享——公共部分放 packages/domain，两个应用只放各自的皮。

**为什么 API 不用 Jest（Nest 自带）？**
规格定前后端统一 Vitest。顺带好处：去掉 Jest 后不再引入 unrs-resolver 原生构建脚本，pnpm approve-builds 的警告也随之消失。

**契约链路是不是太绕？**
绕一次，省一劳。前端手写类型时后端改字段 90% 不会同步；契约生成让类型永远跟随后端，且 CI 强制无 diff。

**没有 CI 能不能先跑？**
能。本地 pnpm lint/typecheck/test/build 与 CI 同一套检查；ci.yml 只是搬到远端兜底。

**这些配置能砍掉哪些？**
硬性必需：turbo.json、eslint+prettier、pnpm-workspace.yaml+lockfile、共享 tsconfig。协作护栏（单人可后置）：husky/commitlint/CI/docker-compose——建议保留，越早养成习惯成本越低。
