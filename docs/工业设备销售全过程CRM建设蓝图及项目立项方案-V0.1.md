# 工业设备销售全过程 CRM 建设蓝图及项目立项方案

> 版本：V0.1（讨论稿）
> 编制日期：2026 年 8 月 25 日
> 项目状态：立项前业务讨论
> 适用对象：公司管理层、销售管理人员、销售人员、业助、后台/财务及项目实施人员

## 0. 文档定位

本文件用于在正式投入开发前，统一公司对 CRM 建设目的、业务边界、目标流程、角色职责、分期路线和成功标准的认识，并提请管理层对项目方向和实施原则进行审批。

本文件不是详细页面 PRD，也不是技术开发规格。管理层批准业务蓝图和建设范围后，再据此形成分阶段 PRD、数据口径、实施计划和技术方案。

当前版本基于公司现状访谈、既有 Lite CRM 探索性原型及行业产品调研形成。尚未确认的内容明确列入“待确认事项”，不作为既定事实。

## 1. 项目摘要

公司主营泵浦及成套过滤设备，面向 B2B 小型离散制造业客户开展销售，年经营规模约 6000 万元。销售团队约 20 人，按不同省区开展客户开发和维护，各地区设置相应管理人员。获客方式以园区陌生拜访和老客户维护为主，展会为补充渠道，典型销售周期通常为 1 个月或更长，主要经历需求沟通、方案与报价、持续跟进、下单、出货和回款等环节。

目前客户信息、拜访记录、商机意向、报价进展及回款信息分散在个人微信、旧 CRM、旧 ERP 和多个 Excel 台账中。销售完成拜访后通常没有形成系统化的下一步行动；报价后客户可能一至两个月没有进展，但销售、业助和管理人员无法及时判断原因。业助根据正式报价或口头报价在 Excel 中登记意向金额，后续状态依赖人工向销售询问，造成意向池长期累积、有效性难以确认。订单、出货和回款信息主要由后台通过手工台账跟进，责任销售难以及时查看本人客户的应收和回款情况。

本项目拟建设一套以客户为中心、面向工业设备线下直销的销售全过程 CRM，贯通：

> 客户开发 → 拜访 → 下一步行动 → 商机 → 报价协同 → 下单 → 出货 → 应收 → 回款

项目的核心不是增加销售填报，而是通过“一次记录、多处使用”，让销售获得个人待办、客户历史、报价及回款信息和自动周报，让区域经理获得团队过程与异常清单，让管理层获得可信的销售漏斗、订单结果和回款风险信息。

## 2. 提请管理层审批的核心事项

本次立项建议管理层重点审批以下方向：

1. 是否同意将项目定位为“销售全过程管理”，而非单纯客户资料管理或统计报表建设。
2. 是否同意以“服务销售执行、减少重复填报”为首要产品原则，管理人员原则上优先使用系统数据，不再要求重复提交系统中已有信息。
3. 是否同意首期优先建设客户、拜访、下一步行动、商机、报价状态及自动周报，先解决过程不可见和意向池失真问题。
4. 是否同意订单、出货、应收和回款纳入总体蓝图，并根据 ERP 数据条件分阶段接入。
5. 是否同意复杂产品配置、自动定价和正式报价单生成不纳入首期，报价制作暂时保持现状，CRM 仅承担必要的流程衔接。
6. 是否同意选择一个区域或小组开展试点，经真实使用验证后再推广至全部销售团队。
7. 是否明确项目业务负责人、各角色代表及数据治理责任人，避免项目仅由开发人员独立定义业务规则。

## 3. 业务背景与管理现状

### 3.1 业务特征

| 项目     | 当前情况                                                             |
| -------- | -------------------------------------------------------------------- |
| 产品     | 泵浦及成套过滤设备                                                   |
| 客户     | B2B 小型离散制造业企业                                               |
| 销售方式 | 线下园区陌拜、老客户维护，展会渠道补充                               |
| 销售组织 | 约 20 名销售，按省区划分，地区设管理人员                             |
| 销售周期 | 通常 1 个月或更长                                                    |
| 典型过程 | 接触客户、了解需求、方案/报价、持续跟进、下单、出货、回款            |
| 报价特点 | 产品搭配和价格形成较复杂，价目表难以由销售直接套用，业助承担报价支持 |
| 成交判断 | 下订单后基本视为销售成功；出货后确定性进一步提高；回款完成后经营闭环 |
| 付款特点 | 合同形式不完全固定，存在十多种付款安排，需要支持多节点应收计划       |

### 3.2 当前信息分布

| 信息           | 主要载体                 | 当前局限                                         |
| -------------- | ------------------------ | ------------------------------------------------ |
| 客户与联系人   | 个人微信、旧 CRM、旧 ERP | 分散、信息完整度不一，旧 ERP 多数仅有客户名称    |
| 拜访与商机     | 旧 CRM                   | 填写费力、查询不便、数据不完整，销售本人获益有限 |
| 报价和意向金额 | 业助制作文件、Excel 台账 | 后续状态依赖人工询问，更新不及时                 |
| 周计划与周报   | 人工整理                 | 缺乏连续计划，重复汇总，难以核对                 |
| 订单与出货     | 旧 ERP/后台信息          | 与销售过程缺少衔接，前端销售查看不便             |
| 应收与回款     | 后台 Excel 台账          | 依赖人工查看和催办，销售不易掌握本人客户情况     |

### 3.3 当前管理链路

```text
销售接触客户
  → 个人记录或在旧 CRM 零散填写
  → 需要报价时联系业助
  → 业助制作正式报价或登记口头报价
  → Excel 增加一条意向
  → 业助不定期询问销售进展
  → 未及时更新的意向长期悬空
  → 管理层难以判断有效意向、停滞意向和真实预计成交
```

订单之后的过程同样存在信息断点：后台掌握订单、出货和回款台账，但销售人员无法在客户上下文中方便查看，催款主要依靠人工识别和通知。

## 4. 核心问题与原因判断

### 4.1 销售过程缺少连续的下一步行动

拜访记录主要停留在“已经做过什么”，没有稳定转化为“下一步由谁、在什么时候做什么”。销售依赖个人记忆和小台账，管理层难以知道销售每天在推进哪些客户，也无法及时识别遗漏和停滞。

### 4.2 意向池记录了历史报价，却不能代表有效商机

正式报价和口头报价都会进入 Excel 意向台账，但报价是已经发生的业务事实，不等于客户需求仍然有效。由于缺少最近联系时间、客户反馈、下一步日期、停滞原因及状态确认机制，历史报价持续累积，无法形成可信的有效商机池和销售预测。

### 4.3 现有 CRM 的价值交换不成立

销售人员需要贡献数据，但填写后不便查询自己的客户历史、后续计划、报价和回款情况，也不能自动减少周报、台账和管理询问。系统对销售本人帮助不足，因此个人台账和记忆反而更高效。

### 4.4 多角色协同依赖人工追问

销售掌握客户真实反馈，业助掌握报价结果，后台/财务掌握订单、出货和回款事实，区域经理负责过程管理。当前缺少统一业务对象和状态衔接，各角色通过微信、电话和 Excel 追问，信息更新成本高、责任边界模糊。

### 4.5 过程管理和结果统计相互割裂

拜访、商机和报价反映销售过程；订单、出货和回款反映经营结果。目前两类信息未围绕同一客户和商机贯通，管理层既难以观察过程，也难以分析过程如何转化为结果。

## 5. 建设目标

### 5.1 总体目标

建设一套面向工业设备线下直销的销售全过程 CRM，以客户及具体采购需求为主线，形成销售个人执行、跨角色协同、区域过程管理和公司经营分析的统一数据基础。

### 5.2 分项目标

1. **让销售有用**：提供今日待办、客户历史、下一步提醒、报价/订单/回款查询和自动周报，逐步替代个人零散台账。
2. **让过程可见**：按日呈现销售实际拜访、客户跟进、报价后反馈、逾期事项和需要协助的问题。
3. **让漏斗可信**：区分历史报价、待确认商机、有效商机、停滞商机、暂停/丢失商机和成交订单。
4. **让协同顺畅**：明确销售、业助、区域经理和后台/财务的事实录入与处理责任，减少重复登记和人工追问。
5. **让结果闭环**：逐步贯通下单、出货、应收和回款，使责任销售和管理人员及时识别回款风险。
6. **让数据可治理**：统一客户、商机、报价、订单和回款口径，保留关键业务事件与状态变化，支持追溯。

## 6. 建设原则

1. **先业务、后开发**：先确认管理规则、角色职责和数据口径，再确定页面及技术实现。
2. **销售本人优先受益**：要求销售填写的数据必须能转化为本人可用的客户记忆、行动提醒、进展查询或自动汇总。
3. **一次录入、多处使用**：同一业务事实由最接近事实发生的角色录入一次，其他角色直接使用，禁止 CRM、Excel 和周报重复登记。
4. **下一步驱动**：有效客户和商机不只记录历史，还必须形成明确的后续行动；没有下一步时须明确原因。
5. **异常优于堆报表**：管理视图优先识别逾期、停滞、待确认、高金额风险和回款异常，而非单纯展示累计数量。
6. **事实与判断分开**：报价、订单、出货、到账属于事实；商机有效性、预计成交时间和预计金额属于当前判断，两者不能混用。
7. **系统边界清晰**：CRM 不替代生产、ERP 和财务系统；正式订单、出货和实际到账原则上以 ERP/财务事实为准。
8. **复杂能力分期建设**：产品配置、自动定价、正式报价单生成和深度 ERP 集成在核心流程稳定后单独评估。
9. **移动端任务化**：移动端优先完成现场短任务闭环，不照搬桌面端全部功能。
10. **管理机制同步改变**：管理人员须以系统作为日常管理入口，不能在要求系统填写后继续要求相同内容的线下台账。

## 7. 目标业务蓝图

### 7.1 端到端主流程

```text
客户/联系人
  → 拜访或其他客户互动
  → 形成具体采购需求（商机）
  → 发起报价支持（如需要）
  → 报价完成并进入客户跟进
  → 持续记录客户反馈与下一步行动
  → 下单或明确暂停/丢失
  → 出货
  → 生成应收计划
  → 到期提醒、催收及实际回款
  → 完成经营闭环
```

### 7.2 客户与联系人

客户是长期经营对象，商机是客户某一次具体采购需求。系统应集中保存客户基础信息、联系人、负责人、历史拜访、商机、报价事实、订单及回款概况。

首期重点不是建立尽可能多的客户字段，而是确保销售能快速找到客户、查看历史、记录最新进展并形成下一步行动。客户归属、区域范围和必要的查重机制由服务端统一控制。

### 7.3 拜访与下一步行动

销售完成拜访后，最小必填内容建议包括：

- 客户；
- 本次沟通结果；
- 下一步行动；
- 下一步日期。

如确实没有下一步，应选择暂无需求、等待客户、等待内部支持、项目暂停、已转其他供应商等原因。系统根据下一步日期自动进入销售“今日待办”，逾期后提醒本人，并按规则进入区域经理异常清单。

一次记录应自动更新客户时间线、个人待办、商机进展、周报草稿和管理视图，避免销售重复填写。

### 7.4 商机与销售漏斗

商机用于承载一项具体需求，而不是简单复制客户名称或报价记录。建议每个活跃商机至少回答：

1. 最近一次何时联系；
2. 客户最新反馈是什么；
3. 当前卡在哪里；
4. 下一步由谁在何时完成；
5. 当前预计金额和预计下单时间；
6. 是否需要业助、技术或经理协助。

商机阶段不宜只依赖销售主观判断，应结合业务事实和最近活动进行校验。V0.1 建议采用以下业务状态，最终名称由销售管理层确认：

| 状态       | 说明                                         | 是否计入有效意向池           |
| ---------- | -------------------------------------------- | ---------------------------- |
| 待确认     | 已发现需求或已登记报价，但当前有效性尚未确认 | 单独列示                     |
| 需求沟通   | 已确认存在采购需求，正在了解方案和条件       | 是                           |
| 报价准备   | 已发起报价支持，尚未完成正式报价             | 是                           |
| 已报价跟进 | 已完成口头或正式报价，等待或推动客户反馈     | 是                           |
| 停滞       | 超过管理规则规定时间没有有效互动或下一步逾期 | 单独列示，不直接等同有效预测 |
| 暂停       | 客户项目延后、预算未批等，暂不积极推进       | 否或单独列示                 |
| 已下单     | 已取得正式订单，销售阶段成功                 | 转订单统计                   |
| 已丢失     | 已确认未成交，并记录原因                     | 否                           |

停滞时间阈值、有效确认周期和区域经理介入规则需由管理层审批。

### 7.5 报价协同

首期建设“报价协同”，不建设复杂报价单生成或自动定价系统。

建议流程：

1. 销售在商机内提出报价支持需求，说明客户、需求、预计金额及必要信息；
2. 业助继续使用现有工具和专业判断完成报价；
3. 报价完成时仅确认完成日期、最终金额及必要状态；相同信息不重复填写；
4. CRM 自动记录“已报价”事实，并生成销售后续跟进任务；
5. 正式报价文件是否保存于 CRM，根据实际查阅、交接和追溯需求确定，首期不强制上传；
6. 业助不再维护独立 Excel 意向池，CRM 根据商机和报价状态自动形成清单。

报价制作能力可在后续单独优化。若未来建设产品配置和定价工具，应与 CRM 商机衔接，而非把全部生产和价格逻辑堆入 CRM。

### 7.6 订单与出货

下订单代表销售意义上的基本成功，出货代表履约确定性进一步提高。系统应分别保存或同步订单日期、订单金额、订单编号、出货状态及出货日期，不能用单一“已成交”覆盖全部状态。

订单和出货原则上以 ERP 为事实来源。若首期无法接口集成，可通过后台一次录入、定期导入或外部编号关联实现最小闭环，禁止销售和后台重复维护两套完整订单台账。

### 7.7 应收与回款

不同合同的十多种付款方式应抽象为若干应收节点，而不是为每种付款方式编写独立流程。

| 应收节点示例 | 计划条件       | 计划比例/金额 | 到期日      | 实收金额 | 状态   |
| ------------ | -------------- | ------------- | ----------- | -------- | ------ |
| 预付款       | 下单后         | 按合同约定    | 待计算/确定 | —        | 待收   |
| 发货款       | 发货前或发货时 | 按合同约定    | 待计算/确定 | —        | 未到期 |
| 验收款/尾款  | 验收后若干天   | 按合同约定    | 待计算/确定 | —        | 未到期 |

后台/财务负责正式应收及实际到账事实；销售应能按本人客户查看待收、即将到期和已逾期金额，并承担约定的客户沟通或催收协同责任。系统应按日形成到期提醒和逾期异常清单。

实际回款数据的来源、录入责任、ERP/财务接口条件及销售催款责任仍待确认。

### 7.8 自动周报与管理看板

周报原则上由日常业务记录自动汇总，销售只补充系统无法自动获得的判断和需协调事项。建议包括：

- 本周完成的客户拜访和关键沟通；
- 新增及实质推进的商机；
- 已完成报价及客户反馈；
- 已下单和已出货事项；
- 停滞、逾期和需要协助的商机；
- 下周客户行动计划；
- 应收即将到期及逾期事项。

管理层看板同时提供过程与结果，但应优先展示需要处理的异常：无下一步、逾期未跟进、报价后长期无反馈、高金额停滞、回款逾期等。

## 8. 角色职责与直接价值

| 角色       | 主要职责                                         | 系统提供的直接价值                                             |
| ---------- | ------------------------------------------------ | -------------------------------------------------------------- |
| 销售       | 维护客户反馈、商机判断和下一步行动，配合催收     | 今日待办、客户完整历史、快速记录、报价/订单/回款查看、自动周报 |
| 业助       | 提供报价支持，确认报价完成事实，协助数据质量检查 | 报价支持任务队列、减少微信追问、取消独立意向 Excel 台账        |
| 区域经理   | 审视团队过程，处理停滞、高金额风险和资源协调     | 团队待办、逾期/停滞清单、商机结构、指导意见                    |
| 后台/财务  | 维护或同步订单、出货、应收及实际到账事实         | 统一应收计划、责任人明确、逾期清单、减少重复催办               |
| 管理层     | 确认管理规则、查看经营过程和结果                 | 有效漏斗、订单/出货/回款统计、地区和团队风险                   |
| 系统管理员 | 用户、权限、基础字典及系统维护                   | 统一组织和数据权限、审计追溯                                   |

权限总体原则为“能力权限 × 组织数据范围”：销售查看本人负责数据，区域经理查看管理范围，业助及后台根据实际职责获得必要范围，管理层按审批范围查看汇总和明细。具体权限矩阵需在详细设计阶段确认。

## 9. 数据口径与管理规则

### 9.1 事实、状态与预测分开

- **业务事实**：拜访发生、报价完成、订单形成、出货、实际到账；发生后保留记录。
- **当前状态**：商机当前阶段、是否停滞、下一步和责任人；随业务推进更新。
- **经营预测**：预计成交金额、预计下单日期、成交可能性；属于管理判断，需要定期确认。

### 9.2 金额口径

| 口径               | 定义                                     | 用途         |
| ------------------ | ---------------------------------------- | ------------ |
| 初步需求金额       | 尚未正式报价时，销售对项目规模的初步判断 | 早期储备参考 |
| 正式/口头报价金额  | 确实向客户报出的金额                     | 历史报价事实 |
| 有效商机金额       | 近期确认仍在推进的商机当前预计金额       | 销售漏斗     |
| 停滞/待确认金额    | 超期无进展或尚未完成有效性确认的金额     | 风险和清理   |
| 订单金额           | 已取得订单的金额                         | 销售结果     |
| 已出货金额         | 已完成出货的金额                         | 履约结果     |
| 应收/实收/逾期金额 | 付款计划、实际到账及到期未收金额         | 现金回收管理 |

管理层不得直接以历史报价累计金额代表有效销售预测。

### 9.3 时间粒度

管理视图按日更新，但底层保存真实事件日期和时间，包括拜访、报价、下一步、下单、出货、应收和实收日期。系统自动按天、周、月汇总，不要求人工制作每日快照。

### 9.4 待管理层确定的规则

- 报价后正常跟进周期；
- 多少天无有效互动进入停滞；
- 多少天未更新需区域经理介入；
- 暂停商机多久重新确认；
- 哪些商机必须填写预计下单日期；
- 回款到期前多少天提醒；
- 逾期后销售、区域经理和后台分别承担什么责任；
- 长期不跟进客户是否允许移交或进入公海。

## 10. 建设范围建议

### 10.1 首期建议范围

首期以解决“销售本人不好用、下一步缺失、意向池不可信”为目标：

1. 客户、联系人、负责人及基础查重；
2. 移动端客户查询和快速拜访记录；
3. 下一步行动、今日待办和逾期提醒；
4. 商机及有效性确认；
5. 轻量报价支持状态衔接；
6. 销售个人客户时间线和商机视图；
7. 区域经理团队过程及异常清单；
8. 自动周报草稿；
9. 基础权限、区域数据范围和审计；
10. 订单、出货和回款采用最小可行的查看/录入或导入方式，具体取决于 ERP 条件。

### 10.2 后续候选范围

- ERP 自动同步订单、出货和回款；
- 完整应收计划和回款协同；
- 报价支持工作流、价格审批和外部文件链接；
- 产品配置、自动定价和报价单生成；
- 钉钉免登、消息和待办集成；
- 展会线索批量导入和线索培育；
- 客诉、费用及其他经营模块；
- 语音/文字快速录入与智能摘要；
- 管理预测和经营分析深化。

### 10.3 首期明确非目标

- 替代 ERP、生产管理或财务核算系统；
- 一次性建设完整合同、订单、库存、开票和财务系统；
- 在 CRM 内直接实现复杂产品组合和全部报价计算；
- 要求销售重复维护 CRM、Excel 和手工周报；
- 未经业务验证即开发大量管理报表或 AI 功能；
- 为追求字段完整而增加与执行无关的必填项。

## 11. 分阶段实施路线

| 阶段        | 建设重点                                                 | 建议验证结果                                                 |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| A. 业务确认 | 统一流程、阶段、金额口径、角色职责和管理规则             | 管理层批准蓝图；销售、业助、区域经理、后台代表确认流程       |
| B. 小组试点 | 客户、拜访、下一步、商机、报价状态、个人工作台和自动周报 | 销售愿意日常使用；有效商机可识别；区域经理能按系统开展周管理 |
| C. 管理推广 | 团队异常看板、全区域推广、数据清理和使用制度             | 大部分重复台账取消；意向池定期确认；管理层获得可信过程数据   |
| D. 结果闭环 | 订单、出货、应收和回款查看/同步及提醒                    | 销售可查看本人客户回款；后台和管理层掌握逾期风险             |
| E. 深化优化 | ERP 集成、报价工具优化、钉钉和智能录入                   | 减少手工导入和重复操作，逐步提升自动化                       |

每个阶段应先试点、再验收、后推广，不以功能开发完成代替业务使用成功。

## 12. 成功指标建议

V0.1 先提出指标方向，目标值由管理层结合试点基线确认。

| 目标     | 指标建议                                    | 建议目标（待审批）   |
| -------- | ------------------------------------------- | -------------------- |
| 销售可用 | 单次基础拜访记录完成时间                    | 常规场景不超过 30 秒 |
| 行动闭环 | 活跃商机具备明确下一步的比例                | ≥ 90%                |
| 漏斗可信 | 超期未确认商机得到处理的比例                | ≥ 90%                |
| 减少重复 | CRM 之外重复意向 Excel 台账                 | 试点稳定后取消       |
| 周报减负 | 可由系统自动生成的周报内容比例              | ≥ 80%                |
| 过程可见 | 区域经理可通过系统识别的逾期/停滞事项覆盖率 | ≥ 90%                |
| 结果可见 | 责任销售可查看的订单、出货和应收覆盖率      | 分阶段达到 ≥ 90%     |
| 使用成效 | 试点销售持续使用率                          | 目标值待定义         |
| 数据质量 | 有效商机最近活动、状态和金额完整率          | ≥ 90%                |

除系统数据外，应通过试点访谈确认销售是否减少个人重复台账、业助是否减少人工追问、区域经理是否真正用系统开展管理。

## 13. 实施与治理机制

### 13.1 项目组织建议

- 指定一名管理层项目发起人，负责跨部门决策；
- 指定一名业务负责人，对流程、口径和验收结果负责；
- 销售、业助、区域经理、后台/财务各安排代表参与；
- 开发人员负责实现和技术风险，不代替业务负责人决定管理规则；
- 建立固定评审节奏，按真实业务案例验收，而非只看页面演示。

### 13.2 试点原则

- 优先选择业务量适中、管理人员愿意使用、销售代表性较强的一个区域或小组；
- 试点同时包含销售、业助和区域经理，避免只测试单一角色；
- 使用真实客户和真实商机，但做好数据权限和必要脱敏；
- 试点期间保留必要兜底，达到验收条件后再取消重复台账；
- 对不使用、难使用和数据不可信的原因逐项复盘，不以强制填报掩盖产品问题。

### 13.3 数据迁移原则

- 优先迁移仍有经营价值的客户、联系人、有效商机和未结应收；
- 历史报价累计台账须先清理有效性，不能全部直接作为活跃商机导入；
- 旧 CRM、ERP 和 Excel 的重复客户应统一识别；
- 微信中的个人客户资料需要制定可执行的整理办法，不能依赖一次性人工全量搬迁；
- 历史拜访等低价值过程数据可按成本评估，不追求形式上的全量迁移。

### 13.4 管理制度配套

- 系统已自动汇总的信息不再要求线下重复报送；
- 管理人员在会议和辅导中优先使用系统记录；
- 数据质量问题反馈到具体流程和责任角色，不笼统归责销售；
- 必填字段和提醒规则由业务价值驱动，定期清理无使用者的数据项；
- 对商机有效性、停滞处理和回款协同形成明确管理规则。

## 14. 主要风险与应对

| 风险             | 表现                         | 应对原则                                       |
| ---------------- | ---------------------------- | ---------------------------------------------- |
| 再次成为填报系统 | 销售录入后仍需写Excel和周报  | 一次录入多处使用，先取消重复环节再推广         |
| 范围失控         | 同时建设CRM、报价、ERP和财务 | 明确首期边界，复杂报价和深度集成后置           |
| 数据不可信       | 商机长期不更新、金额虚高     | 下一步驱动、定期确认、停滞自动识别             |
| 管理层不用系统   | 仍通过口头和微信追问         | 管理会议使用系统，形成统一入口                 |
| 角色责任不清     | 业助继续追问并维护全量意向   | 明确销售维护客户判断、业助确认报价事实         |
| ERP条件不明      | 订单/回款重复录入            | 先摸清数据源和接口，采用最小衔接方案           |
| 移动体验不佳     | 现场填报步骤多、查询不便     | 任务化首页、默认带入、最小必填、真实场景测试   |
| 旧数据污染       | 历史台账全部作为有效商机导入 | 迁移前清理和分类，保留历史事实但不冒充有效预测 |

## 15. 待确认事项

以下内容不阻碍 V0.1 进入讨论，但应在正式立项或阶段 A 完成前确认：

1. 管理层最关注的过程指标、结果指标及优先顺序；
2. 各区域组织关系、业助服务范围和具体权限；
3. 商机阶段名称、停滞阈值和经理介入规则；
4. 典型付款方式及一个订单分批出货、分批回款的情况；
5. 销售在催款中的责任以及回款与绩效/提成的关系；
6. ERP 当前保存的订单、出货、开票和回款数据及导出/API能力；
7. 报价文件当前存放、查阅和人员交接的真实需求；
8. 客诉、费用、客户公海和接管审批是否属于首期重点；
9. 试点区域、计划周期、预算、开发和长期维护资源；
10. 旧 CRM、ERP、Excel 和个人微信数据的迁移范围。

## 16. 与现有 Lite CRM 探索成果的关系

现有 Lite CRM 及其 PRD、技术蓝图、交互设计和原型代码，反映了前期对移动端填报、客户旅程、客户归属、权限、拜访、商机、客诉、计划和费用等问题的探索，也验证了部分技术路线的可行性。

本次立项不以现有实现作为既定范围。应当先依据本文件确认业务蓝图，再逐项判断现有成果：

| 现有探索                 | 对新蓝图的意义               | 建议处理                               |
| ------------------------ | ---------------------------- | -------------------------------------- |
| 客户、联系人、查重和归属 | 构成客户数据基础             | 保留思路，按实际管理规则复核           |
| 拜访、商机和下一步行动   | 与核心问题高度一致           | 作为首期主链路深化                     |
| 移动快速填报和周视图     | 有助于销售本人使用           | 以真实现场体验重新验收                 |
| 权限、组织树和区域范围   | 符合分省区管理模式           | 结合真实组织关系调整                   |
| 周计划与指导意见         | 可支撑过程管理               | 验证是否需要销售另填计划，优先自动生成 |
| 客诉、费用、接管审批     | 具备业务价值，但优先级未确认 | 不因已经开发而自动纳入首期             |
| 报价、订单、出货和回款   | 现有覆盖不足                 | 在新蓝图中补齐并分期建设               |
| 技术架构与契约体系       | 证明实现基础和可维护性       | 作为后续技术方案输入，不占管理正文重点 |

因此，现有 Lite CRM 应定位为“前期探索和可复用资产”，而非倒推立项范围的依据。

## 18. V0.1 结论

本项目的首要价值不在于建立更多表单，而在于把分散在销售个人、业助和后台手中的信息转化为连续、可行动、可确认的销售过程。

建议管理层首先批准项目方向、首期边界、实施原则和试点机制；随后由跨角色业务小组在阶段 A 内确认商机、报价、订单和回款规则，再进入详细产品设计和开发排期。
