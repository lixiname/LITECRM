## 批次 8：移动端销售闭环与个人工作台

### 已落地

- 移动端周视图与桌面端统一为“待执行 / 已发生”两层：待执行计划不因完成而消失，而是转为灰色已结束计划并保留在原计划日期；执行产生的拜访、商机跟进、报价和客诉事实按实际发生日展示，并标识“来自计划 / 直接记录”。
- 周视图支持从计划直接进入对应业务表单；原计划的客户、商机、计划时间和计划内容作为上下文带入，用户只补实际结论、实际时间及下一次行动。临时发生的拜访、商机跟进、报价和客诉仍可从当日直接记录，不伪造计划。
- “我的”从纯账号页调整为个人销售工作台，集中呈现逾期待执行、今日待执行、本周已执行和本周已发生，并允许从逾期及今日事项直接进入执行表单；账号、角色、数据范围和退出登录保留在下方。
- 移动端新增独立商机详情：集中展示阶段、客户、负责人、当前参考金额及依据、下一计划、需求与预计成交时间、报价历史和跟进历史；客户页商机卡先进入该详情，不再默认跳入跟进表单。
- 移动端商机支持独立执行“记录跟进 / 记录报价 / 确认成交 / 未成交结案”。确认成交要求下单时间和成交金额，可关联被客户接受的有效报价；未成交结案明确区分丢单与需求消失并要求说明。两类终局命令均复用服务端原有事务和行动收口，不依赖桌面端补录。
- 移动端新建商机补齐金额是否约数、金额说明、需求发现日、预计成交日和正式报价单引用；跟进补齐实际发生时间与稳定编码的沟通方式；报价补齐报价时间、正式报价编号和文件引用。跟进方式由共享领域选项统一中英文映射，历史 `offline_visit` 与新表单继续使用同一稳定编码。
- 移动端所有写入路由统一要求 `customer.write`；只读业助可查看数据，但不能通过直接地址进入快速记录、拜访、商机、客诉或费用填报。费用接口同步增加服务端能力校验，权限不再只依赖页面隐藏。

### 验证基线

- 移动端投影测试覆盖“完成计划仍保留在原计划日、执行事实通过 `sourcePlanId` 回链”和各业务类型执行路由；服务端权限测试覆盖销售可访问费用、只读业助被拒绝。
- 以 390×844 移动视口完成真实浏览器验收：销售周视图、个人工作台、客户活动时间线、商机详情、跟进表单、成交表单、丢单/需求消失表单均可正常打开；销售、区域经理、管理员分别显示本人、本团队、全部数据范围；业助写入路由和写入入口均被拦截。
- 本批不新增数据库表或迁移；继续复用 `follow_up_actions`、`sourcePlanId`、商机跟进/报价事实及明确终局命令。

## 批次 7：管理看板首版

### 已落地

- 桌面端新增管理看板，按“管理概览 / 销售漏斗 / 团队动态 / 重点客户 / 团队费用”组织第一批可直接用于管理决策的读模型；管理者登录默认进入看板，销售仍进入个人周视图。
- 商机口径拆为“当前开放池”和“期间流量”：开放池中每个商机只计最近有效报价，无有效报价时回退预估金额，并分别展示仅预估、口头报价、正式报价；期间流量独立统计新增、首次报价、首次正式报价、成交和失败结案，避免存量与流量相加。
- 漏斗支持按日期、下辖人员、销售大区和产品线筛选；人员汇总展示开放商机、报价池、停滞金额和本期成交，并可下钻到已带负责人筛选的商机列表。
- 团队动态按业务事实的实际记录人归属，汇总拜访、跟进、报价、客诉处理、待执行和逾期行动；人员卡可打开同一期间的逐日内容，选择“本周”时即形成单人周内容。
- 重点客户只覆盖下辖人员的 S/A 类客户，关注原因由未解决客诉、行动逾期、无下一步、长期无动作和预计成交逾期实时派生，不新增易失真的手工风险字段。
- 团队费用只将已提交记录计入金额，按人员和类别聚合；草稿只提示数量，作废记录不进入经营口径。
- 报表接口统一受 `dashboard.view` 和既有组织可见范围约束；管理者查看单人周内容时必须显式校验目标人员属于可见范围。数据库日期边界统一按 `Asia/Shanghai` 业务日处理。
- Docker 开发库固定映射到宿主机 5433，避开 Windows 本机 PostgreSQL 的 5432；迁移、基础种子、演示数据与 API 均已确认连接同一容器数据库。

## 批次 6：桌面端周视图交互收口

### 已落地

- 桌面端日列从“计划 / 业务记录 / 客诉”三个并列小区重构为“待执行 / 已发生”两层，客诉登记与客诉处理和其他业务事实一起按发生时间倒序展示。

- 更早逾期计划改为可折叠处理区，并与日列待办使用一致的“去执行”主操作。
- 本批只调整 Web 读取与交互投影，复用既有事实模型和领域表单，不需要数据库迁移；移动端周视图待后续移动端集中改版时按同一语义对齐。

## 批次 4：商机多产品线与初始商业金额事实

### 已落地

- 商机产品线从 `opportunities.product_line` 单值字段改为 `opportunity_product_lines` 关系表，同一商机支持 0..N 个产品线，Web 与移动端新建入口均使用多选。
- 新建商机增加初始金额依据：预估金额、口头报价、正式报价单。预估只进入商机预测快照；报价依据会追加首条报价事实并使商机进入 `following`。
- 商机主记录、产品线关系、可选首条报价、第一步行动和客户最近活动投影由一个数据库事务完成，不产生“建了商机但报价或行动缺失”的中间状态。
- 列表、详情和客户商机卡统一展示当前参考金额及来源；当前参考金额优先取最近有效报价，无有效报价时回退预估金额。
- 后续改价继续复用报价追加模型：口头转正式、正式报价改价都新增报价，选择被替代报价后写入 `supersedes_quote_id` 并将旧报价置为 `superseded`；不选择时保留为并行有效方案。Web 与移动端均提供该选择。
- 迁移文件为 `0010_calm_santa_claus.sql`；OpenAPI 与共享 domain 类型已同步。

- 当前数据库仍为测试/演示数据，迁移允许直接移除旧单值产品线字段，不保留错误的双写兼容层。

## 批次 5：客诉生命周期时间线

### 已落地

- 客诉存储模型保持不变：主表保存当前状态，`complaint_follow_ups` 只追加处理事实，`follow_up_actions` 保存唯一当前行动。
- 详情接口新增统一 `timeline` 读取模型，包含 `registered / follow_up / pending_action / resolved` 四类节点，并由服务端统一派生 pending/overdue 状态和处理人名称。
- Web 客诉详情改为“状态摘要 + 完整生命周期时间线”；登记、历次处理、当前待办及解决结果不再拆成详情字段与二级记录表。
- Mobile 新增客诉详情页，客户详情和周视图中的客诉记录可进入同一时间线；处理按钮继续进入轻量执行表单。
- Web 客诉列表与 Timeline 合并为一个分页主从工作台；默认每页 20 条、最大 100 条，旧 `/complaints/:id` 地址重定向到工作台并保留选中项和执行计划参数。
- 客诉列表 API 改为服务端分页摘要，支持状态、关键词、客户和逾期筛选，数据库统一按未解决逾期、未解决、已解决排序；仅选中客诉加载 Timeline。
- 客诉详情读取权限与维护权限拆开：数据范围内可查看，只有客户维护者/管理链/admin 可以追加处理或确认解决。

### 验证基线

- 真实数据库主链用例覆盖未解决客诉的“登记 + 当前待办”以及解决后的“登记 + 处理 + 解决终点”节点序列。
- 本批不需要数据库迁移，仅新增 API 读取投影和双端呈现。
- Timeline 统一采用倒序阅读：顶部为当前待办或解决结果，其后为最近处理到最早处理，最底部为客诉登记；列表分页与排序规则不受影响。
- 全仓 86 项测试、类型检查、lint、契约一致性和生产构建均通过；运行中的 API 已验证分页响应及演示客诉 `pending_action,registered` 节点序列，Web `/complaints` 返回 200。

## 批次 1：客户查重、客户等级与分级名额

### 已落地

- 客户当前分级字段由 `level` 统一为 `grade`，API、契约、domain、Web 和移动端同步改名；S/A/B/C 只表达客户等级。
- 公司默认名额改为 `customer_grade_quota_defaults`；个人覆盖改为 `user_customer_grade_quota_overrides`，唯一口径为 `(user_id, customer_grade)`。
- 建档、移交、公海认领、接管审批和客户改级均按“负责人 × 客户等级”检查 active 客户名额。
- 名额校验进入业务事务，并先锁定目标负责人行；同一负责人的并发名额占用被串行化，不再在事务外先 count 后写入。
- `normalized_key` 唯一索引已移除，只用于疑似重复候选和检索；ERP 客户编码、统一社会信用代码仍为可空硬唯一键，空字符串入库前归为 NULL。
- 新增 append-only 的 `customer_grade_changes`；客户改级必须提供原因，并记录原等级、新等级、操作人和业务时间。
- 客户资料更新要求 `expected version`（请求字段为 `version`）；客户资料、联系人、归属变更和接管审批相关更新开始统一维护 `updatedAt/version`，并在并发冲突时返回 409。
- 数据库迁移保留原名额配置行并映射到同一客户等级；若旧表存在同一负责人、同一等级的重复覆盖记录，迁移主动中止并要求人工合并，不静默丢数据。

## 批次 2：销售事实、报价事实与统一未来行动

### 已完成代码收口

- `visit_records` 只保存已发生的拜访事实；可选的下一行动写入独立 `follow_up_actions`，不再复制到周计划项。
- 新增 append-only 的 `opportunity_follow_ups`；商机主表只保存当前阶段、估算和最近跟进时间，不用一行覆盖历次结论。
- 新增 `opportunity_quotes`，同一商机允许口头报价 0..N、正式报价 0..N；重新报价追加记录，只有显式替代才把旧报价标为 `superseded`。
- 移除“推进接口带报价金额即成交”的旧路径；新增 `/opportunities/:id/follow-ups`、`/quotes`、`/win` 和 `/close` 四类明确命令。
- 商机赢单状态统一为 `won`；只有 `/win` 生成 Deal，`deals.source_opportunity_id` 设计为必填且唯一，可选关联客户接受的报价。
- 新增 `follow_up_actions` 作为未来行动唯一事实源，覆盖手工、拜访、商机初始/跟进/报价、客诉初始/跟进七类来源；支持 pending/completed/cancelled、完成、改期、取消和乐观锁。
- 记录口头或正式报价时必须同时安排报价后的客户反馈行动，直接封住“报价事实已登记但后续无人跟”的断点。
- `weekly_plans` 只保留业务周摘要；周视图直接查询行动，并单列早于当前查询范围的逾期待办。
- 客户移交、认领和接管批准会同事务转交未完成行动；客户释放会取消其剩余行动，历史事实和已完成行动不改写。
- 客诉主表保存当前状态，跟进只追加；继续处理时完成旧行动并创建下一行动，解决时取消剩余行动。
- Web 已提供商机跟进、报价、确认成交、结案和行动周视图；移动端拜访/新建商机/登记客诉表单与行动周视图已切换新模型。
- OpenAPI 及共享 domain 类型已重新生成/同步；旧 `AmountType`、`AdvanceOpportunityDto`、`ordered` 和多套未来日期字段不再出现在现行业务契约中。

### 数据迁移设计
