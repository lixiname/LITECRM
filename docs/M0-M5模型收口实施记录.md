## 批次 1：客户查重、客户等级与分级名额

### 已落地

- 客户当前分级字段由 `level` 统一为 `grade`，API、契约、domain、Web 和移动端同步改名；S/A/B/C 只表达客户等级。
- 公司默认名额改为 `customer_grade_quota_defaults`；个人覆盖改为 `user_customer_grade_quota_overrides`，唯一口径为 `(user_id, customer_grade)`。
- 建档、移交、公海认领、接管审批和客户改级均按“负责人 × 客户等级”检查 active 客户名额。
- 名额校验进入业务事务，并先锁定目标负责人行；同一负责人的并发名额占用被串行化，不再在事务外先 count 后写入。
- `normalized_key` 唯一索引已移除，只用于疑似重复候选和检索；ERP 客户编码、统一社会信用代码仍为可空硬唯一键，空字符串入库前归为 NULL。
- 新增 append-only 的 `customer_grade_changes`；客户改级必须提供原因，并记录原等级、新等级、操作人和业务时间。
- 客户资料更新要求 `expected version`（请求字段为 `version`）；客户资料、联系人、归属变更和接管审批相关更新开始统一维护 `updatedAt/version`，并在并发冲突时返回 409。
- 数据库迁移保留原名额配置行并映射到同一客户等级；若旧表存在同一负责人、同一等级的重复覆盖记录，迁移主动中止并要求人工合并，不静默丢数据。

### 当前边界

- 分级名额配置表和服务端约束已具备，管理配置页面尚未开发。
- 客户改级 API 已具备，现有 Web/移动详情页尚无编辑入口。
- 乐观锁尚未覆盖商机、拜访、客诉、计划、费用等全部可变聚合；本批只覆盖触及的客户及归属路径。
- 客户互动、商机跟进、多次报价、统一未来行动和明确下单仍属于后续批次。

### 本批验证结果

- `0005_customer-grade-quota.sql` 已在本地测试库执行成功。
- 全仓 `pnpm typecheck` 通过。
- 全仓 `pnpm test` 通过：API 57、domain 11、Web 1、mobile 1，共 70 项。
- 新增用例已验证：分等级计数、满额 409、并发争用最后一个名额仅一条成功、相同 normalizedKey 可分别建档、改级原因/历史和旧版本 409。

## 批次 2：销售事实、报价事实与统一未来行动

### 已完成代码收口

- `visit_records` 只保存已发生的拜访事实；可选的下一行动写入独立 `follow_up_actions`，不再复制到周计划项。
- 新增 append-only 的 `opportunity_follow_ups`；商机主表只保存当前阶段、估算和最近跟进时间，不用一行覆盖历次结论。
- 新增 `opportunity_quotes`，同一商机允许口头报价 0..N、正式报价 0..N；重新报价追加记录，只有显式替代才把旧报价标为 `superseded`。
- 移除“推进接口带报价金额即成交”的旧路径；新增 `/opportunities/:id/follow-ups`、`/quotes`、`/win` 和 `/close` 四类明确命令。
- 商机赢单状态统一为 `won`；只有 `/win` 生成 Deal，`deals.source_opportunity_id` 设计为必填且唯一，可选关联客户接受的报价。
- 新增 `follow_up_actions` 作为未来行动唯一事实源，覆盖手工、拜访、商机初始/跟进/报价、客诉初始/跟进七类来源；支持 pending/completed/cancelled、完成、改期、取消和乐观锁。
- 记录口头或正式报价时必须同时安排报价后的客户反馈行动，直接封住“报价事实已登记但后续无人跟”的断点。
- `weekly_plans` 只保留业务周摘要；周视图直接查询行动，并单列早于当前查询范围的逾期待办。
- 客户移交、认领和接管批准会同事务转交未完成行动；客户释放会取消其剩余行动，历史事实和已完成行动不改写。
- 客诉主表保存当前状态，跟进只追加；继续处理时完成旧行动并创建下一行动，解决时取消剩余行动。
- Web 已提供商机跟进、报价、确认成交、结案和行动周视图；移动端拜访/新建商机/登记客诉表单与行动周视图已切换新模型。
- OpenAPI 及共享 domain 类型已重新生成/同步；旧 `AmountType`、`AdvanceOpportunityDto`、`ordered` 和多套未来日期字段不再出现在现行业务契约中。

### 数据迁移设计

- 迁移 `0006_sales-facts-and-actions.sql` 先把旧 `weekly_plan_items` 原 ID 转为手工行动，指导意见目标同步改到该行动，再删除旧表。
- 旧拜访、商机和客诉的未来日期会转换成行动；旧拜访已经自动复制出同日同客户计划项时避免再生成一条重复行动。
- 旧客诉跟进中的历史下一日期会保留为行动历史；仅与客诉当前日期一致的最新一条保持 pending，其余标为 completed。
- 旧 `ordered` 商机转换为 `won`。历史 Deal 若没有来源商机或多个 Deal 共用一个来源商机，会补建“历史成交迁移”商机，保证新的一对一约束不丢记录。
- 历史 Deal 金额为空时以 0 承接，并在备注写明“原成交金额为空”，避免伪装成已知金额；后续正式数据迁移仍应按源台账对账修正。

### 文件职责收口

- API 商机模块按职责拆为：创建/查询 `OpportunitiesService`（约 132 行）、过程命令 `OpportunityCommandsService`（约 264 行）、访问与状态规则 `OpportunityAccessService`（约 42 行）。
- Web 商机详情页约 128 行；跟进/报价/成交/结案录入集中在约 218 行的独立命令组件。自动生成的 OpenAPI 契约不纳入业务文件体量判断。
- 本批没有引入跨域“万能 Service”；行动生命周期由 `FollowUpActionsService` 统一，业务域只在自己的事务内调用。
