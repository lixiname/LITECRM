## 〇、测试是什么（先建立心智模型）

**测试 = 把「系统应该表现出的行为」写成可重复执行的断言。跑一次，系统立刻告诉你它是否遵守承诺。**

所以测试的质量由两件事决定：

1. **承诺清单是否完整**：该验证的边界（没权限？空数据？不该包含的？）都验证了吗
2. **断言是否诚实**：是走真实链路验证，还是 mock 自嗨（只证明"我的 mock 对"）

> 反模式：`it('calls the service')` —— 描述的是"代码动作"，没有意义。
> 正模式：`it('sales 越权访问用户管理被拒 403')` —— 描述的是"业务承诺"，失败一眼看出哪个承诺没兑现。

## 一、测试分层（金字塔）

```
         ▲   e2e 端到端：整机通电试运行（慢、贵、最可信）
       ▲ ▲ ▲  集成：几个零件组装后配合
     ▲ ▲ ▲ ▲ ▲  单元：逐个零件检查（快、多、便宜）
```

| 层             | 隔离程度            | 本项目例子                                                                    | 验证什么                           |
| -------------- | ------------------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| **单元测试**   | 单函数/类，隔离依赖 | `access.service.spec.ts` 测 `computeTeamVisibleIds`（纯函数，喂假数据不连库） | 逻辑本身对错                       |
| **集成测试**   | 多组件协作          | domain 的 `http.spec.ts`（mock fetch 测 401 自动刷新链路）                    | 组件间配合                         |
| **端到端 e2e** | 完整应用 + 真实依赖 | `permission-matrix.spec.ts`（真实 DB + 完整 Nest + 真实 HTTP）                | 系统整体承诺（如"服务端唯一裁决"） |

**分层选择原则**：能用纯函数单测的用单测（快），必须经过真实链路的用 e2e（真）。没有值得验证的承诺的环节可以暂时只留 smoke 占位。

**为什么权限必须 e2e 而不是单测**：规格 §6.1 承诺"服务端唯一裁决"——绕过前端直接打接口也要被拦。这个承诺只有完整链路能验证：登录（真实 bcrypt）→ 拿 token → 带 token 打接口 → Guard 裁决。mock 只能证明"我的 mock 调用对"，证明不了"真实请求被拦"。

## 二、本项目测试地图（测了哪些）

| 环节            | 文件                                                          | 测的承诺                       | 依赖环境                                       |
| --------------- | ------------------------------------------------------------- | ------------------------------ | ---------------------------------------------- |
| 纯函数/服务逻辑 | `api/src/access/access.service.spec.ts`（9 用例）             | 树推导、能力点判定、数据范围   | 无（纯 JS）                                    |
| HTTP 封装层     | `domain/src/services/__tests__/http.spec.ts`（5 用例）        | 401 自动刷新、单飞、错误规范化 | mock fetch + jsdom                             |
| Pinia store     | `domain/src/stores/__tests__/auth.spec.ts`（6 用例）          | 登录/登出/恢复会话/失效清理    | createPinia + jsdom(localStorage) + mock fetch |
| 后端完整链路    | `api/src/auth/__tests__/permission-matrix.spec.ts`（11 用例） | 4 角色快照、越权 403、树范围   | 真实 DB + 完整 Nest + supertest                |
| 前端页面        | `web`/`mobile` 各 1 个 smoke                                  | 撑起流水线（业务组件测试暂缺） | jsdom + @vue/test-utils（已装未用）            |

> **规律：测哪些 = 哪个环节有值得验证的承诺。** 每个测试文件的 `it()` 描述就是该环节的承诺清单。

## 三、工具链全景（用什么测）

| 工具                    | 职责                                                                                   | 管哪个环节                                         |
| ----------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------- |
| **Vitest**              | 测试运行器 + 断言（expect）+ mock（vi）+ 环境（jsdom/node），读各包 `vitest.config.ts` | 全部测试的"引擎"（前后端统一，规格决策 2 弃 Jest） |
| **supertest**           | HTTP 测试客户端，打 Nest 的**内存 server**（不占端口）                                 | 后端 e2e 的"请求发出器"                            |
| **@nestjs/testing**     | `Test.createTestingModule` 装配完整 `AppModule`                                        | 后端 e2e 的"应用装配器"                            |
| **真实 PostgreSQL**     | 数据层（本地 `litecrm-db` 容器 / CI postgres service）                                 | 后端 e2e 的"真实数据源"                            |
| **jsdom**               | 模拟浏览器环境（window/localStorage/DOM）                                              | domain + 前端测试的"环境"                          |
| **Pinia**               | `createPinia/setActivePinia` 隔离 store 实例                                           | domain store 测试的"沙箱"                          |
| **Turborepo**           | 按包编排 `test` 脚本 + 缓存                                                            | 跨包的"调度器"                                     |
| **husky + lint-staged** | pre-commit 只跑 **lint + format**（不跑测试）                                          | 提交门禁（快）                                     |
| **GitHub Actions CI**   | push/PR 时跑 `pnpm test` 全套                                                          | 远程兜底（全）                                     |

> 分工要点：**husky 拦"代码风格"（快），CI 拦"测试/类型/构建"（全）**——提交时不跑测试是为了不拖慢开发，但 CI 保证最终必测。

## 四、机制：约定优于配置（工具怎么串起来的）

**核心认知：turbo.json 只放"规则"，不放"清单"。** 清单全是运行时发现的，共四层约定：

| 层                    | 约定来源                                                          | 决定什么                                                             |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------- |
| ① 有哪些包            | `pnpm-workspace.yaml` 的 `packages: ['apps/*','packages/*']` glob | turbo 扫描目录 + 读各包 `package.json.name` → 8 个包                 |
| ② 每个包有没有某任务  | 各包 `package.json.scripts`（如 `"test": "vitest run"`）          | 有 → turbo 执行（Command = script 值）；无 → 标 `<NONEXISTENT>` 跳过 |
| ③ 哪些文件是测试      | 各包 `vitest.config.ts` 的 `include: ['src/**/*.spec.ts']`        | vitest 按 `.spec.ts` 约定扫描文件                                    |
| ④ 任务怎么跑/缓存策略 | 根 `turbo.json`（`dependsOn`/`cache`/`outputs`）                  | 只定义规则，不定义"谁跑"                                             |

**为什么之前 `turbo test` 显示 "Running test in 4 packages"**：只有 api/domain/web/mobile 四个包写了 `"test"` 脚本；contracts/design-tokens/eslint-config/tsconfig 没写所以被跳过。给某包补上 `"test"` 脚本后 turbo 自动纳入——**零编排配置**。

**缓存机制**：turbo 对每个任务的输入文件（包内源码 + 配置 + 锁文件）算 hash；输入没变 → cache hit（跳过执行，秒回）；变了 → 重新执行。测试报告/日志输出到 `.turbo/`。

### 一次 `pnpm test` 的完整流转（7 个节点）

```
你敲 pnpm test
 ① turbo 读根 turbo.json 的 task "test"，从 workspace 发现包清单（8 个）
 ② 逐个包查 scripts.test → 4 个包有，标记为待执行
 ③ 对每个包执行 test script（即 vitest run，cwd = 该包目录）
 ④ vitest 读该包 vitest.config.ts（environment + include）
 ⑤ vitest 按 include 收集 .spec.ts 文件
 ⑥ 执行每个测试文件：beforeAll(建数据/建app) → it() → afterAll(关资源)
 ⑦ 汇总报告；turbo 记录 hash 缓存（下次文件没变直接读缓存）
```

## 五、整个链路里：手写 vs 自动生成

**核心规律：写什么内容"手写"，怎么组织/怎么跑/生成物"自动"。**

| 环节          | 手写                              | 自动生成/自动计算                             |
| ------------- | --------------------------------- | --------------------------------------------- |
| 应用代码      | DTO、service、组件、store…        | —                                             |
| 契约类型      | DTO 上的 `@ApiProperty` 装饰器    | `openapi.json` + `generated/api.ts`（库生成） |
| 数据库迁移    | `schema/*.ts` 表定义              | `drizzle/*.sql`（drizzle-kit 生成）           |
| 测试文件      | `*.spec.ts` 的断言与 setup        | —                                             |
| 测试配置      | 各包 `vitest.config.ts`（写一次） | —                                             |
| 包清单        | `pnpm-workspace.yaml`（写一次）   | turbo 扫描 glob → 8 个包（自动）              |
| 任务计划      | `turbo.json` 规则（写一次）       | "哪些包有 test/跑什么命令"（自动发现）        |
| 缓存          | —                                 | 输入文件 hash（自动计算）                     |
| 测试报告/日志 | —                                 | vitest + turbo 自动输出                       |

## 六、关键技术细节（写测试时的实操）

### 1. Setup 保证可重复（每次跑结果一样）

```ts
beforeAll(async () => {
  await seedAccounts() // seed 用 onConflictDoUpdate：存在则更新、不存在则插入 → 幂等
  // ...
})
```

**测试最怕"第一次绿、第二次红"**，幂等 setup 从根上杜绝。项目 seed 见 `apps/api/scripts/seed.ts`（`pnpm db:seed`）。

### 2. 手动补生产配置（防止"测试环境 ≠ 生产环境"）

`Test.createTestingModule` 不会自动带上 `main.ts` 里的 `setGlobalPrefix('api')` 和全局 `ValidationPipe`。不补的话测试打的路径和校验行为与真实环境不一致——**测试会骗你**。所以 e2e setup 里显式补齐：

```ts
app.setGlobalPrefix('api')
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }))
```

### 3. supertest 不真占端口

`request(app.getHttpServer())` 直接打内存里的 HTTP server，不经过 TCP 监听——**既有真实 HTTP 语义，又足够快**（权限矩阵 11 个用例约 0.8s）。

### 4. 断言边界，不只断言正确路径

只测"admin 能进"是不够的，至少补三类：

- 无权限：无 token → 401、sales 访问 admin 专属接口 → 403
- 反例：该"不包含"的（如 executive 的 team 范围**不含上级**）
- 空数据：无持久化会话时保持未登录

### 5. Helper 消除噪音

把"怎么登录、怎么查 id"抽成小函数，测试主体只留业务断言，读起来像需求文档：

```ts
async function login(username: string, password: string) {
  const res = await request(app.getHttpServer())
    .post('/api/auth/login')
    .send({ username, password })
  expect(res.status).toBe(200)
  return res.body
}
```

### 6. Setup/Teardown 生命周期

- `beforeAll`：建数据、建 app（一次）
- `afterAll`：`await app.close()` 释放连接，防止测试互相污染
- 单个用例的独立数据准备用 `beforeEach`（本项目 e2e 用 seed 幂等替代）

## 七、e2e 是什么 / 什么时候用

**e2e = end-to-end（端到端）**：模拟真实客户端从入口到出口走完整流程，不 mock 任何东西——数据库是真的、HTTP 是真的、JWT 是真的、Guard 是真的。

```ts
// 真实启动：完整 Nest 应用 + 真实 PostgreSQL
const app = await Test.createTestingModule({ imports: [AppModule] }).compile()
await app.init()
// 真实 HTTP 请求（supertest）
const res = await request(app.getHttpServer()).post('/api/auth/login').send({...})
// 全程真实链路：bcrypt 校验 → JWT 签发 → 带 token 打接口 → Guard 裁决
expect(res.status).toBe(200)
```

**为什么 e2e 不能到处都是**：慢（启动应用 + 连 DB）、依赖环境（必须有数据库）、失败定位难。所以用金字塔策略：大量单测保逻辑、适量集成测配合、**少量 e2e 守关键承诺**（登录、权限这类"服务端裁决"必须 e2e）。

## 八、写测试的 Checklist

1. **先列承诺**：读规格/需求，把每条"应该怎样"写下来（一个承诺一条）
2. **决定层**：纯逻辑 → 单测；跨组件 → 集成；涉及"服务端裁决/真实数据" → e2e
3. **写 Setup 保证幂等**：跑 2 次结果必须一样
4. **写断言**：`it()` 描述 = 一句人话承诺；断言写"行为"不写"实现"
5. **补边界**：至少问三个问题——没权限呢？空数据呢？不该包含的呢？
6. **跑两遍验证幂等**：第一遍建数据，第二遍复用数据，结果都绿
7. **让测试能"报警"**：故意改错一条断言，确认测试会红（mutation 自查，确保测试不是摆设）

## 九、常用命令速查

| 命令                             | 作用                                                         |
| -------------------------------- | ------------------------------------------------------------ |
| `pnpm test`                      | turbo 编排，跑全部有 test 脚本的包                           |
| `pnpm --filter @crm/api test`    | 只跑 api 包测试                                              |
| `pnpm --filter @crm/domain test` | 只跑 domain 包测试                                           |
| `pnpm exec turbo run test --dry` | 只看测试计划（不执行），理解"发现机制"用                     |
| `pnpm db:seed`                   | 幂等初始化 5 个账号（admin/manager/sales1/sales2/assistant） |

## 十、环境要求

- **后端 e2e 测试依赖真实 DB**：本地需 `docker compose up -d db`（或 CI postgres service）；测试 `beforeAll` 会自动幂等 seed，无需手动准备
- **前端/domain 测试**：无外部依赖（jsdom + mock fetch）
- **提交门禁**：husky pre-commit 只跑 lint-staged（lint+format）；测试在 CI 全量执行
