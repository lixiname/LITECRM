# Lite CRM 测试速查（实战向）

> [!TIP]
> **实战优先**：主线 = 照着做就能写测试。标 ⬇️ 折叠或 `进阶` 的是原理内容，**第一遍跳过不影响**。
> 范本：单测 `apps/api/src/access/access.service.spec.ts` · 集成 `packages/domain/src/services/__tests__/http.spec.ts` · e2e `apps/api/src/auth/__tests__/permission-matrix.spec.ts`

---

## 一、核心模型（3 句记住）

1. **测试 = 把规格承诺翻译成可自动执行的断言。** `it('sales 越权访问用户管理被拒 403')` 就是一句承诺。
2. **金字塔**：单元（多·快）→ 集成 → e2e（少·真）。能用单测别上 e2e。
3. **测哪些 = 有承诺的环节**。没承诺的环节用 smoke 占位即可。

## 三、工具链速查（谁干什么）

| 工具                | 管什么                                                           |
| ------------------- | ---------------------------------------------------------------- |
| **Vitest**          | 全部测试的引擎（运行/断言/mock/环境），读各包 `vitest.config.ts` |
| **supertest**       | 后端 e2e 发真实 HTTP 请求（打内存 server，不占端口）             |
| **@nestjs/testing** | 在测试里装配完整 Nest 应用                                       |
| **jsdom**           | 给前端/domain 测试模拟浏览器（localStorage/window）              |
| **Turborepo**       | 跨包编排 `test` 脚本 + 缓存                                      |
| **husky + CI**      | husky 只拦代码风格；**测试由 CI 全量跑**                         |

## 四、写测试五步法（反复训练用）

1. **列承诺**：读规格/需求，一条承诺 = 一个 `it()`
2. **选层**：纯逻辑 → 单测；跨组件 → 集成；服务端裁决/真实数据 → e2e
3. **幂等 setup**：跑两遍结果一致（seed 用 `onConflictDoUpdate`，见 `scripts/seed.ts`）
4. **写断言**：描述**行为**不描述实现；补三类边界——没权限？空数据？不该包含的？
5. **验证**：跑两遍 + **故意改错一条断言确认会红**（防止测试是摆设）

> [!NOTE] `it()` 文案即承诺：`❌ it('calls the service')` → `✅ it('sales 越权被拒 403')`

## 五、后端 e2e 模板（照抄改）

```ts
beforeAll(async () => {
  await seedAccounts() // 幂等造数（脚本共享）
  const app = await Test.createTestingModule({ imports: [AppModule] }).compile()
  app.setGlobalPrefix('api') // ← 必须手动补生产配置
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }))
  await app.init()
})
afterAll(async () => {
  await app.close()
})

async function login(username: string, password: string) {
  // helper 抽离
  const res = await request(app.getHttpServer())
    .post('/api/auth/login')
    .send({ username, password })
  expect(res.status).toBe(200)
  return res.body
}

it('sales 越权访问 /users 被拒 403', async () => {
  const sales = await login('sales1', 'Crm@123456')
  const res = await request(app.getHttpServer())
    .get('/api/users')
    .set('Authorization', `Bearer ${sales.accessToken}`)
  expect(res.status).toBe(403)
})
```

<details>
<summary>⬇️ 进阶：理解「为什么」（第一遍跳过，有兴致再读）</summary>

### A. 约定优于配置：工具怎么发现彼此

**turbo.json 只放"规则"（dependsOn/cache），不放"清单"**——清单全是运行时发现的：

| 层               | 约定来源                                                     | 决定什么                                                       |
| ---------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| 有哪些包         | `pnpm-workspace.yaml` 的 `packages: ['apps/*','packages/*']` | turbo 扫描 glob → 8 个包                                       |
| 每包有没有某任务 | 各包 `package.json.scripts`                                  | 有 → 执行（Command = script 值）；无 → 标 `<NONEXISTENT>` 跳过 |
| 哪些文件是测试   | 各包 `vitest.config.ts` 的 `include: ['src/**/*.spec.ts']`   | vitest 按 `.spec.ts` 约定扫描                                  |
| 任务规则         | 根 `turbo.json`                                              | 只定义"怎么跑"，不定义"谁跑"                                   |

**推论**：给某包补上 `"test"` 脚本，turbo 下次自动纳入，零编排配置。

### B. 手写 vs 自动生成

**写什么内容手写，怎么组织/怎么跑/生成物自动。**

| 手写                                                                     | 自动                                                                                           |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 应用代码、测试文件、各包 vitest.config、workspace/turbo 规则（各写一次） | 契约类型（openapi-typescript）、迁移 SQL（drizzle-kit）、包清单、任务计划、缓存 hash、测试报告 |

### C. e2e 什么时候非它不可

**涉及"服务端唯一裁决"的承诺必须 e2e**：登录/越权/权限这类"绕过前端也要被拦"的语义，mock 证明不了。慢 + 依赖真实 DB，所以只在关键路径用。

### D. 缓存机制（turbo hash）

turbo 对任务输入文件算 hash；输入没变 → cache hit（秒回），变了 → 重跑。所以**改了源码再跑 test 是增量执行**，没改的包直接命中缓存。

### E. 为什么前后端统一 Vitest（规格决策 2）

弃 Jest 避免 `jest-resolve → unrs-resolver` 原生构建脚本（Windows/pnpm 供应链安全）；顺带 pnpm approve-builds 警告消失。

</details>

## 附：环境要求

- **后端 e2e 依赖真实 DB**：本地 `docker compose up -d db`（或 CI postgres service）；`beforeAll` 自动幂等 seed，无需手动准备
- **前端/domain 测试**：无外部依赖（jsdom + mock fetch）
- **提交门禁**：husky pre-commit 只跑 lint+format；测试在 CI 全量执行
