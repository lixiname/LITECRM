## 一、项目定位

**面向小团队、线下拜访型 B2B 销售的轻量 CRM**：销售外勤用移动端记录客户动态、拜访、商机与客诉；每次有效互动形成可执行的下一步行动；商机下的口头报价与正式报价持续留痕，客户明确下单后才形成成交事实。先形成「客户 → 互动 → 行动 → 商机 → 报价 → 成交」可信主链，再由管理视图消费这些事实。

| 优先级 | 领域                                                                 |
| ------ | -------------------------------------------------------------------- |
| P0     | 移动端记录与下一步行动（拜访/商机「顺手、快、记录后可继续推进」）    |
| P1     | 可信商机（跟进、口头报价、正式报价、成交边界清楚，长期无动作可识别） |
| P2     | 客户分级与分级名额（支撑客户结构优化；产品分级另建产品主数据）       |
| P3     | 管理视图（销售漏斗/转化/储备等只读聚合，不反向污染事实模型）         |

**规模口径**：销售约 20 人，另有区域管理人员和多位业助；客户与业务记录为中小企业量级。单台普通服务器足够，**正确性、可维护性与低录入负担优先于性能优化**。

**环境（已确认）**：

- 桌面浏览器：Chrome + Edge
- 移动浏览器：Android 常规浏览器为主 + 少量 iOS Safari；钉钉内 WebView
- 部署：腾讯云 Linux 云服务器（单台 2C4G）；域名 + IP 已有（**ICP 备案待办**）
- 账号：初期账号密码；后期钉钉免登
- 双端访问：同域名不同路径 `/`（桌面）+ `/mobile/`（移动），入口按 UA 自动跳转，钉钉微应用 URL 配 `/mobile/`

## 三、仓库结构

> 架构模式：分层架构——表现层（apps/web、apps/mobile）/ 应用层（api 的 service）/ 领域层（packages/domain）/ 基础设施层（Drizzle、PG）。依赖方向：表现→应用→领域，基础设施依赖领域层（依赖倒置），禁止跨层调用。

```
crm/
  apps/
    web/                      # 桌面端：管理后台全集（Element Plus）
      src/pages/  src/features/  src/router/  src/theme/
    mobile/                   # 移动端 H5：填报子集（Vant）
      src/pages/  src/features/  src/router/  src/theme/
    api/                      # NestJS + Drizzle
      src/
        access/ auth/ org/ audit/ catalog/ customers/ claims/
        activities/ opportunities/ complaints/ planning/ expenses/
        team/ reporting/ ai/ alerts/ common/
  packages/
    contracts/                # openapi-typescript 生成契约（只含生成物 + 少量补充类型）
    domain/                   # 两端共享业务层
      services/               #   API 薄 client（基于生成契约）
      stores/                 #   Pinia（session/角标/周上下文）
      composables/            #   useQuery、格式化、权限判断
      types/                  #   非 API 领域类型
    design-tokens/            # 双端统一主题变量
    eslint-config/  tsconfig/
  docs/                       # adr/、milestones/
  pnpm-workspace.yaml
```

**硬性约束**：

- 后端是唯一事实源：DTO → Swagger → 契约 → 前端，单向下发
- domain 层唯一：API 调用、状态、权限判断、校验规则只在 packages/domain，两端 import，禁止复制
- 页面禁止直接 fetch / 拼 URL，一律走 domain/services
- 枚举单源：一律 import 契约枚举，禁止手写字符串字面量
- UI 库只管外观层，业务逻辑零重复

## 四、核心决策

| #   | 决策         | 结论                                                                                                                       |
| --- | ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 1   | 产品边界     | 独立设计 CRM，不与 OGSM/OKR 合并                                                                                           |
| 2   | 双端形态     | 桌面 Web 管理后台 + 移动 H5（浏览器/后期钉钉内嵌），不做原生                                                               |
| 3   | 前端技术栈   | Vue 3 + TS；桌面 Element Plus、移动 Vant；monorepo 双入口共享 domain                                                       |
| 4   | 数据获取     | Pinia + 手写 useQuery（接口对齐 TanStack Query 预留升级口）                                                                |
| 5   | 前后端契约   | openapi-typescript 生成类型 + 手写薄 client + CI 校验无 diff；前端禁手写枚举字面量，非 API 类型留 domain 层                |
| 6   | 数据层       | Drizzle，synchronize 退役，迁移驱动                                                                                        |
| 7   | 旧库数据     | 原型数据首版不迁，模型稳定并完成业务验证后再 ETL；权威主数据对账，缺失的历史报价/行动不得臆造                              |
| 8   | 里程碑       | M0–M9（见第十一章）                                                                                                        |
| 9   | 权限模型     | 混合访问控制：RBAC 管操作（能力点）× 组织树管数据范围，服务端唯一裁决；角色 4 类（见 6.2）                                 |
| 10  | AI 能力预留  | ai/ 模块两域（intake 录入 + insight 分析），叠加通道不碰事实层；M0-M7 只留 schema 与模块位，M8 insight → M9 intake         |
| 11  | 客户查重检索 | 客户编码/信用代码硬唯一；归一化名称、电话、地址等只做疑似重复识别，不以商号归一化结果直接判定法定主体（见 7.3）            |
| 12  | 跨模块联动   | 强一致=直接调用+同事务；弱一致=@nestjs/event-emitter 进程内事件；不引消息队列（见 6.4）                                    |
| 13  | 销售计划源   | 未来计划独立建模且带明确业务类型；拜访/商机/客诉领域命令完成原计划并生成下一计划，周视图只做查询投影                       |
| 14  | 报价与成交   | 一个商机可有 0..N 次口头报价和 0..N 次正式报价；报价不等于成交，客户明确下单才生成 Deal                                    |
| 15  | 分级名额     | S/A/B/C 只表示客户等级；名额按「负责人 × 客户等级」约束，不再设置同名的销售容量等级                                        |
| 16  | 并发与时间   | 可变聚合由应用层统一维护 updated_at/version，并以条件更新防止覆盖；数据库负责 FK/UQ/CHECK，不用触发器承载业务流程          |
| 17  | 客户活动投影 | 拜访/跟进/报价/客诉/成交表是事实源；客户最近活动与时间线是可重建读模型，由写入事实的同一应用事务维护，不另建第二套动态事实 |

### 5.2 前端分层

> 模式：前端分层架构——页面编排层（pages，只做组装）/ 领域组件层（features）/ 基础设施层（libs）。

```
pages/          # 路由页面，只做编排（单组件 ≤ 400 行）
features/       # 领域组件 + 领域 composable（每业务域一个目录）
libs/           # api（传输层）/ query（useQuery）/ auth（Pinia store）/ ui（共享组件）
```

### 5.3 数据获取（useQuery）

> 模式：Repository 模式——页面不直接访问数据源，经 domain/services（repository 抽象）获取；useQuery 是缓存/加载封装。

```ts
// packages/domain/src/composables/useQuery.ts
// 接口对齐 TanStack Query：useQuery({ key, fetcher, options })；约 40 行
// 暴露 data / loading / error / reload() / setData()

const { data, loading, reload } = useQuery(`customers:list:${filters}`, () =>
  listCustomers(filters),
)
// 写操作后：reload() 或 setData()，不整页刷新
```

- 跨页共享状态（session/权限快照/角标/业务周）走 Pinia stores

### 5.4 重合功能 schema 共享（防双端表单漂移）

- domain 层定义字段配置（字段名/类型/必填/选项/校验/提交字段），桌面与移动表单组件读取同一份配置渲染
- 改字段只改 domain 一份，双端同时生效
- 主链路 e2e 双端各跑一遍，重合功能行为一致

### 5.5 应用外壳与导航（App Shell）

> 原则：**产品是「软件」不是「功能演示页」**——所有页面必须承载于统一应用外壳（侧边栏/顶栏 或 底部 Tabbar），导航即信息架构。

- **web（桌面管理后台）**：标准侧边栏 Layout——Logo + 一级导航（客户 / 商机 / 客诉 / 行动 / 费用）+ 系统管理区（接管审批 / 字典配置 / 用户管理）+ 顶栏（当前页标题 / 用户菜单 / 退出）
- **mobile（H5）**：底部 Tabbar（客户 / 快速记一笔 / 我的）；填报入口优先（规格 5.1 分配）
- **导航权限**：菜单项按能力点控制（`hasAbility`），与路由守卫同源；无权限的入口不渲染
- **落地页**：登录成功后 web 进「客户列表」（业务主入口），mobile 进「客户」；不设无意义的按钮堆首页

### 5.6 页面设计规范

- **页面结构**：`PageHeader（标题 + 操作区）` + 内容区（列表 / 表单 / 详情），三区职责固定
- **三态统一**：加载中 / 空状态 / 错误态 用共享组件，禁止各页零散手写
- **样式唯一来源**：布局与间距一律走 design-tokens（红线 16 延伸）；组件内不散落硬编码色值/间距
- **一致性**：同类型页面（列表/表单/详情）结构对齐；按钮语义统一（主操作主色、危险操作红色、次要操作灰）

## 六、后端规格

### 6.1 权限模型

> 参考：PDP/PEP——Guard 为策略执行点（PEP），统一权限服务为策略决策点（PDP），决策集中一处。

权限是贯穿所有业务模块的横切基础设施，由三个正交组件构成：

```
┌────────────────┐   ┌────────────────┐   ┌────────────────┐
│ 身份 Identity   │   │ 组织 Organization│   │ 授权 Authorization│
│ 我是谁？        │   │ 我属于哪个树？   │   │ 我能做什么/看什么？ │
│ (登录/JWT)     │   │ (reportsToId)  │   │ (能力点×数据范围)  │
└───────┬────────┘   └───────┬────────┘   └───────┬────────┘
        └────────────────────┼────────────────────┘
                             ▼
                   业务模块（查询/写操作必经横切）
```

- **三组件解耦**：登录不关心你有几个下属；组织树不管你会不会「导出」；授权只问「这个操作+这批数据，对你放行吗」
- **授权是唯一决策点**：「能做什么」由 Guard 统一裁决（能力点）；「能看什么」由统一权限服务在查询层过滤（数据范围）
- **服务端唯一决策**：前端只消费登录返回的权限快照（capabilities + dataScope），绕过前端的 API 调用同样被拦
- **审计独立**：「谁做了什么」是另一条横切链，与授权正交但依赖身份

**访问控制模式：混合式（RBAC × 组织树）**

| 模式                                     | 判断                             |
| ---------------------------------------- | -------------------------------- |
| 纯 RBAC（角色→权限）                     | 表达不了「看下属的」树形数据范围 |
| 纯 ABAC（属性→策略）                     | 策略引擎对小团队是负资产         |
| **混合：RBAC 管操作 + 组织树管数据范围** | **选定**——管理后台最常见形态     |

**数据范围（组织树自动推导）**：self（本人）/ team（本人+直属下属递归）/ full（全量）；admin/assistant 短路为 full；所有列表/搜索/看板查询统一 `WHERE owner_id IN (可见集合)`；region 是数据属性，不进权限模型

### 6.2 角色模型（4 类 = 能力组合）

| 角色             | 数据范围（树自动）    | 基础填报 | 管理操作    | 经营看板 | 全量统计/导出 | 系统配置 |
| ---------------- | --------------------- | -------- | ----------- | -------- | ------------- | -------- |
| sales 销售       | self / team           | ✅       | 有下属时 ✅ | ❌       | ❌            | ❌       |
| executive 经营层 | team（总经理=全公司） | ✅       | ✅          | ✅       | ❌            | ❌       |
| assistant 业助   | full                  | ❌       | ❌          | ✅ 只读  | ✅            | ❌       |
| admin 管理员     | full                  | 可选     | ✅          | ✅       | ✅            | ✅       |

- 用户 = 1 个角色 + reportsToId（上级）；管理层级完全由树决定，不设独立角色
- 销售线角色（sales/executive）默认具备填报；**经营看板仅 executive（方案 A）**
- assistant = 全量只读 + 统计确认的数据质量负责人（AI 统计的确认人，能力位预留）

### 6.3 后端模块清单

> 模式：模块化分层——每域 module/controller/service；业务模块依赖基础设施（access/auth/audit/common），禁止反向；业务模块间经服务接口或事件协作。

```
src/
  access/        # 组织范围权限（横切基础设施，收敛可见性计算）
  auth/          # 登录（password + dingtalk provider 抽象）/JWT/改密
  org/           # 用户、角色、汇报树、区域
  audit/         # 审计日志
  catalog/       # 客户维度配置（产业/应用/类型/产品线/来源）
  customers/     # 客户档案、联系人、验重、归属、移交、公海
  claims/        # 接管认领审批流
  activities/    # 拜访 + 销售日志聚合（查询面）
  opportunities/ # 商机查询 + 过程命令 + 跟进记录 + 口头/正式报价 + 成交 Deal
  complaints/    # 客诉 + 跟进事件
  follow-up-actions/ # 下一步行动唯一写模型 + 行动生命周期
  planning/      # 业务周视图 + 周摘要 + 指导意见
  expenses/      # 费用 + 作废
  team/          # 团队执行/费用/风险看板（只读聚合）
  reporting/     # 管理看板（经营三件套首批：漏斗/储备预测/转化率归因；趋势/结构后置，只读聚合）
  ai/            # AI 能力（intake 录入侧 + insight 分析侧；M8+ 实现，预留模块位）
  alerts/        # 提醒（定时扫描 + 站内）
  common/        # 基础 schema/枚举/过滤器
```

约束：业务服务禁止自行遍历组织树算权限，一律走统一权限服务；每接口必配 class-validator DTO。

### 6.4 跨模块联动

> 模式：本地事件（In-process Events）+ Unit of Work——强一致联动同一 UoW 提交；弱一致发布订阅。

- **强一致（直接调用 + 同一事务）**：拜访/商机推进/客诉跟进→产生或更新下一步行动；明确下单→生成唯一 Deal；接管批准→客户归属与未完成行动交接；新增业务事实→推进 `customers.last_activity_at` 等客户活动投影
- **弱一致（@nestjs/event-emitter 进程内事件）**：商机推进→提醒、客诉登记→风险告警；失败不阻塞主流程
- 不引消息队列/事件总线

### 6.5 安全基线

| 项        | 方案                                                   |
| --------- | ------------------------------------------------------ |
| 登录凭证  | access token 2h + refresh token 14d 无感刷新           |
| 防爆破    | 同一账号连续 5 次密码错误锁定 15 分钟（按账号）        |
| 敏感字段  | 手机号等列表脱敏（138****1234），详情页/有权限者见全号 |
| 改密/停用 | 已签发 token 立即失效（token 版本号校验）              |

## 七、数据模型

### 7.1 schema 原则

> 领域建模模式：事件日志 + 状态快照——历史事实只追加、主表保存当前状态；下一步行动是独立可变实体；聚合根封装不变量；命令与查询分离。这里不是完整 Event Sourcing，业务主表仍是权威当前状态。

- **可变聚合**：id（UUID）+ createdAt + updatedAt + version；应用层统一执行 `updated_at=now(), version=version+1`，并以 `WHERE id=? AND version=?` 条件更新，冲突返回 409
- **只追加事实/事件**：id + createdAt + occurredAt（按需）；不设置无意义的 updatedAt/version，禁止覆盖商业历史
- **数据库职责**：外键、唯一约束、CHECK 约束和事务完整性；不使用触发器或存储过程承载商机推进、客户移交等业务流程
- **当前开发期数据策略**：本地库仅承载测试/演示数据，模型正确性优先于历史测试数据兼容；字段语义或关系设计需要调整时，允许使用破坏性迁移、清库重建或重新 seed，不为测试数据保留错误字段和长期兼容层。正式数据首次导入前必须明确冻结迁移边界；进入正式数据阶段后切换为备份、可回滚、可对账的保守迁移策略
- 关系查询按需声明（with），默认高效 join，防 N+1
- 枚举/状态统一 **varchar + CHECK 约束 + 应用层枚举**（不用 PG enum——避免 ALTER TYPE 迁移坑）；users 表预留 phone（钉钉绑定）
- **AI 预留**：业务记录带 `entry_source`（manual/voice/image/chat/ai）+ `entry_ref_id`（原始素材引用）；预留 `ai_drafts` 草稿确认通道（AI 永不直接写业务数据，先草稿→人工确认→落库）；结构化优先，自由文本受控；指标口径单一来源；pg_trgm 现在上，pgvector M8 时装扩展 + 独立向量表（customer_embeddings，业务表不存向量）

### 数据模型 ER 图（Mermaid）

> 颜色约定：🟢 实体表（主数据/业务对象）｜🟠 关系表（明细/事件/流水）。

> 设计约定：① 字典字段（industry/sub_industry/customer_type/source/product_lines）保存**稳定字典值**，展示时读取字典 `label`；其中 industry=客户行业、sub_industry=具体领域，二者是正交业务维度而非父子分类；展示名可调整，稳定值创建后不直接修改，停用项仍用于解析历史数据；② 多态引用（management_comments/alerts/audit_logs）为**弱引用**，写路径必须校验目标存在；③ 派生字段（first_visited_at 等）由应用层投影器在业务事实同一事务内维护，并可从事实表重算；不使用数据库触发器，不把派生值反向当作事实源。
> 设计约定（区域模型）：省/地级市使用独立行政区划参考表并保存稳定代码；销售大区属于业务辖区，通过 sales_region_areas 映射行政区。客户选择省市后自动解析 sales_region_id，城市映射优先于省映射，未命中时保持为空；行政区划和销售大区不得复用普通业务字典。
> 设计约定（功能边界）：① 费用=轻量统计（draft/submitted/voided 服务统计口径），无审批流，报销单据查验/审批打款排除在 CRM 边界外；② 拜访、商机推进和客诉跟进记录已经发生的事实，并在同一事务中完成旧行动、创建或调整下一步行动；③ 周视图以 follow_up_actions 为唯一计划源，并按发生时间聚合各领域事实，禁止复制计划日期和行动文字。
> 设计约定（必填标注）：字段级 `?` = 数据库层可空；记录级条件必填（如「至少一个联系人电话」）用备注/应用层约束表达，不反映在字段级。
> 设计约定（归属语义）：归属单一事实源在 customers.owner_id（当前归属）；子实体（商机/客诉/拜访/跟进）的 owner_id = **创建时归属快照**（不可变，历史回溯用），当前归属一律 JOIN 客户推导——归属变更只改客户，子实体自动跟随且历史保留。
> 设计约定（选项字典化）：**业务描述性分类进字典（customer_dimension_options，admin 可配置）**——客户维度 5 类 + complaint_type/trade_type/opportunity_source/visit_type；**状态机与权限不进字典**（stage/status/role/ability 保持代码枚举，避免配置与运行逻辑脱节）。字典 `name` 保存稳定 key，`label` 保存展示名称；Web 与移动端均从 catalog API 读取选项和显示文案，不维护前端硬编码副本。录入时应用层校验稳定值存在且启用；读取接口保留停用项，以便历史记录继续解析。

### 7.3 检索与查重

> 检索模式：三阶段检索（Exact 精确 → Fuzzy 模糊 → Vector 向量），各层职责边界清晰。

| 层     | 方案                                              | 时机 |
| ------ | ------------------------------------------------- | ---- |
| 精确层 | 客户编码/信用代码唯一索引（法定或权威标识硬拦截） | M2   |
| 模糊层 | pg_trgm 相似度查重 + GIN 索引加速检索             | M2   |
| AI 层  | pgvector embedding 变体识别                       | M8+  |

- **查重判定**：信用代码或 ERP 客户编码相同 → 硬拦截；归一化名称完全相等、别名/简称、电话、地址或 trigram 相似 → 提示疑似重复。高置信命中仍允许在明确确认后继续建档，确认动作与理由留审计
- **归一化**：去空格/统一大小写/去「有限公司/集团」等后缀，只用于候选生成、相似度比较和检索排序；`normalized_key` 建 GIN/普通索引但**不得唯一**，不能替代法定主体标识
- **检索排序**：完全匹配 > 前缀匹配 > 包含匹配 > 别名命中 > trigram 相似度兜底；输入即搜（防抖 300ms）
- **权限边界**：查重/搜索可命中权限外客户，但只返回最小标识（名称+城市）；详情必须走权限校验
- **迁移**：drizzle-kit 生成 SQL 迁移提交进仓库；CI 校验生成物无 diff

### 8.1 登录与身份

#### 时序流程（账号密码通道）

```mermaid
sequenceDiagram
    participant C as 前端
    participant S as AuthService
    participant U as users表
    C->>S: POST /auth/login (username, password)
    S->>U: 查用户（含锁定状态）
    U-->>S: user
    S->>S: 校验 locked_until / bcrypt 比对
    alt 密码错误
        S->>U: 失败计数+1（达5次→locked_until=now+15min）
        S-->>C: 401 账号或密码错误
    else 密码正确
        S->>U: 清失败计数 + 更新 last_login_at/ip
        S->>S: 签发 access(2h)+refresh(14d,滑动) + 权限快照
        S-->>C: access / refresh / user / 权限快照
    end
```

#### 关键规则

| 规则       | 内容                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------- |
| 防爆破     | 连续 5 次密码错误 → locked_until = now+15min；锁定期内拒绝（按账号）                      |
| 凭证       | access 2h + refresh 14d（JWT 无状态，**滑动续期**）                                       |
| token 失效 | JWT 携带 token_version；改密/停用 users.token_version+1 → 全部旧 token 失效（含 refresh） |
| 权限快照   | 登录响应带 capabilities + dataScope（dataScope 由组织树当次推导）                         |
| 登出       | 前端清理本地 token；服务端无撤销（改密/停用靠 token_version 兜底）                        |

#### 钉钉免登（M6）

- auth provider 抽象：password / dingtalk 两通道（/auth/login + /auth/dingtalk）
- 钉钉：dd.getAuthCode → 后端换身份（手机号匹配 users.phone）→ 复用同一签发逻辑
- 共用：签发、token_version、权限快照逻辑

#### 数据读写

| 操作     | 表       | 说明                                                             |
| -------- | -------- | ---------------------------------------------------------------- |
| 登录校验 | users 读 | username/password_hash/role/is_active/token_version/locked_until |
| 登录成功 | users 写 | last_login_at/ip、清失败计数                                     |
| 登录失败 | users 写 | 失败计数、锁定时间                                               |
| 改密     | users 写 | password_hash + token_version+1                                  |

#### 改密码（本人）

```mermaid
sequenceDiagram
    participant C as 前端
    participant S as AuthService
    participant U as users表
    C->>S: POST /auth/change-password (old, new)
    S->>U: 查用户
    S->>S: bcrypt 比对旧密码
    alt 旧密码错误
        S-->>C: 400 旧密码错误
    else 旧密码正确
        S->>S: 校验新密码强度（≥8 位）
        S->>U: 更新 password_hash + token_version+1
        S-->>C: 成功 → 前端清 token → 重新登录
    end
```

规则：旧密码 bcrypt 校验；新密码 ≥8 位；改密后 token_version+1 → 全部 token（含 refresh）立即失效，所有设备重新登录。

#### 重置密码（管理员）

```mermaid
sequenceDiagram
    participant A as admin
    participant S as UsersService
    participant U as users表
    A->>S: POST /users/:id/reset-password
    S->>S: 校验 admin（user.manage）
    S->>U: 生成随机临时密码 → 更新 password_hash + token_version+1
    S-->>A: 返回临时密码（仅此一次展示）
    A->>U: 线下告知用户 → 用其登录
```

规则：仅 admin（user.manage）；生成随机临时密码（不手填）；重置 token_version+1 → 该用户全端失效；不做自助找回、不做强制改密（保持简单）。

#### 多端登录

- 允许一账号多端（手机+电脑）同时在线——外勤常态；不做单端互斥
- 安全性由 token_version 兜底（改密/重置 → 全端失效）
- 数据模型无新增字段；未来若需强制改密加 must_change_password（当前不做）

> 推敲补充：users 加 login_failed_count + locked_until（防爆破状态持久化，已入 ER 图）。

### 8.2 客户录入与查重

#### 必填策略

| 字段          | 策略                     | 说明                                                            |
| ------------- | ------------------------ | --------------------------------------------------------------- |
| name          | 必填                     | 可地址式名称（园区客户填「XX工业园3栋2楼」）                    |
| 联系人电话    | 必填（至少一个，可无名） | 电话统一挂联系人（main_phone 已废弃）；无名联系人承担「裸电话」 |
| address       | 软建议                   | 园区客户自然要填                                                |
| 信用代码/编码 | 可选                     | 有则权威硬查重                                                  |

#### 查重管道（五步）

```mermaid
flowchart TD
    A[录入名称/地址/电话] --> B[① 清洗归一化<br/>名称→normalized_key 地址→去量词 电话→去符号 pinyin-pro生成拼音]
    B --> C[② 权威标识硬拦截<br/>ERP客户编码 信用代码]
    C -->|命中| D[409 已存在 硬拦]
    C -->|未命中| E[③ 候选生成 Blocking<br/>同园区名 同电话 同商号首字]
    E --> F[④ 相似度比较<br/>natural Jaro-Winkler pg_trgm pinyin同音字 电话精确]
    F --> G[⑤ 置信度分级 高中低]
    G --> H[前端弹疑似列表 + 继续新建 + 申请接管]
```

#### 主次通道与库组合

| 通道         | 字段                 | 保证       | 实现                                                 |
| ------------ | -------------------- | ---------- | ---------------------------------------------------- |
| 名称（主）   | name                 | 必填       | natural(Jaro-Winkler) + pg_trgm + pinyin-pro(同音字) |
| 电话（主）   | contacts.phone       | 至少一必填 | 归一化后精确                                         |
| 地址（增强） | address              | 软建议     | pg_trgm                                              |
| 权威（硬拦） | ERP客户编码/信用代码 | 可选       | 唯一索引                                             |
| 名称（软判） | normalized_key       | 自动生成   | 精确/相似命中均进入疑似列表，不设唯一                |

#### 缺失处理

- 通道「有则参与，无则跳过」——字段缺失不拖累其他通道
- 唯一约束对 NULL 天然放行（没填信用代码的互不误拦）
- 置信度只按参与通道计算
- 口语名 + 无地址无电话 → 软提示「信息不完整，可能无法识别重复」（不拦截）

#### 置信度分级

| 置信度 | 命中条件                                                        | 前端                                           |
| ------ | --------------------------------------------------------------- | ---------------------------------------------- |
| 高     | 归一化名称精确 / 地址归一化精确 / 拼音相同且字数相同 / 电话精确 | 醒目提示 + 查看/申请接管；明确确认后可继续建档 |
| 中     | trigram ≥0.5 / Jaro-Winkler ≥0.8                                | 普通提示                                       |
| 低     | 弱相似                                                          | 弱提示                                         |

#### 检索

- 输入即搜（防抖 300ms）：完全 > 前缀 > 包含 > 别名 > trigram 兜底
- 权限过滤：owner_id IN (可见集合)（与查重的全库不同）
- 结果：名称 + 城市 + 负责人 + 等级

#### 批量查重（M7 后）

- 全库跑同管道 → 聚类（传递闭包）→ 疑似重复报告 → 业助处理

#### 权限边界

- 查重/搜索可命中权限外客户，但只返回最小标识（名称+城市）；点击详情走权限
- 命中权限外客户 → 前端显示「已有归属 · 申请接管」

### 8.3 客户归属治理（Ownership Governance）

#### 客户分级与分级名额

- `customers.grade` 是客户当前等级，S/A/B/C 只表达客户价值/经营优先级，不表达销售人员能力等级
- 默认名额按客户等级配置；个人覆盖以 `(user_id, customer_grade)` 唯一。例如某销售最多维护 5 个 S 类、15 个 A 类客户
- 建档指定负责人、移交、认领、接管批准及客户改级时，均在同一事务内校验目标负责人对应等级的剩余名额；并发操作必须锁定相应名额配置或使用等价的条件更新，禁止“先在事务外 count、再写入”
- 客户负责人必须是在职销售或经理；候选列表与所有写接口复用同一资格规则，不能只依赖前端下拉选项限制
- 客户改级写 `customer_grade_changes`，记录原等级、新等级、原因、操作人和业务时间；当前结构看 `customers.grade`，历史变化看追加记录
- 产品分级不复用客户等级或产品线字典。需要开展产品结构管理时新增产品主数据、稳定产品编码和产品等级，并与 Open 5000 建立外部编码映射

#### 新建归属（Ownership on Create）

```mermaid
sequenceDiagram
    participant F as 前端
    participant S as CustomersService
    participant U as users表
    F->>S: POST /customers (..., ownerId?)
    alt 未传 ownerId 且建档人为在职销售/经理
        S->>S: owner_id = created_by_id（建档人）
    else 未传 ownerId 且建档人不具备归属资格
        S-->>W: 拒绝并提示选择负责人
    else 传了 ownerId（指定负责人）
        S->>U: 校验负责人为在职销售/经理 + 该客户等级剩余名额
        U-->>S: OK / 超限拒绝
    end
    S->>S: 建档（created_by_id=登记人, owner_id=归属人）
    S-->>F: 201 建档成功
```

- 数据模型：created_by_id（建档人）与 owner_id（负责人）**两个独立字段**，语义分离
- **默认策略**：销售或经理未指定负责人 → owner_id = created_by_id（录入即所有权，90% 场景零操作）；不具备客户归属资格的代录人必须指定负责人
- **指定负责人**：录入表单通过人员选择器传 owner_id（代录场景：管理员帮销售录 → 指定归属该销售），后端统一校验目标为在职销售/经理及其客户等级名额
- **应用层责任**：默认值、指定与分级名额校验均在 Service/DTO 层；客户表不保存第二套“已占名额”计数

#### 所有权转移（Ownership Transfer）

```mermaid
sequenceDiagram
    participant F as 前端
    participant S as CustomersService
    participant T as 事务 UoW
    F->>S: POST /customers/:id/transfer (toOwnerId, reason)
    S->>S: 授权（owner/管理链/admin）+ 目标负责人对应客户等级名额校验
```

**不变式（Invariant）**：历史事实（已成交/已关闭/已解决记录）所有权快照不可改写。

#### 接管申请（Ownership Claim / Takeover Request）

**状态机**

```mermaid
stateDiagram-v2

    pending --> approved : 批准（复用 changeOwner）
    pending --> rejected : 拒绝（必填意见）
    pending --> withdrawn : 申请人撤回
    approved --> [*]
```

**时序**

```mermaid
sequenceDiagram
    participant B as 申请人
    participant S as ClaimsService
    participant A as 审批人(候选池: owner/管理链/admin)
    participant N as 被通知方(owner/管理链)

    A->>S: POST /claims/:id/approve {comment?}

    S->>S: changeOwner 事务（复用）

```

**规则（图外补充）**：

- **单点审批（Single-Approver）**：候选池多人、任一批准即生效（非会签）
- **审批候选池**：当前所有权人 + 管理链 + 管理员
- **禁止自我审批**：候选池排除申请人；当前 owner 同意让出自己的客户（被接管方确认）允许
- **并发防护**：同客户仅一条 pending（唯一性）、归属快照校验（currentOwnerId）、分级名额校验和条件更新必须在同一事务中
- **超时升级（轻量）**：pending 超 7 天 → 提醒 owner + 通知管理链

#### 主动释放（Voluntary Release）

```mermaid
sequenceDiagram
    participant S as 销售(owner)
    participant C as CustomersService
    participant T as 事务 UoW
    S->>C: POST /customers/:id/release {target: pool|invalid, reason}
    C->>C: 校验（owner/管理链/admin、reason 必填）
    C->>C: 校验开放商机与未解决客诉
    alt 有开放商机或未解决客诉
        C-->>S: 409 请先结案业务或移交客户
    else 无未结业务
        C->>T: 开启事务
        C->>T: ① 客户 owner=null、status=public/invalid
        C->>T: ② 审计留痕（release + reason）
        C->>T: ③ 仅取消 pending customer_visit，系统生成取消原因
        T-->>C: 提交
        C-->>S: 成功（腾出该客户等级名额）
    end
```

**规则（图外补充）**：

- **权限**：放入公海允许 owner/管理链/admin；标记无效仅区域负责人/admin；reason 必填（审计）
- **未结业务拦截**：开放商机或未解决客诉 → 禁止释放；前端直接禁用状态变更入口并展示具体阻断项，后端保留同样的业务校验作为并发与跨端兜底；客户有明确业务责任时应移交，而不是成为无人负责客户
- **未来行动**：普通待拜访计划自动取消，原因由系统写为“客户已放入公海/客户已标记无效”；商机/客诉行动因前置拦截不会被释放动作误删；历史行动不改写
- **分级名额**：owner 所属唯一标准——释放后（owner=null）不占对应客户等级名额
- **去向**：pool（公海，他人可认领）| invalid（无效，记录保留）

#### 公共池（Public Pool）

```mermaid
sequenceDiagram
    participant S as 销售
    participant C as CustomersService
    S->>C: POST /customers/:id/claim
    C->>C: 校验（status=public、销售区域、该客户等级剩余名额）
    C->>C: owner→销售、status→active
    C-->>S: 认领成功
```

- **数据范围**：销售可检索本销售区域公海，区域负责人可查看本区域公海，管理员可查看全公司；区域未映射客户作为待治理公海可见
- **认领边界**：认领只解决归属，不强制同时填写首次行动，不新增“待安排首次行动”状态、限时提醒或专项工作台
- **无效档案**：销售日常列表不展示；区域负责人可查看本区域、管理员可查看全公司；恢复时重新指定负责人、填写原因并校验名额，恢复后 status=active
- **查重边界**：查重覆盖 active/public/invalid，跨范围仅返回已存在及状态提示，避免通过新建客户绕过公海或无效历史
- **数据库不变量**：`active ⇔ owner_id 非空`；`public/invalid ⇔ owner_id 为空`，数据库 CHECK 与应用状态机双重约束
- 池回收（Reclamation）：backlog，本期不实现

### 8.5 商机闭环（Opportunity Lifecycle）

#### 状态机

```mermaid
stateDiagram-v2

    [*] --> following : 以口头/正式报价新建
    following --> following : 记录商机推进(可含报价)
    intent --> following : 记录首次推进
    following --> won : 客户明确下单(生成Deal)
    intent --> won : 客户直接明确下单(生成Deal)
    following --> lost : 丢失
    following --> demand_disappeared : 需求消失
    intent --> lost : 丢失
    intent --> demand_disappeared : 需求消失
    won --> [*]
    lost --> [*]
    demand_disappeared --> [*]
```

> 报价不是状态终点：口头报价 0..N 次、正式报价单 0..N 次均作为商机下的追加事实。是否已正式报价可以由报价记录推导；只有“客户明确下单”才能进入 `won`。

#### 创建、推进、可选报价与成交确认

```mermaid
sequenceDiagram

    participant S as OpportunitiesService
    participant D as 事务 UoW
    C->>S: POST /opportunities (customerId, productLines[], initialAmountBasis, initialAmount, firstAction)
    S->>S: 校验（客户可维护、产品线字典、初始金额依据、第一步行动）

    opt 本次产生报价

    end
```

| 规则          | 内容                                                                                                                                     |

| 权限          | 客户可维护（owner/管理链/admin）                                                                                                         |
| 创建          | 产品线使用 0..N 关系；初始金额依据可为预估/口头报价/正式报价。商机、产品线、可选首条报价与第一步行动同事务写入                           |
| 推进          | 每次推进追加结构化结论并创建或沿用唯一下一计划；本次可选产生一条关联报价；仅从计划入口执行时以 source_plan_id 承接来源计划，或走终态命令 |

#### 商机工作台查询投影

商机工作台是读取模型，不新增“商机台账”或“停滞状态表”。服务端按客户当前归属裁剪数据范围，分页查询商机后一次性组装客户名称、客户当前负责人、最近跟进、最近报价与最早 pending 行动；`opportunities.owner_id` 仍只承担创建时责任快照。前端不得逐行请求这些上下文，也不得在浏览器自行猜测数据权限。

停滞风险按以下事实实时派生，只对 `intent/following` 生效：

- `no_pending_action`：不存在 pending 行动；
- `action_overdue`：当前 pending 行动计划时间已过；
- `inactive_30d`：商机创建、最近跟进、最近报价三者的最大业务时间距今达到 30 天；
- `expected_close_overdue`：预计成交日已过。

这些标记是查询结果，不可人工维护。筛选条件与列表标记必须使用同一套服务端规则，避免页面显示和统计口径分叉。读取模型可以返回多个原因供筛选和详情解释，但列表只选择一个首要待处理原因并显示“另有 N 项”，避免把阶段、状态和全部风险混成标签堆。

#### 与 8.3 衔接

认领/接管 → 名下开放商机按客户当前归属可见，未完成行动在事务内交接给新负责人；历史跟进、报价和成交责任快照不改写。

### 8.6 客诉闭环（Complaint Lifecycle）

#### 状态机（两态：核心管理终态，进度靠事件）

```mermaid
stateDiagram-v2
    [*] --> registered : 登记客诉
    registered --> registered : 跟进（追加处理记录并安排下一行动）
    registered --> resolved : 确认解决（写解决结果）
    resolved --> [*] : 终态（禁止任何跟进）
```

#### 时序图（登记 + 跟进/解决）

```mermaid
sequenceDiagram
    participant C as 前端
    participant S as ComplaintsService
    participant D as 事务 UoW
    C->>S: POST /complaints (customerId, type, description, firstAction)
    S->>S: 校验（客户可维护、description 和第一步行动必填）
    S->>D: 写 complaints(status=registered) + follow_up_action
    S->>D: 触发客户风险告警（异步）
    D-->>S: 提交
    S-->>C: 201 登记成功
    C->>S: POST /complaints/:id/follow-up (content, outcome, sourcePlanId?, nextAction?, resolution?)
    S->>S: 校验（已解决则拒绝、content 必填、分支规则见下）
    S->>D: 追加 complaint_follow_ups + 完成旧行动
    alt outcome=resolved（确认解决）
        S->>D: 主记录迁移 status→resolved + resolution/resolvedAt + 取消未完成行动
    else 仍需处理
        S->>D: 创建下一步 follow_up_action
    end
    D-->>S: 提交
    S-->>C: 成功
```

#### 图外规则

| 规则           | 内容                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| 权限           | 客户可维护（owner/管理链/admin）                                             |
| 登记           | description、第一步行动必填，触发客户风险告警                                |
| 跟进           | content 必填；FOLLOWED_UP → 必填下一步行动；RESOLVED → 必填解决结果          |
| 状态机单向终态 | RESOLVED 禁止任何跟进（后端拦截 + 前端置灰）                                 |
| 事件           | complaint_follow_ups 只追加（历史回溯）                                      |
| 状态单一事实源 | complaints.status（跟进事件不覆盖主状态）                                    |
| 逾期           | 派生（关联 pending 行动逾期且客诉未解决）→ 风险视图，非状态                  |
| 重开           | 不开放——解决后再有问题 = 新建客诉                                            |
| 数据模型       | complaints 当前状态 + complaint_follow_ups 历史 + follow_up_actions 未来动作 |

#### 客诉生命周期读取模型

`GET /complaints/:id` 在不新增事实表的前提下，将现有三类事实组合为统一倒序 `timeline`：当前行动形成顶部 `pending_action`（逾期时状态为 `overdue`），或由解决快照形成顶部 `resolved`；其后为 0..N 个 `follow_up` 倒序节点，客诉主表形成最底部 `registered` 节点。该投影同时提供客户名称与处理人显示名，Web 和 Mobile 只负责按节点状态渲染，不各自推断顺序和逾期语义。

`GET /complaints` 是独立的分页摘要投影：默认 20 条、最大 100 条，返回 `items/total/page/pageSize`，支持客户、状态、关键词和逾期筛选；排序在 SQL 中统一执行“未解决逾期 → 未解决 → 已解决”。列表不携带 Timeline，Web 只为当前选中记录请求详情，从而保持数据量与查询次数有界。

读取详情只要求数据范围可见；追加跟进、确认解决仍要求客户维护权限。存储层继续保持“主表当前快照 + 子表不可变历史 + 行动表未来计划”，界面不展示这些表边界。

- 8.3 释放：有未解决客诉 → 禁止释放（先处理）——即本闭环的「解决」操作
- 8.9 风险看板：未解决客诉（status=registered）→ 风险聚合

#### 首个可试用版本的确定性口径

- 当前报价池与期间转化必须分开：期末开放存量按“仅预估 / 口头报价 / 正式报价”互斥分桶；期间流量按新增商机、首次报价、首次正式报价、成交和失败结案分别统计
- 一个开放商机只贡献一个当前参考金额：最新 `active` 报价优先，无有效报价回退 estimated_amount；superseded/withdrawn 仅留历史，不进入当前池，禁止累加历次报价
- 结案赢单率唯一口径为 `won / (won + lost + demand_disappeared)`，按 selected range 内 closed_at/deal.occurred_at 统计；无结案样本返回 null
- 存量责任按 customers.owner_id 当前归属；执行过程按各事实 actor/owner；opportunities.owner_id 仍是创建时快照，禁止用于当前团队存量统计
- S/A 关注清单从未解决客诉、pending 行动逾期、开放商机无下一步/30 天无动作/预计成交逾期及客户 30 天无活动实时派生；首版不增加全局关注字段
- 费用只聚合 submitted，draft 只报未提交数量，voided 剔除；销售目标、阶段概率、ERP 订单/出货/应收/回款均不在首版确定性指标中
- reporting 使用服务端批量查询与内存/SQL 聚合，不向浏览器下发全量事实后计算；约 20 人规模暂不引缓存、物化视图或数据仓库，达到真实数据量后再用 EXPLAIN 决定索引
- 所有时间戳按 UTC+8 业务日归属，查询表达式不得依赖数据库会话默认时区；date 类型保持自然日语义

## 九、集成与部署

> 架构模式：标准 Web 部署——Nginx（反向代理 + 静态资源 + HTTPS 终结）+ 应用服务（PM2 守护）+ 关系型数据库（PG）。

### 9.1 钉钉集成（M1 抽象 / M6 实现）

- **auth provider 抽象**：password（桌面/移动浏览器）+ dingtalk（钉钉内）；前端按 UA 检测钉钉环境决定登录方式
- **免登流程**：钉钉内 H5 → `dd.getAuthCode` → 后端调钉钉开放平台换身份（手机号/工号）→ 匹配 users 表 → 签发本系统 JWT
- **schema**：users.phone；登录双通道 `POST /auth/login` 与 `POST /auth/dingtalk`
- **前提**：域名完成 ICP 备案 + HTTPS（备案待办，1-2 周流程）

### 9.2 部署架构

```
腾讯云 Linux 服务器（单台 2C4G）
├── Nginx            # 唯一对外入口（443 HTTPS）+ 双端静态资源 + /api 反向代理 + UA 分流
├── Node 服务        # NestJS，PM2 守护（127.0.0.1:3001）
└── PostgreSQL 16    # 本机监听 127.0.0.1（不对外）
```

| 决策点   | 方案                                                               |
| -------- | ------------------------------------------------------------------ |
| 单机     | 每日 pg_dump 备份（RPO≈1天/RTO≈几小时）                            |
| 双端部署 | web/mobile 静态产物由 Nginx 直接服务，更新零停机                   |
| 迁移执行 | 发布脚本显式执行（备份 → migrate → pm2 restart），非应用启动副作用 |
| 配置     | 生产 .env 存服务器不入 git；仓库只提交 .env.example                |
| HTTPS    | Nginx 终结；腾讯云免费证书或 Let''s Encrypt                        |
| 备份     | 每日 pg_dump + 保留策略 + 异地副本；至少一次恢复演练               |
| 安全边界 | 防火墙只开 443/22；PG 只监听本机；生产关闭调试                     |
| 日志     | NestJS 日志落盘 + Nginx log + logrotate 轮转                       |
| 发布流程 | 单人脚本：git pull → 备份 → build → migrate → pm2 restart          |
| 双端分流 | Nginx 层 UA 判断 302，零前端代码                                   |

- **PM2 配置**：`pm2 start apps/api/dist/main.js --name crm-api --env production`；`pm2 save` + `pm2 startup` 开机自启；日志走 pm2 logs

### 9.3 本地开发环境

- 数据库：本地开发两种方案——Docker（`docker compose` 提供 PostgreSQL 16 + pg_trgm 扩展）或本机已装 PG（建用户/建库/建扩展三步见 `docs/M0-工程骨架说明.md` 步 9，注意三条命令分开执行）；生产用部署机原生 PG
- 连接参数经 `.env` 注入（不入 git），配置模板提交 `.env.example`

## 十、开发与工程

> 契约模式：Contract-First（OpenAPI 契约优先）——契约是生成物，后端 DTO 为唯一事实源。

### 10.1 工程流程（单人 + 异地办公）

- 代码同步：git + GitHub 私有仓库；主干开发（main 直推，小改动小提交）
- 工程护栏：根 .gitignore（node_modules/dist/coverage/.env*/*.local）+ Node 版本约束（engines ≥ 20.19 或 22+，配 .nvmrc）
- 换机器可跑：提交 pnpm-lock.yaml + .env.example + README《环境准备清单》
- CI：GitHub Actions 自 M0 启用，使用一次性 PostgreSQL service，从空库执行 install → migrate → lint → typecheck → test → build → 契约无 diff；空库迁移同时验证 `pg_trgm` 等数据库前置能力，不依赖开发机历史状态；与本地门禁 husky + lint-staged 并行
- 数据备份：定时 pg_dump
- 测试基线：**统一 Vitest（API 不用 Jest——避免 jest-resolve→unrs-resolver 原生构建脚本；NestJS 用 Vitest + supertest）** + 后端单测（权威键硬查重/名称软查重、分级名额、接管审批、报价多次追加、行动生命周期、成交幂等、乐观锁冲突）+ 主链路 e2e（登录→建客户→拜访→行动→商机跟进→多次报价→明确下单）+ 前端表单组件单测 + 数据库测试打真 SQL

### 10.2 开发原则（Coding Principles）

1. **单一职责原则（SRP）**：每个文件/模块只承担一个职责；单文件 ≤ 400 行，超出按职责拆分——杜绝上帝对象（God Object / God Class）
2. **关注点分离（SoC）与模块化（Modularity）**：按架构层（表现/应用/领域/基础设施）与业务域组织，高内聚低耦合，模块间经显式接口协作
3. **依赖方向（Dependency Rule）**：依赖单向（表现层 → 应用层 → 领域层 ← 基础设施层）；禁止反向依赖与循环依赖

### 10.3 编码红线

| #   | 约束                                                                                                  |
| --- | ----------------------------------------------------------------------------------------------------- |
| 1   | HTTP 客户端全项目同源，禁止复制实现；传输层唯一，禁直接 fetch                                         |
| 2   | URL 与请求体按业务域收敛，禁止散落页面                                                                |
| 3   | 抽象层级匹配团队规模，避免过度设计                                                                    |
| 4   | 命名冲突用 import 别名                                                                                |
| 5   | 类型单源：契约类型唯一来源，禁止重复声明                                                              |
| 6   | 权限服务端收口，搜索不能绕开范围                                                                      |
| 7   | UUID 与文本字段不能混比（Drizzle 类型约束）                                                           |
| 8   | 「事件」与「当前状态」同时保存（事件表 + 主表状态）                                                   |
| 9   | 日期区分事实日期（occurredAt）与行动日期（plannedAt）；历史记录不得承载可变的未来计划                 |
| 10  | 业务周是业务口径，不是自然周替代品                                                                    |
| 11  | 前端状态更新不能依赖刷新（reload/setData）                                                            |
| 12  | 可复用业务表单必须同源                                                                                |
| 13  | 开发端口占用≠程序故障（health 检查）                                                                  |
| 14  | 审计日志用于业务回溯，不等于数据版本库                                                                |
| 15  | 移动端优先保证操作闭环                                                                                |
| 16  | 移动端适配禁止手工断点 CSS，样式只走 design-tokens                                                    |
| 17  | 禁止超大单体文件（单文件 ≤ 400 行，超出按职责拆分）——老项目 VisitsPage 2410 行的教训                  |
| 18  | 依赖构建脚本审批（pnpm ≥10）：未经 allowBuilds 放行的包禁止执行构建脚本；放行仅限确需运行才能工作的包 |
| 19  | 同一业务事实只维护一次：周视图查询 follow_up_actions，禁止从拜访/商机再复制计划项                     |
| 20  | 报价事实与成交事实分离：报价金额或报价记录不得隐式触发 Deal                                           |
| 21  | 可变聚合更新必须维护 updatedAt/version 并做条件更新；事件/历史表只追加                                |
| 22  | 归一化客户名只做查重线索，不设唯一约束；硬唯一仅使用客户编码/统一社会信用代码                         |

### 10.4 构建脚本审批策略（pnpm 11）

- pnpm ≥ 10 默认忽略依赖构建脚本（供应链安全）；被忽略的包自动写入 `pnpm-workspace.yaml` 的 `allowBuilds` 占位（`set this to true or false`），需人工判定后 `pnpm approve-builds` 或手改
- **测试统一 Vitest 后 API 不依赖 jest-resolve，`unrs-resolver` 不再出现**；`allowBuilds` 仅放行确需构建脚本的包（如原生 NAPI 绑定），其余一律 `false`
- 判定标准：包带 postinstall 且不运行会影响运行时正确性才放行；不确定的一律不放行
