## 一、项目定位

**面向小团队、线下拜访型 B2B 销售的轻量 CRM**：销售外勤用移动端填报客户动态/拜访/商机/客诉；管理者在桌面端查看经营看板（销售漏斗/转化/储备等）；形成「记录 → 跟进 → 闭环 → 洞察」链路。

| 优先级 | 领域                                                          |
| ------ | ------------------------------------------------------------- |
| P0     | 移动端填报体验（拜访/商机/客诉「顺手、快、不打断」）          |
| P1     | 数据闭环质量（事件与状态并存、事实日期准确、权限正确）        |
| P2     | 管理看板全面化（销售漏斗/转化/储备——AI insight 的确定性底座） |

**规模（已确认）**：客户 ~2000；用户 15；填报 ~150 条/天 → 单台普通服务器足够，**正确性与可维护性优先于性能**。

**环境（已确认）**：

- 桌面浏览器：Chrome + Edge
- 移动浏览器：Android 常规浏览器为主 + 少量 iOS Safari；钉钉内 WebView
- 部署：腾讯云 Linux 云服务器（单台 2C4G）；域名 + IP 已有（**ICP 备案待办**）
- 账号：初期账号密码；后期钉钉免登
- 双端访问：同域名不同路径 `/`（桌面）+ `/mobile/`（移动），入口按 UA 自动跳转，钉钉微应用 URL 配 `/mobile/`

## 三、仓库结构

> 架构模式：分层架构——表现层（apps/web、apps/mobile）/ 应用层（api 的 service）/ 领域层（packages/domain）/ 基础设施层（Drizzle、PG）。依赖方向：表现→应用→领域，基础设施依赖领域层（依赖倒置），禁止跨层调用。

```
crm/
  apps/
    web/                      # 桌面端：管理后台全集（Element Plus）
      src/pages/  src/features/  src/router/  src/theme/
    mobile/                   # 移动端 H5：填报子集（Vant）
      src/pages/  src/features/  src/router/  src/theme/
    api/                      # NestJS + Drizzle
      src/
        access/ auth/ org/ audit/ catalog/ customers/ claims/
        activities/ opportunities/ complaints/ planning/ expenses/
        team/ reporting/ ai/ alerts/ common/
  packages/
    contracts/                # openapi-typescript 生成契约（只含生成物 + 少量补充类型）
    domain/                   # 两端共享业务层
      services/               #   API 薄 client（基于生成契约）
      stores/                 #   Pinia（session/角标/周上下文）
      composables/            #   useQuery、格式化、权限判断
      types/                  #   非 API 领域类型
    design-tokens/            # 双端统一主题变量
    eslint-config/  tsconfig/
  docs/                       # adr/、milestones/
  pnpm-workspace.yaml
```

**硬性约束**：

- 后端是唯一事实源：DTO → Swagger → 契约 → 前端，单向下发
- domain 层唯一：API 调用、状态、权限判断、校验规则只在 packages/domain，两端 import，禁止复制
- 页面禁止直接 fetch / 拼 URL，一律走 domain/services
- 枚举单源：一律 import 契约枚举，禁止手写字符串字面量
- UI 库只管外观层，业务逻辑零重复

### 5.2 前端分层

> 模式：前端分层架构——页面编排层（pages，只做组装）/ 领域组件层（features）/ 基础设施层（libs）。

```
pages/          # 路由页面，只做编排（单组件 ≤ 400 行）
features/       # 领域组件 + 领域 composable（每业务域一个目录）
libs/           # api（传输层）/ query（useQuery）/ auth（Pinia store）/ ui（共享组件）
```

### 5.3 数据获取（useQuery）

> 模式：Repository 模式——页面不直接访问数据源，经 domain/services（repository 抽象）获取；useQuery 是缓存/加载封装。

```ts
// packages/domain/src/composables/useQuery.ts
// 接口对齐 TanStack Query：useQuery({ key, fetcher, options })；约 40 行
// 暴露 data / loading / error / reload() / setData()

const { data, loading, reload } = useQuery(`customers:list:${filters}`, () =>
  listCustomers(filters),
)
// 写操作后：reload() 或 setData()，不整页刷新
```

- 跨页共享状态（session/权限快照/角标/业务周）走 Pinia stores

### 5.4 重合功能 schema 共享（防双端表单漂移）

- domain 层定义字段配置（字段名/类型/必填/选项/校验/提交字段），桌面与移动表单组件读取同一份配置渲染
- 改字段只改 domain 一份，双端同时生效
- 主链路 e2e 双端各跑一遍，重合功能行为一致

## 六、后端规格

### 6.1 权限模型

> 参考：PDP/PEP——Guard 为策略执行点（PEP），统一权限服务为策略决策点（PDP），决策集中一处。

权限是贯穿所有业务模块的横切基础设施，由三个正交组件构成：

```
┌────────────────┐   ┌────────────────┐   ┌────────────────┐
│ 身份 Identity   │   │ 组织 Organization│   │ 授权 Authorization│
│ 我是谁？        │   │ 我属于哪个树？   │   │ 我能做什么/看什么？ │
│ (登录/JWT)     │   │ (reportsToId)  │   │ (能力点×数据范围)  │
└───────┬────────┘   └───────┬────────┘   └───────┬────────┘
        └────────────────────┼────────────────────┘
                             ▼
                   业务模块（查询/写操作必经横切）
```

- **三组件解耦**：登录不关心你有几个下属；组织树不管你会不会「导出」；授权只问「这个操作+这批数据，对你放行吗」
- **授权是唯一决策点**：「能做什么」由 Guard 统一裁决（能力点）；「能看什么」由统一权限服务在查询层过滤（数据范围）
- **服务端唯一决策**：前端只消费登录返回的权限快照（capabilities + dataScope），绕过前端的 API 调用同样被拦
- **审计独立**：「谁做了什么」是另一条横切链，与授权正交但依赖身份

**访问控制模式：混合式（RBAC × 组织树）**

| 模式                                     | 判断                             |
| ---------------------------------------- | -------------------------------- |
| 纯 RBAC（角色→权限）                     | 表达不了「看下属的」树形数据范围 |
| 纯 ABAC（属性→策略）                     | 策略引擎对小团队是负资产         |
| **混合：RBAC 管操作 + 组织树管数据范围** | **选定**——管理后台最常见形态     |

**数据范围（组织树自动推导）**：self（本人）/ team（本人+直属下属递归）/ full（全量）；admin/assistant 短路为 full；所有列表/搜索/看板查询统一 `WHERE owner_id IN (可见集合)`；region 是数据属性，不进权限模型

### 6.2 角色模型（4 类 = 能力组合）

| 角色             | 数据范围（树自动）    | 基础填报 | 管理操作    | 经营看板 | 全量统计/导出 | 系统配置 |
| ---------------- | --------------------- | -------- | ----------- | -------- | ------------- | -------- |
| sales 销售       | self / team           | ✅       | 有下属时 ✅ | ❌       | ❌            | ❌       |
| executive 经营层 | team（总经理=全公司） | ✅       | ✅          | ✅       | ❌            | ❌       |
| assistant 业助   | full                  | ❌       | ❌          | ✅ 只读  | ✅            | ❌       |
| admin 管理员     | full                  | 可选     | ✅          | ✅       | ✅            | ✅       |

- 用户 = 1 个角色 + reportsToId（上级）；管理层级完全由树决定，不设独立角色
- 销售线角色（sales/executive）默认具备填报；**经营看板仅 executive（方案 A）**
- assistant = 全量只读 + 统计确认的数据质量负责人（AI 统计的确认人，能力位预留）

### 6.3 后端模块清单

> 模式：模块化分层——每域 module/controller/service；业务模块依赖基础设施（access/auth/audit/common），禁止反向；业务模块间经服务接口或事件协作。

```
src/
  access/        # 组织范围权限（横切基础设施，收敛可见性计算）
  auth/          # 登录（password + dingtalk provider 抽象）/JWT/改密
  org/           # 用户、角色、汇报树、区域
  audit/         # 审计日志
  catalog/       # 客户维度配置（产业/应用/类型/产品线/来源）
  customers/     # 客户档案、联系人、验重、归属、移交、公海
  claims/        # 接管认领审批流
  activities/    # 拜访 + 销售日志聚合（查询面）
  opportunities/ # 商机 + 商机事件 + 成交 Deal
  complaints/    # 客诉 + 跟进事件
  planning/      # 业务周 + 周计划 + 指导意见
  expenses/      # 费用 + 作废
  team/          # 团队执行/费用/风险看板（只读聚合）
  reporting/     # 管理看板（经营三件套首批：漏斗/储备预测/转化率归因；趋势/结构后置，只读聚合）
  ai/            # AI 能力（intake 录入侧 + insight 分析侧；M8+ 实现，预留模块位）
  alerts/        # 提醒（定时扫描 + 站内）
  common/        # 基础 schema/枚举/过滤器
```

约束：业务服务禁止自行遍历组织树算权限，一律走统一权限服务；每接口必配 class-validator DTO。

### 6.4 跨模块联动

> 模式：本地事件（In-process Events）+ Unit of Work——强一致联动同一 UoW 提交；弱一致发布订阅。

- **强一致（直接调用 + 同一事务）**：拜访→自动生成周计划项、接管批准→三域交接（商机/客诉/未来计划项）
- **弱一致（@nestjs/event-emitter 进程内事件）**：商机推进→提醒、客诉登记→风险告警；失败不阻塞主流程
- 不引消息队列/事件总线

### 6.5 安全基线

| 项        | 方案                                                   |
| --------- | ------------------------------------------------------ |
| 登录凭证  | access token 2h + refresh token 14d 无感刷新           |
| 防爆破    | 同一账号连续 5 次密码错误锁定 15 分钟（按账号）        |
| 敏感字段  | 手机号等列表脱敏（138****1234），详情页/有权限者见全号 |
| 改密/停用 | 已签发 token 立即失效（token 版本号校验）              |

## 七、数据模型

### 7.1 schema 原则

> 领域建模模式：事件溯源变体（Event Log + 状态快照）——事件表只追加、主表存当前状态；聚合根封装不变量；命令/查询分离。

- 基础 schema：id（UUID 文本型）+ createdAt + updatedAt + version（乐观锁）
- 关系查询按需声明（with），默认高效 join，防 N+1
- 枚举/状态统一 **varchar + CHECK 约束 + 应用层枚举**（不用 PG enum——避免 ALTER TYPE 迁移坑）；users 表预留 phone（钉钉绑定）
- **AI 预留**：业务记录带 `entry_source`（manual/voice/image/chat/ai）+ `entry_ref_id`（原始素材引用）；预留 `ai_drafts` 草稿确认通道（AI 永不直接写业务数据，先草稿→人工确认→落库）；结构化优先，自由文本受控；指标口径单一来源；pg_trgm 现在上，pgvector M8 时装扩展 + 独立向量表（customer_embeddings，业务表不存向量）

### 7.2 实体清单（域 → 表）

> 聚合根：Customer / Opportunity / Complaint / WeeklyPlan / DailyExpense；其余为聚合内实体或事件。

| 域            | 实体表                                                               |
| ------------- | -------------------------------------------------------------------- |
| org           | users、capacity_config、user_capacity_overrides                      |
| customers     | customers、contacts、customer_transfers                              |
| opportunities | opportunities、opportunity_events、deals                             |
| complaints    | complaints、complaint_follow_ups                                     |
| activities    | visit_records                                                        |
| planning      | business_weeks、weekly_plans、weekly_plan_items、management_comments |
| expenses      | daily_expenses                                                       |
| claims        | customer_claim_requests                                              |

| alerts        | alerts                                                               |
| audit         | audit_logs                                                           |

### 数据模型 ER 图（Mermaid）

> 颜色约定：🟢 实体表（主数据/业务对象）｜🟠 关系表（明细/事件/流水）。

> 设计约定：① 字典字段（industry/sub_industry/customer_type/source/product_lines）存**字符串快照**，字典改名不同步、历史自洽；② 多态引用（management_comments/alerts/audit_logs）为**弱引用**，写路径必须校验目标存在；③ 派生字段（first_visited_at 等）由事件写入。
> 设计约定（功能边界）：① 费用=轻量统计（draft/submitted/voided 服务统计口径），无审批流，报销单据查验/审批打款排除在 CRM 边界外；② 下次拜访=visit 留档 + 强一致生成周计划项提醒（无溯源关联）；③ 计划与拜访两表独立，团队执行看板分列展示，不做配对。
> 设计约定（必填标注）：字段级 `?` = 数据库层可空；记录级条件必填（如「至少一个联系人电话」）用备注/应用层约束表达，不反映在字段级。
> 设计约定（归属语义）：归属单一事实源在 customers.owner_id（当前归属）；子实体（商机/客诉/拜访/跟进）的 owner_id = **创建时归属快照**（不可变，历史回溯用），当前归属一律 JOIN 客户推导——归属变更只改客户，子实体自动跟随且历史保留。

### 7.3 检索与查重

> 检索模式：三阶段检索（Exact 精确 → Fuzzy 模糊 → Vector 向量），各层职责边界清晰。

| 层     | 方案                                               | 时机 |
| ------ | -------------------------------------------------- | ---- |
| 精确层 | normalizedKey/客户编码/信用代码 唯一索引（硬拦截） | M2   |
| 模糊层 | pg_trgm 相似度查重 + GIN 索引加速检索              | M2   |
| AI 层  | pgvector embedding 变体识别                        | M8+  |

- **查重判定**：归一化后完全相等/信用代码或编码相同 → 硬拦截；别名/简称精确命中 或 trigram 相似度 ≥ 0.5 → 提示疑似重复（不拦截，忽略动作留审计）
- **归一化**：去空格/统一大小写/去「有限公司/集团」等后缀（效果比调阈值大）
- **检索排序**：完全匹配 > 前缀匹配 > 包含匹配 > 别名命中 > trigram 相似度兜底；输入即搜（防抖 300ms）
- **权限边界**：查重/搜索可命中权限外客户，但只返回最小标识（名称+城市）；详情必须走权限校验
- **迁移**：drizzle-kit 生成 SQL 迁移提交进仓库；CI 校验生成物无 diff

### 8.1 登录与身份

#### 时序流程（账号密码通道）

```mermaid
sequenceDiagram
    participant C as 前端
    participant S as AuthService
    participant U as users表
    C->>S: POST /auth/login (username, password)
    S->>U: 查用户（含锁定状态）
    U-->>S: user
    S->>S: 校验 locked_until / bcrypt 比对
    alt 密码错误
        S->>U: 失败计数+1（达5次→locked_until=now+15min）
        S-->>C: 401 账号或密码错误
    else 密码正确
        S->>U: 清失败计数 + 更新 last_login_at/ip
        S->>S: 签发 access(2h)+refresh(14d,滑动) + 权限快照
        S-->>C: access / refresh / user / 权限快照
    end
```

#### 关键规则

| 规则       | 内容                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------- |
| 防爆破     | 连续 5 次密码错误 → locked_until = now+15min；锁定期内拒绝（按账号）                      |
| 凭证       | access 2h + refresh 14d（JWT 无状态，**滑动续期**）                                       |
| token 失效 | JWT 携带 token_version；改密/停用 users.token_version+1 → 全部旧 token 失效（含 refresh） |
| 权限快照   | 登录响应带 capabilities + dataScope（dataScope 由组织树当次推导）                         |
| 登出       | 前端清理本地 token；服务端无撤销（改密/停用靠 token_version 兜底）                        |

#### 钉钉免登（M6）

- auth provider 抽象：password / dingtalk 两通道（/auth/login + /auth/dingtalk）
- 钉钉：dd.getAuthCode → 后端换身份（手机号匹配 users.phone）→ 复用同一签发逻辑
- 共用：签发、token_version、权限快照逻辑

#### 数据读写

| 操作     | 表       | 说明                                                             |
| -------- | -------- | ---------------------------------------------------------------- |
| 登录校验 | users 读 | username/password_hash/role/is_active/token_version/locked_until |
| 登录成功 | users 写 | last_login_at/ip、清失败计数                                     |
| 登录失败 | users 写 | 失败计数、锁定时间                                               |
| 改密     | users 写 | password_hash + token_version+1                                  |

#### 改密码（本人）

```mermaid
sequenceDiagram
    participant C as 前端
    participant S as AuthService
    participant U as users表
    C->>S: POST /auth/change-password (old, new)
    S->>U: 查用户
    S->>S: bcrypt 比对旧密码
    alt 旧密码错误
        S-->>C: 400 旧密码错误
    else 旧密码正确
        S->>S: 校验新密码强度（≥8 位）
        S->>U: 更新 password_hash + token_version+1
        S-->>C: 成功 → 前端清 token → 重新登录
    end
```

规则：旧密码 bcrypt 校验；新密码 ≥8 位；改密后 token_version+1 → 全部 token（含 refresh）立即失效，所有设备重新登录。

#### 重置密码（管理员）

```mermaid
sequenceDiagram
    participant A as admin
    participant S as UsersService
    participant U as users表
    A->>S: POST /users/:id/reset-password
    S->>S: 校验 admin（user.manage）
    S->>U: 生成随机临时密码 → 更新 password_hash + token_version+1
    S-->>A: 返回临时密码（仅此一次展示）
    A->>U: 线下告知用户 → 用其登录
```

规则：仅 admin（user.manage）；生成随机临时密码（不手填）；重置 token_version+1 → 该用户全端失效；不做自助找回、不做强制改密（保持简单）。

#### 多端登录

- 允许一账号多端（手机+电脑）同时在线——外勤常态；不做单端互斥
- 安全性由 token_version 兜底（改密/重置 → 全端失效）
- 数据模型无新增字段；未来若需强制改密加 must_change_password（当前不做）

> 推敲补充：users 加 login_failed_count + locked_until（防爆破状态持久化，已入 ER 图）。

### 8.2 客户录入与查重

#### 必填策略

| 字段          | 策略                     | 说明                                                            |
| ------------- | ------------------------ | --------------------------------------------------------------- |
| name          | 必填                     | 可地址式名称（园区客户填「XX工业园3栋2楼」）                    |
| 联系人电话    | 必填（至少一个，可无名） | 电话统一挂联系人（main_phone 已废弃）；无名联系人承担「裸电话」 |
| address       | 软建议                   | 园区客户自然要填                                                |
| 信用代码/编码 | 可选                     | 有则权威硬查重                                                  |

#### 查重管道（五步）

```mermaid
flowchart TD
    A[录入名称/地址/电话] --> B[① 清洗归一化<br/>名称→商号key 地址→去量词 电话→去符号 pinyin-pro生成拼音]
    B --> C[② 硬拦截 唯一索引<br/>商号key 编码 信用代码]
    C -->|命中| D[409 已存在 硬拦]
    C -->|未命中| E[③ 候选生成 Blocking<br/>同园区名 同电话 同商号首字]
    E --> F[④ 相似度比较<br/>natural Jaro-Winkler pg_trgm pinyin同音字 电话精确]
    F --> G[⑤ 置信度分级 高中低]
    G --> H[前端弹疑似列表 + 继续新建 + 申请接管]
```

#### 主次通道与库组合

| 通道         | 字段                  | 保证       | 实现                                                 |
| ------------ | --------------------- | ---------- | ---------------------------------------------------- |
| 名称（主）   | name                  | 必填       | natural(Jaro-Winkler) + pg_trgm + pinyin-pro(同音字) |
| 电话（主）   | contacts.phone        | 至少一必填 | 归一化后精确                                         |
| 地址（增强） | address               | 软建议     | pg_trgm                                              |
| 权威（硬拦） | 商号key/编码/信用代码 | 可选       | 唯一索引                                             |

#### 缺失处理

- 通道「有则参与，无则跳过」——字段缺失不拖累其他通道
- 唯一约束对 NULL 天然放行（没填信用代码的互不误拦）
- 置信度只按参与通道计算
- 口语名 + 无地址无电话 → 软提示「信息不完整，可能无法识别重复」（不拦截）

#### 置信度分级

| 置信度 | 命中条件                                                     | 前端                |
| ------ | ------------------------------------------------------------ | ------------------- |
| 高     | 商号key精确 / 地址归一化精确 / 拼音相同且字数相同 / 电话精确 | 醒目提示 + 申请接管 |
| 中     | trigram ≥0.5 / Jaro-Winkler ≥0.8                             | 普通提示            |
| 低     | 弱相似                                                       | 弱提示              |

#### 检索

- 输入即搜（防抖 300ms）：完全 > 前缀 > 包含 > 别名 > trigram 兜底
- 权限过滤：owner_id IN (可见集合)（与查重的全库不同）
- 结果：名称 + 城市 + 负责人 + 等级

#### 批量查重（M7 后）

- 全库跑同管道 → 聚类（传递闭包）→ 疑似重复报告 → 业助处理

#### 权限边界

- 查重/搜索可命中权限外客户，但只返回最小标识（名称+城市）；点击详情走权限
- 命中权限外客户 → 前端显示「已有归属 · 申请接管」

```mermaid

    else 传了 ownerId（指定负责人）
        S->>U: 校验负责人存在 + 分级容量（S/A/B/C）
        U-->>S: OK / 超限拒绝
    end
    S->>S: 建档（created_by_id=登记人, owner_id=归属人）
    S-->>F: 201 建档成功
```

- 数据模型：created_by_id（建档人）与 owner_id（负责人）**两个独立字段**，语义分离
- **默认策略**：未指定负责人 → owner_id = created_by_id（录入即所有权，90% 场景零操作）
- **指定负责人**：录入表单可选传 owner_id（代录场景：业助/管理员帮销售录 → 指定归属该销售），校验容量
- **应用层责任**：默认值、指定、容量校验均在 Service/DTO 层，数据模型无需额外字段

**时序**

```mermaid
sequenceDiagram

    participant S as ClaimsService
```

- **禁止自我审批**：候选池排除申请人；当前 owner 同意让出自己的客户（被接管方确认）允许
- **并发防护**：同客户仅一条 pending（唯一性）、归属快照校验（currentOwnerId）、容量校验
- **超时升级（轻量）**：pending 超 7 天 → 提醒 owner + 通知管理链

## 九、集成与部署

> 架构模式：标准 Web 部署——Nginx（反向代理 + 静态资源 + HTTPS 终结）+ 应用服务（PM2 守护）+ 关系型数据库（PG）。

### 9.1 钉钉集成（M1 抽象 / M6 实现）

- **auth provider 抽象**：password（桌面/移动浏览器）+ dingtalk（钉钉内）；前端按 UA 检测钉钉环境决定登录方式
- **免登流程**：钉钉内 H5 → `dd.getAuthCode` → 后端调钉钉开放平台换身份（手机号/工号）→ 匹配 users 表 → 签发本系统 JWT
- **schema**：users.phone；登录双通道 `POST /auth/login` 与 `POST /auth/dingtalk`
- **前提**：域名完成 ICP 备案 + HTTPS（备案待办，1-2 周流程）

### 9.2 部署架构

```
腾讯云 Linux 服务器（单台 2C4G）
├── Nginx            # 唯一对外入口（443 HTTPS）+ 双端静态资源 + /api 反向代理 + UA 分流
├── Node 服务        # NestJS，PM2 守护（127.0.0.1:3001）
└── PostgreSQL 16    # 本机监听 127.0.0.1（不对外）
```

| 决策点   | 方案                                                               |
| -------- | ------------------------------------------------------------------ |
| 单机     | 每日 pg_dump 备份（RPO≈1天/RTO≈几小时）                            |
| 双端部署 | web/mobile 静态产物由 Nginx 直接服务，更新零停机                   |
| 迁移执行 | 发布脚本显式执行（备份 → migrate → pm2 restart），非应用启动副作用 |
| 配置     | 生产 .env 存服务器不入 git；仓库只提交 .env.example                |
| HTTPS    | Nginx 终结；腾讯云免费证书或 Let''s Encrypt                        |
| 备份     | 每日 pg_dump + 保留策略 + 异地副本；至少一次恢复演练               |
| 安全边界 | 防火墙只开 443/22；PG 只监听本机；生产关闭调试                     |
| 日志     | NestJS 日志落盘 + Nginx log + logrotate 轮转                       |
| 发布流程 | 单人脚本：git pull → 备份 → build → migrate → pm2 restart          |
| 双端分流 | Nginx 层 UA 判断 302，零前端代码                                   |

- **PM2 配置**：`pm2 start apps/api/dist/main.js --name crm-api --env production`；`pm2 save` + `pm2 startup` 开机自启；日志走 pm2 logs

### 9.3 本地开发环境

- 数据库：本地开发两种方案——Docker（`docker compose` 提供 PostgreSQL 16 + pg_trgm 扩展）或本机已装 PG（建用户/建库/建扩展三步见 `docs/M0-工程骨架说明.md` 步 9，注意三条命令分开执行）；生产用部署机原生 PG
- 连接参数经 `.env` 注入（不入 git），配置模板提交 `.env.example`

## 十、开发与工程

> 契约模式：Contract-First（OpenAPI 契约优先）——契约是生成物，后端 DTO 为唯一事实源。

### 10.1 工程流程（单人 + 异地办公）

- 代码同步：git + GitHub 私有仓库；主干开发（main 直推，小改动小提交）
- 工程护栏：根 .gitignore（node_modules/dist/coverage/.env*/*.local）+ Node 版本约束（engines ≥ 20.19 或 22+，配 .nvmrc）
- 换机器可跑：提交 pnpm-lock.yaml + .env.example + README《环境准备清单》
- CI：GitHub Actions 自 M0 启用（install → lint → typecheck → test → build → 契约无 diff），与本地门禁 husky + lint-staged 并行
- 数据备份：定时 pg_dump
- 测试基线：**统一 Vitest（API 不用 Jest——避免 jest-resolve→unrs-resolver 原生构建脚本；NestJS 用 Vitest + supertest）** + 后端单测（验重/分级容量/接管审批链/费用作废/周计划联动）+ 主链路 e2e（登录→建客户→拜访→商机→成交）+ 前端表单组件与看板逻辑单测 + 数据库测试打真 SQL

### 10.2 开发原则（Coding Principles）

1. **单一职责原则（SRP）**：每个文件/模块只承担一个职责；单文件 ≤ 400 行，超出按职责拆分——杜绝上帝对象（God Object / God Class）
2. **关注点分离（SoC）与模块化（Modularity）**：按架构层（表现/应用/领域/基础设施）与业务域组织，高内聚低耦合，模块间经显式接口协作
3. **依赖方向（Dependency Rule）**：依赖单向（表现层 → 应用层 → 领域层 ← 基础设施层）；禁止反向依赖与循环依赖

### 10.3 编码红线

| #   | 约束                                                                                                  |
| --- | ----------------------------------------------------------------------------------------------------- |
| 1   | HTTP 客户端全项目同源，禁止复制实现；传输层唯一，禁直接 fetch                                         |
| 2   | URL 与请求体按业务域收敛，禁止散落页面                                                                |
| 3   | 抽象层级匹配团队规模，避免过度设计                                                                    |
| 4   | 命名冲突用 import 别名                                                                                |
| 5   | 类型单源：契约类型唯一来源，禁止重复声明                                                              |
| 6   | 权限服务端收口，搜索不能绕开范围                                                                      |
| 7   | UUID 与文本字段不能混比（Drizzle 类型约束）                                                           |
| 8   | 「事件」与「当前状态」同时保存（事件表 + 主表状态）                                                   |
| 9   | 日期区分事实日期（occurredAt）与计划日期（nextFollowUpDate）                                          |
| 10  | 业务周是业务口径，不是自然周替代品                                                                    |
| 11  | 前端状态更新不能依赖刷新（reload/setData）                                                            |
| 12  | 可复用业务表单必须同源                                                                                |
| 13  | 开发端口占用≠程序故障（health 检查）                                                                  |
| 14  | 审计日志用于业务回溯，不等于数据版本库                                                                |
| 15  | 移动端优先保证操作闭环                                                                                |
| 16  | 移动端适配禁止手工断点 CSS，样式只走 design-tokens                                                    |
| 17  | 禁止超大单体文件（单文件 ≤ 400 行，超出按职责拆分）——老项目 VisitsPage 2410 行的教训                  | 前端组件/页面、后端 service/controller 通用约束 |
| 18  | 依赖构建脚本审批（pnpm ≥10）：未经 allowBuilds 放行的包禁止执行构建脚本；放行仅限确需运行才能工作的包 | 供应链安全                                      |

### 10.4 构建脚本审批策略（pnpm 11）

- pnpm ≥ 10 默认忽略依赖构建脚本（供应链安全）；被忽略的包自动写入 `pnpm-workspace.yaml` 的 `allowBuilds` 占位（`set this to true or false`），需人工判定后 `pnpm approve-builds` 或手改
- **测试统一 Vitest 后 API 不依赖 jest-resolve，`unrs-resolver` 不再出现**；`allowBuilds` 仅放行确需构建脚本的包（如原生 NAPI 绑定），其余一律 `false`
- 判定标准：包带 postinstall 且不运行会影响运行时正确性才放行；不确定的一律不放行
