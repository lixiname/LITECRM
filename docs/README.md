# Lite CRM 文档导航与版本规则

> 本页是 `docs/` 的入口。代码变更只同步“现行文档”，带 V0.x/M0 名称的阶段稿保留当时上下文，不做追溯修改。

## 1. 现行文档

| 文档                        | 回答的问题                           | 何时随代码更新                     |
| --------------------------- | ------------------------------------ | ---------------------------------- |
| `重构架构决策与实施蓝图.md` | 目标模型、架构约束和里程碑是什么     | 业务语义、数据模型或技术决策变化时 |
| `PRD.md`                    | 用户要完成什么、规则和验收标准是什么 | API 行为、业务规则或页面能力变化时 |
| `交互设计打磨.md`           | 功能如何呈现、页面如何衔接           | 关键流程或交互模式变化时           |
| `技术打磨清单.md`           | 当前还有哪些实现阻断项               | 每批开发完成后勾选并注明剩余边界   |
| `M0-M5模型收口实施记录.md`  | 目标方案已经落到代码的哪一步         | 每个模型收口提交同步追加一条记录   |
| `测试体系与编写指南.md`     | 如何验证实现                         | 测试策略、命令或测试分层变化时     |

现行文档描述“当前有效结论”。发生替代性决策时直接修改现行文档，并在实施记录中说明变化，不再新建一份内容高度重复的 V0.x 文件。

## 2. 冻结快照与参考材料

以下文件用于追溯立项讨论或外部调研，不要求随代码更新：

- `工业设备销售全过程CRM建设蓝图及项目立项方案-V0.1.md`
- `工业设备销售全过程CRM项目立项汇报-V0.2.md`
- `工业设备销售全过程CRM建设方案纲要-V0.3.md`
- `工业设备销售全过程CRM立项简报-V0.4.html`
- `M0-工程骨架说明.md`
- `B2B-CRM全球代表产品与移动端体验调研.md`

如需修订管理层材料，应产生明确的新版本；外部调研有新的证据时单独形成新调研基线，不能用实现状态反向改写原始调研结论。

## 3. 同步规则

每个代码批次至少检查四件事：

1. 目标模型是否变化；变化则更新技术规格。
2. 用户可感知行为或验收标准是否变化；变化则更新 PRD/交互文档。
3. 实施状态是否变化；必须更新技术打磨清单和实施记录。
4. 数据库结构或接口是否变化；迁移、OpenAPI 生成物、测试与代码同批提交。

Git 提交是版本事实源。文档头部版本号用于辨认内容基线，不替代提交历史。
