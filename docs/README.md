# Lite CRM 文档入口

> 如果不知道该看哪一份，从本页开始。目录编号同时表示文档状态和推荐顺序；只有 `01-当前有效` 中的文档是当前设计依据。

## 一、目录状态

| 目录                            | 状态                   | 如何使用                                             |
| ------------------------------- | ---------------------- | ---------------------------------------------------- |
| [`01-当前有效`](./01-当前有效/) | **在用，持续维护**     | 产品、模型、交互、开发和验收均以这里为准             |
| [`02-参考资料`](./02-参考资料/) | **按需查阅，不是规格** | 查外部产品依据、历史工程背景时使用                   |
| [`03-实施证据`](./03-实施证据/) | **只证明做过什么**     | 查迁移、测试和阶段收口证据，不用来决定系统应如何设计 |
| [`99-历史归档`](./99-历史归档/) | **不再使用**           | 仅追溯立项演变和旧方案；不得作为新开发依据           |

根目录中的 Excel 是本地业务材料，已排除版本控制，不属于产品规格。

## 二、当前有效文档的阅读顺序

第一次完整了解项目时，按以下顺序阅读：

1. [CRM 业务设计方法与成熟产品借鉴](./01-当前有效/CRM业务设计方法与成熟产品借鉴.md)

   先理解 CRM 为什么这样设计、成熟产品与理论能借鉴什么。

2. [产品需求明细（PRD）](./01-当前有效/PRD.md)

   再了解用户、业务流程、规则、页面能力和验收口径。

3. [架构决策与实施蓝图](./01-当前有效/重构架构决策与实施蓝图.md)

   接着确认对象、状态机、数据模型、权限、事务和集成边界。

4. [交互设计打磨](./01-当前有效/交互设计打磨.md)

   然后看业务模型如何呈现在桌面端和移动端。

5. [技术质量门禁清单](./01-当前有效/技术打磨清单.md)

   开发前确认通用工程约束和质量红线。

6. [测试体系与编写指南](./01-当前有效/测试体系与编写指南.md)

   最后确定如何验证实现。

`01-当前有效/README.md` 保存同一份简明顺序，直接进入该目录时也不会失去上下文。

## 三、按任务选择文档

| 当前任务           | 必读               | 需要时补充                     |
| ------------------ | ------------------ | ------------------------------ |
| 讨论新业务功能     | 业务设计方法、PRD  | 架构蓝图、交互设计             |
| 修改数据模型或权限 | 架构蓝图、PRD      | 技术清单、测试指南             |
| 调整页面和流程     | 交互设计、PRD      | 架构蓝图                       |
| 修复代码缺陷       | 技术清单、测试指南 | 对应 PRD/架构章节              |
| 做竞品或理论比较   | 业务设计方法       | `02-参考资料` 中的全球产品调研 |
| 查本轮是否已经实现 | `03-实施证据`      | Git 历史和测试结果             |
| 查立项过程         | `99-历史归档`      | 不反向覆盖当前有效文档         |

## 四、发生冲突时以谁为准

1. 用户行为、业务规则和验收结果，以 `PRD.md` 为准。
2. 对象语义、数据模型、权限、事务和技术边界，以架构蓝图为准。
3. 页面布局、入口和衔接方式，以交互设计为准。
4. 工程质量和验证方式，以技术清单与测试指南为准。
5. 业务设计方法解释“为什么”，但不替代已经确认的 PRD 规则。
6. 参考资料、实施证据和历史归档均无权覆盖当前有效文档。

若当前有效文档之间相互矛盾，不靠阅读顺序猜测，应先明确业务决定，再在同一提交中同步修订相关文档。

## 五、维护规则

- 业务语义、用户规则或验收口径变化：修改 PRD；涉及模型时同步架构蓝图，涉及界面时同步交互设计。
- 只有实现进度变化：不修改当前设计文档，由 Git、测试和实施证据记录。
- 外部产品或理论出现新证据：更新业务设计方法或参考资料，不直接改写本公司规则。
- 过期的排期、冻结稿和汇报稿移入 `99-历史归档`，不在当前目录保留同名副本。
- Git 是版本历史来源，文档正文不维护“本次改了什么”的流水账。
